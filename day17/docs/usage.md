# День 17 — свой MCP-сервер и вызов инструментов

Инструкция по приложению дня 17. День добавляет **свой MCP-сервер** и **вызов
инструментов**: в папке лежит собственный MCP-сервер `day17/mcp_server/`
(транспорт stdio), который публикует три инструмента поверх публичного mock API
`https://jsonplaceholder.typicode.com` — `get_user`, `get_post` и
`list_user_posts`. Клиент и реестр умеют не только читать каталог (`tools/list`),
но и вызывать инструмент (`tools/call`), а агент **сам** решает по ключевым
словам реплики, нужен ли вызов, вызывает инструмент и использует полученные
данные в ответе.

Что появилось в приложении: раздел «🔌 MCP» с каталогом известных серверов,
формой ручного вызова инструмента и блоком «🤖 Спросить агента»; эндпоинты
`POST /mcp/call` и `GET /mcp/servers`; скрипты `scripts/mcp_tool_demo.py` и
`scripts/mcp_tool_report.py` с отчётом `docs/reports/mcp_tool_demo.md`. Как
устроено внутри — [architecture.md](architecture.md), эндпоинты с примерами —
[api.md](api.md), прогон дня — [reports/mcp_tool_demo.md](reports/mcp_tool_demo.md),
карта модулей — [../STRUCTURE.md](../STRUCTURE.md).

## 1. Что нужно для запуска

|Компонент|Зачем|Проверка|
|---|---|---|
|Python 3.14 и `uv`|зависимости дня и запуск|`uv --version`|
|Сеть до `https://jsonplaceholder.typicode.com`|данные, которые читают инструменты своего сервера|`curl -s -o /dev/null -w "%{http_code}" https://jsonplaceholder.typicode.com/users/1` → `200`|
|Ключ `DEEPSEEK_API_KEY`|только ответ агента (генерация моделью)|`day17/.env`|

Вызовы инструментов от ключа **не зависят**: свой сервер читает открытый mock
API по HTTP, поэтому каталог, ручные вызовы, сквозной прогон и отчёт дня
работают без ключа. Ключ нужен только там, где ответ строит DeepSeek, — это
чат и кнопка «🤖 Спросить агента». Кстати, и в них вызов инструмента виден даже
при ошибке генерации: отчёт `mcp` заполняется до обращения к модели.

## 2. Установка и запуск

Менеджер зависимостей — `uv`: прямые зависимости в `pyproject.toml`, точные
версии — в `uv.lock`, интерпретатор — `.python-version`. Активировать окружение
не нужно, `uv run` сам находит `.venv`.

```bash
cd day17
uv sync                  # создать .venv по uv.lock (в том числе mcp и httpx)
cp .env.example .env     # затем впишите DEEPSEEK_API_KEY=sk-... (для ответа агента)
```

`uv sync` нужно выполнить **до** первого подключения: цель по умолчанию
(`uv run python mcp_server/server.py`) запускается дочерним процессом, и `uv run`
должен найти уже готовый `.venv` — иначе первая синхронизация окружения может не
уложиться в таймаут подключения `MCP_TIMEOUT = 30.0` с.

Терминал 1 — бэкенд (MCP-подключение живёт в его процессе):

```bash
uv run uvicorn backend.api.main:app --port 8000
```

Терминал 2 — интерфейс: <http://localhost:8501>

```bash
uv run streamlit run app.py
```

Проверка перед работой:

```bash
uv run python scripts/mcp_tool_demo.py   # каталог, вызовы инструмента и шаг агента в консоли
uv run pytest -q                         # весь набор дня: 1222 теста
```

## 3. Свой MCP-сервер

Пакет `day17/mcp_server/` — это MCP-сервер, который запускается как отдельный
процесс и общается с клиентом по JSON-RPC через stdin/stdout (транспорт stdio).

|Файл|Что внутри|
|---|---|
|`config.py`|адрес внешнего API (`DEFAULT_API_BASE = "https://jsonplaceholder.typicode.com"`), таймаут запроса (`DEFAULT_TIMEOUT = 10.0`), границы (`MAX_USER_ID = 10`, `MAX_POSTS_LIMIT = 20`), имя `day17-jsonplaceholder`, версия `1.0.0` и инструкция сервера|
|`schemas.py`|`TypedDict`-структуры ответов (`UserInfo`, `PostInfo`, `PostSummary`, `UserPosts`) — из них SDK собирает `outputSchema`|
|`api_client.py`|HTTP-часть: `JsonPlaceholderClient` (`get_user`, `get_post`, `list_user_posts`), ошибка `ExternalAPIError`, настройка `configure()`/`get_client()`|
|`server.py`|объявление инструментов через `@server.tool()`, разбор аргументов и запуск сервера по stdio|

Запуск руками (из папки дня):

```bash
uv run python mcp_server/server.py --help   # аргументы и код 0
uv run python mcp_server/server.py          # сервер ждёт JSON-RPC на stdin
```

Без `--help` сервер ничего не печатает и просто ждёт запросов на стандартном
вводе — это нормально для stdio-транспорта, и «посмотреть» его в обычном
терминале не получится. Подключайтесь к нему из интерфейса, через API или
скриптом: там он поднимается дочерним процессом сам.

|Аргумент|По умолчанию|Что делает|
|---|---|---|
|`--api-base`|`https://jsonplaceholder.typicode.com`|база внешнего API (тесты и офлайн-прогон подставляют локальный стенд)|
|`--timeout`|`10.0`|таймаут одного HTTP-запроса к внешнему API, с|

Инструменты сервера:

|Инструмент|Параметры|Что возвращает|
|---|---|---|
|`get_user`|`user_id: int` — обязательный|`UserInfo`: `id`, `name`, `username`, `email`, `city`, `phone`, `website`, `company`|
|`get_post`|`post_id: int` — обязательный|`PostInfo`: `id`, `user_id`, `title`, `body`|
|`list_user_posts`|`user_id: int` — обязательный, `limit: int = 5` — от 1 до 20|`UserPosts`: `user_id`, `count`, `posts` (список `{id, title}`)|

Из чего SDK собирает схемы инструмента:

- `inputSchema` — из аннотаций типов и значений по умолчанию; у `get_user` это
  `{"properties": {"user_id": {"type": "integer"}}, "required": ["user_id"]}`,
  у `list_user_posts` — два свойства, обязательное только `user_id`;
- `outputSchema` — из `TypedDict`-аннотации возврата (`UserInfo`, `PostInfo`,
  `UserPosts`);
- `structuredContent` ответа равен самому словарю, который вернул инструмент, а
  `description` инструмента — его docstring: по нему модель понимает, что
  делает инструмент и что значат параметры.

Ошибки внешнего API не роняют сервер и не выглядят трассировкой: `api_client.py`
переводит их в понятный текст, `server.py` — в ошибку инструмента, поэтому
причина доходит и до модели, и до вас в поле `text` результата:

- нет пользователя: «Пользователь с id=999 не найден (HTTP 404): у
  jsonplaceholder 10 пользователей, id от 1 до 10»;
- нет поста: «Пост с id=999 не найден (HTTP 404): у jsonplaceholder 100 постов,
  id от 1 до 100»;
- `limit` вне 1..20: «limit должен быть от 1 до 20, получено 25»;
- сеть/прочий сбой: «Внешний API … недоступен: …».

## 4. Подключение из интерфейса и через API

### Через интерфейс

1. Откройте <http://localhost:8501> (бэкенд уже запущен на порту 8000).
2. В переключателе разделов вверху страницы выберите **«🔌 MCP»**.
3. В поле «URL или команда запуска MCP-сервера» подставлена цель по умолчанию —
   свой сервер дня: `uv run python mcp_server/server.py`. Транспорт оставьте
   `auto`: по виду цели он определяет stdio (команда запуска), `http://` —
   Streamable HTTP, `sse://` — SSE. Явный выбор транспорта сильнее
   автоопределения.
4. Нажмите **«🔌 Подключиться»**. Плашка статуса станет зелёной: имя и версия
   сервера (`day17-jsonplaceholder 1.0.0`), согласованная версия протокола, число
   инструментов и список допустимых событий.

Ниже раздела — **каталог MCP-серверов** (`GET /mcp/servers`): свой сервер дня и
два сервера официального набора (fetch через `uvx`, filesystem через `npx`).
В таблице видны цель, отметка «подключён» и число инструментов у подключённого;
любую другую цель можно выбрать в списке и нажать **«🔌 Подключиться к этому
серверу»**.

Отключение — кнопка **«⏏ Отключиться»**: соединение закрывается, а дочерний
процесс stdio-сервера останавливается. Повторное отключение без соединения —
безопасный no-op. Остановка бэкенда (Ctrl+C) тоже закрывает соединение, поэтому
сервер не остаётся висеть. **Соединение у процесса одно**: подключение к другой
цели закрывает прежнее.

### Через API

```bash
curl -X POST http://127.0.0.1:8000/mcp/connect \
     -H "Content-Type: application/json" \
     -d '{"target": "uv run python mcp_server/server.py"}'
curl http://127.0.0.1:8000/mcp/status
```

`POST /mcp/connect` возвращает то же, что `GET /mcp/status`:

|Поле|Значение|
|---|---|
|`connected`|открыто ли соединение прямо сейчас|
|`state`|состояние стейт-машины: `disconnected` → `connecting` → `connected` / `error`|
|`target`, `transport`, `transport_label`|куда и как подключены|
|`server_name`, `server_version`, `protocol`|что ответил сервер на `initialize` (пусто без соединения)|
|`tool_count`|сколько инструментов уже получено (`0`, пока список не запрашивали)|
|`error`|текст последней ошибки соединения|
|`allowed_events`|что допустимо в этом состоянии (`connect` / `disconnect` / `fail`)|

Недоступный сервер — `502` с текстом причины, неразобранная цель — `400`.
Таймаут подключения и запросов к серверу — `MCP_TIMEOUT = 30.0` с (значение по
умолчанию; скрипт демонстрации принимает `--timeout`).

## 5. Как посмотреть инструменты

**В интерфейсе.** Раздел «🔌 MCP» рисует под статусом подраздел
«🧰 Инструменты MCP-сервера»: подпись «Инструментов: N» и таблицу
`name` / `description` / `input_schema` (схема — одной строкой, обрезанная).
Ниже в раскладке «🧾 Полная input_schema инструмента» выбирается инструмент и
показываются обе схемы целиком: `input_schema` (аргументы) и `output_schema`
(структура `structuredContent` — пусто, если сервер её не публикует).

**Обновить список.** Кнопка **«🔄 Обновить список инструментов»** — запрос идёт с
`refresh=true`, то есть сервер опрашивается заново (без нажатия список берётся
из кэша открытой сессии).

**Через API.**

```bash
curl http://127.0.0.1:8000/mcp/tools
curl "http://127.0.0.1:8000/mcp/tools?refresh=true"   # перезапросить у сервера
```

Ответ содержит инструменты (`name`, `description`, `input_schema`,
`output_schema`), их `count`, а также `target`, `transport`, `server_name` и
`server_version`. Без соединения запрос возвращает `409` — «пусто» и «не
подключено» не путаются.

**Каталог серверов** — `GET /mcp/servers`: три записи (`key`, `label`, `target`,
`description`, `connected`, `tool_count`), `count` и поля `connected_target` /
`connected_key`. `connected` истинно ровно у одного сервера — того, с которым
открыто соединение процесса; `tool_count` заполнен только у него. Это не список
одновременных подключений, а «что ещё можно подключить».

## 6. Как вызвать инструмент вручную

**В интерфейсе** под таблицей инструментов есть подраздел «▶ Вызов инструмента»:

1. Выберите инструмент в списке «Инструмент».
2. Подпись «обязательные аргументы: …» показывает, что обязательно (у `get_user`
   это `user_id`).
3. Заполните форму — она строится по `input_schema` инструмента, а не по списку
   известных полей: `integer`/`number` → числовое поле (значение по умолчанию —
   из схемы, иначе `1`), `boolean` → флажок, `string` → строка, массив или
   объект → строка JSON. Пустой необязательный аргумент не отправляется вовсе,
   поэтому сервер подставляет своё значение по умолчанию (`limit=5`).
4. Нажмите **«▶ Вызвать инструмент»**. Результат появится в подразделе
   «🧾 Результат вызова»: состояние, длительность, имя инструмента и аргументы;
   сами данные — структурированным JSON (для `get_user` — карточка пользователя,
   для `list_user_posts` — список постов), а `limit=3` даёт ровно три поста.

Форма доступна только при подключённом сервере — каталог инструментов приходит
с него, поэтому без соединения вызов вручную сделать нечем.

**Через API.**

```bash
curl -X POST http://127.0.0.1:8000/mcp/call \
     -H "Content-Type: application/json" \
     -d '{"tool": "get_user", "arguments": {"user_id": 1}}'

curl -X POST http://127.0.0.1:8000/mcp/call \
     -H "Content-Type: application/json" \
     -d '{"tool": "list_user_posts", "arguments": {"user_id": 1, "limit": 3}}'
```

Тело запроса — `tool` (имя из `GET /mcp/tools`, до 100 символов) и `arguments`
(по `input_schema`). Ответ (`MCPCallResponse`): `accepted`, `state`, `detected`,
`connected`, `called`, `tool`, `arguments`, `result`, `is_error`, `reason_code`,
`error`, `duration_ms` и `allowed_events`; внутри `result` — `structured`
(структурированные данные), `text` и `duration_ms`.

Коды ответа:

|Ситуация|Код|Что в теле|
|---|---|---|
|вызов прошёл|`200`|`state: "done"`, `result` со структурированными данными|
|инструмент сам вернул ошибку (например, нет пользователя с таким id)|`200`|`is_error: true`, текст причины в `result.text`|
|соединения нет|`409`|`detail` про то, что нужно подключиться через `POST /mcp/connect`|
|инструмента нет в каталоге или аргументы не подходят по схеме|`400`|`detail` с причиной и подсказкой|
|соединение оборвалось, ответа нет|`502`|`detail` — отказ транспорта|
|невалидное тело (пустой `tool`, имя длиннее 100 символов)|`422`|ошибки Pydantic|

Разница принципиальна: «не смогли вызвать» — это отказ HTTP-запроса (400/409/502),
а «инструмент ответил, что не получилось» — это данные (`200` + `is_error`),
потому что и модель, и пользователь должны видеть текст причины.

## 7. Как спросить агента

**В интерфейсе** внизу раздела есть блок «🤖 Спросить агента»: выберите агента,
введите реплику и нажмите **«🤖 Спросить агента»**. Агент получает запрос как
обычный ход генерации и по ключевым словам реплики сам решает, нужен ли вызов
инструмента подключённого сервера. Инструмент и аргументы подбирают доменные
правила (`backend/domain/mcp_intent.py`), а не модель, поэтому вызов видно в
ответе, а данные инструмента дописываются блоком «## Данные MCP-инструмента» в
системный промпт того же запроса — модель отвечает по ним, а не по памяти.
Генерация требует ключа `DEEPSEEK_API_KEY` у бэкенда; сам вызов инструмента от
ключа не зависит.

Распознаваемые реплики (правила идут в порядке приоритета: сначала «посты
пользователя», затем «пользователь», затем «пост»):

|Реплика|Инструмент|Аргументы|
|---|---|---|
|«Какие посты у пользователя 2»|`list_user_posts`|`{"user_id": 2}`|
|«Найди информацию о пользователе с ID 1»|`get_user`|`{"user_id": 1}`|
|«Покажи пост 3»|`get_post`|`{"post_id": 3}`|
|«Расскажи про пользователя» (номера нет)|`get_user`|`{}` → отказ `bad_arguments`: «Не указан обязательный аргумент «user_id»…»|
|«Сколько будет 2+2?»|—|вызова нет вовсе (`detected: false`)|

Фразы сравниваются по началу слова с допуском до трёх букв окончания, поэтому
«пользователя», «пользователю» и «пользователей» совпадают, а
«пользовательский» — нет. Номер аргумента — первое число в тексте.

**Что видно в ответе.** В блоке «💬 Ответ агента» под репликой — ответ модели, а
под ним блок «🔧 MCP-инструмент»: состояние вызова, имя инструмента, аргументы,
длительность, причина отказа и сами данные; зелёная строка сообщает, что данные
добавлены в системный промпт, и на сколько токенов. Если по реплике вызов не
потребовался, там же написано «По запросу инструмент не потребовался: ключевых
слов нет»; если шаг не выполнялся из-за отказа по инвариантам — отдельное
примечание.

Тот же отчёт приходит в поле `mcp` ответа `POST /agents/{agent_id}/generate`
(схема `MCPCallReportOut`): `state`, `detected`, `connected`, `called`,
`accepted`, `tool`, `arguments`, `result`, `is_error`, `reason_code`, `error`,
`duration_ms`, `used_in_prompt`, `added_tokens`. Шаг выполняется после проверки
запроса инвариантами и до контроля лимита контекста, поэтому HTTP-запрос наружу
(который делает инструмент) уходит только у прошедшего проверку хода, а
добавленный блок входит в лимит.

## 8. Сценарии тестирования

Все команды — из папки `day17`; бэкенд для API-сценариев запущен на порту 8000.

### 8.1 Сквозной прогон дня (без ключа DeepSeek)

```bash
uv run python scripts/mcp_tool_demo.py
```

Ожидаемо:

- «=== 1. Каталог инструментов своего MCP-сервера ===» — транспорт stdio, сервер
  `day17-jsonplaceholder 1.0.0`, три инструмента, у каждого напечатаны
  `input_schema` и `output_schema`;
- «=== 2. Вызовы инструмента (tools/call) ===» — `get_user({"user_id": 1})`,
  `get_post({"post_id": 1})` и `list_user_posts({"user_id": 1, "limit": 3})`
  в состоянии `done` со структурированными данными и временем ответа;
- «=== 3. Отказные вызовы ===» — `no_such_tool({})` → `rejected · unknown_tool`,
  `get_user({})` → `rejected · bad_arguments`, `get_user({"user_id": 999})` →
  `failed · tool_error` с текстом про HTTP 404;
- «=== 4. Шаг MCP в работе агента ===» — на вопрос «Найди информацию о
  пользователе с ID 1»: `mcp: инструмент 'get_user', аргументы {"user_id": 1},
  состояние 'done', вызван: True, данные в промпте: True (+N токенов)`, ниже —
  первые строки блока «## Данные MCP-инструмента» из системного промпта; на
  вопрос «Сколько будет 2+2?» — «инструмент вызывался — False»;
- итог: `инструментов: 3; успешных вызовов: 3; отказов: 3`.

Полезные ключи:

```bash
uv run python scripts/mcp_tool_demo.py --live        # настоящий DeepSeek (нужен ключ)
uv run python scripts/mcp_tool_demo.py --json        # итог как JSON
uv run python scripts/mcp_tool_demo.py --timeout 5   # короче ждать сервер
uv run python scripts/mcp_tool_demo.py --api-base http://127.0.0.1:8080   # свой стенд вместо jsonplaceholder
```

Без `--live` клиент DeepSeek подменяется офлайн-заглушкой, которая отвечает по
блоку данных из системного промпта: ответ агента сам доказывает, что результат
инструмента дошёл до запроса. Код выхода `1` — только если не удалось
подключиться к серверу.

### 8.2 Отчёт дня

```bash
uv run python scripts/mcp_tool_demo.py --report docs/reports/mcp_tool_demo.md
uv run python scripts/mcp_tool_demo.py --report docs/reports/mcp_tool_demo.md --tests
```

Ожидаемо: файл создан, в конце вывода — строка `отчёт: docs\reports\mcp_tool_demo.md`.
Отчёт собирается из данных того же прогона (семь разделов: что проверялось, какой
API использовался, сервер и инструменты, вызовы, как агент использовал результат,
автотесты, что осталось за рамками дня); `--tests` добавляет в раздел про
автотесты сводку `uv run pytest -q`.

### 8.3 Вызов без соединения — 409

```bash
curl -i -X POST http://127.0.0.1:8000/mcp/call \
     -H "Content-Type: application/json" \
     -d '{"tool": "get_user", "arguments": {"user_id": 1}}'
```

Ожидаемо: `409` и в `detail` — «Вызов инструмента невозможен: соединение с
MCP-сервером не установлено. Подключитесь через POST /mcp/connect.». Тот же код
`409` даёт `GET /mcp/tools` без соединения.

### 8.4 Неизвестный инструмент — 400

```bash
curl -i -X POST http://127.0.0.1:8000/mcp/call \
     -H "Content-Type: application/json" \
     -d '{"tool": "no_such_tool", "arguments": {}}'
```

Ожидаемо: `400` и `detail` вида «Инструмент «no_such_tool» не найден в каталоге
сервера. Доступны: get_user, get_post, list_user_posts».

### 8.5 Неполные и неподходящие аргументы — 400

```bash
curl -i -X POST http://127.0.0.1:8000/mcp/call \
     -H "Content-Type: application/json" \
     -d '{"tool": "get_user", "arguments": {}}'

curl -i -X POST http://127.0.0.1:8000/mcp/call \
     -H "Content-Type: application/json" \
     -d '{"tool": "get_user", "arguments": {"user_id": {}}}'
```

Ожидаемо: первый — `400` «Не указан обязательный аргумент «user_id» инструмента
«get_user». Укажите число в запросе (например, «пользователь 3») или передайте
аргументы через POST /mcp/call.»; второй — `400` «Аргумент «user_id» инструмента
«get_user» должен быть integer, получено object». Лишний аргумент
(`{"user_id": 1, "limit": 3}`) тоже даёт `400` со списком допустимых имён.

### 8.6 Несуществующий id — 200 и `is_error`

```bash
curl -i -X POST http://127.0.0.1:8000/mcp/call \
     -H "Content-Type: application/json" \
     -d '{"tool": "get_user", "arguments": {"user_id": 999}}'
```

Ожидаемо: `200`, `state: "failed"`, `reason_code: "tool_error"`, `is_error: true`,
а в `result.text` — «…не найден (HTTP 404): у jsonplaceholder 10 пользователей,
id от 1 до 10». Так видно разницу между «не смогли вызвать» и «инструмент не
нашёл данные»: первое — код отказа, второе — ответ инструмента.

### 8.7 Реплика без номера — отказ правил, генерация успешна

В разделе «🔌 MCP» (или через `POST /agents/{agent_id}/generate`) отправьте
агенту «Расскажи про пользователя».

Ожидаемо: инструмент распознан (`detected: true`), но правила допуска его не
пустили — `accepted: false`, `state: "rejected"`, `reason_code: "bad_arguments"`,
в `error` — текст про `user_id`; при этом `status: "ok"`: отказ правил не роняет
ход, просто ответ строится без данных инструмента (`used_in_prompt: false`).

### 8.8 Сервер отключён — шаг MCP не выполняется

Нажмите «⏏ Отключиться» в разделе «🔌 MCP» и снова спросите агента про
пользователя с ID 1.

Ожидаемо: в отчёте `mcp` — `connected: false`, `detected: false`, `state: "idle"`,
`used_in_prompt: false`; ответ приходит без внешних данных, генерация
завершается успешно. То же и после «Отключиться» в API:

```bash
curl -X POST http://127.0.0.1:8000/mcp/disconnect -d '{}'
```

### 8.9 Агент сам вызывает инструмент (нужен ключ)

1. Подключитесь к своему серверу в разделе «🔌 MCP».
2. В блоке «🤖 Спросить агента» введите «Найди информацию о пользователе с ID 1».
3. Ожидаемо: в ответе — блок «🔧 MCP-инструмент» с `get_user`, аргументами
   `{"user_id": 1}`, состоянием «успешно» и данными пользователя; зелёная строка
   про добавленные в промпт токены; сам ответ упоминает имя и город из данных
   инструмента.
4. Вопрос «Сколько будет 2+2?» — блок сообщает, что по запросу инструмент не
   потребовался.
