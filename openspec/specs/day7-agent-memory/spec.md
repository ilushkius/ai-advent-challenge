# Day7 Agent Memory Specification

## Purpose

День 7 челленджа: веб-приложение `day7/` на основе архитектуры дня 6 (FastAPI +
Streamlit + DeepSeek), в котором каждый агент обладает **контекстной памятью**:
полный диалог (`user`/`assistant`) хранится в SQLite и переживает перезапуски
бэкенда, а при каждом запросе в DeepSeek отправляется вся история сообщений.

## Requirements

### Requirement: Персистентное хранение агентов и сообщений в SQLite

Приложение SHALL хранить состояние в SQLite через SQLAlchemy: таблица `agents`
(конфигурация: идентификатор, имя, модель, температура, системный промпт, лимит
токенов, дата создания) и таблица `messages` со связью один-ко-многим к агентам.
Сообщение SHALL иметь поля `id` (Integer, первичный ключ), `agent_id` (String,
внешний ключ к агенту, индексированный), `role` (String), `content` (Text),
`timestamp` (DateTime). База SHALL создаваться автоматически при старте бэкенда.

#### Scenario: Таблицы создаются при старте

- GIVEN запускаемый бэкенд дня 7 без существующего файла базы данных
- WHEN приложение стартует
- THEN рядом с бэкендом появляется SQLite-файл с таблицами `agents` и `messages`,
  и сообщение ссылается на агента внешним ключом

#### Scenario: Удаление агента удаляет его сообщения

- GIVEN агент с сохранённым диалогом из нескольких сообщений
- WHEN агент удаляется через API
- THEN из базы удаляется и запись агента, и все его сообщения (каскад по
  внешнему ключу)

### Requirement: Загрузка истории агента

Агент SHALL загружать свою историю из базы данных: при создании нового агента
история пустая, а при старте приложения ранее созданные агенты SHALL
восстанавливаться из таблицы `agents` вместе с полным диалогом из `messages` в
порядке возрастания времени.

#### Scenario: Новый агент начинает с пустой истории

- GIVEN работающий бэкенд
- WHEN клиент создаёт нового агента
- THEN агент появляется в списке с числом сообщений 0, а его диалог пуст

#### Scenario: Агент восстанавливается после рестарта бэкенда

- GIVEN агент с записанным диалогом и остановленный (повторно запущенный)
  бэкенд
- WHEN клиент запрашивает список агентов и историю после рестарта
- THEN агент присутствует в списке с прежней конфигурацией, а его история
  содержит все сообщения из базы в исходном порядке

### Requirement: Генерация с полным контекстом диалога

При запросе к агенту приложение SHALL добавить сообщение пользователя в историю,
отправить в DeepSeek **всю** историю диалога (если задан системный промпт — он
SHALL идти первым сообщением с ролью `system`), получить ответ модели, добавить
его в историю как сообщение ассистента и сохранить обновлённую историю в базу.
Вызов SHALL использовать конфигурацию агента (`model`, `temperature`,
`max_tokens`) и OpenAI-совместимый endpoint `https://api.deepseek.com`.

#### Scenario: Ответ модели учитывает предыдущий диалог

- GIVEN агент, у которого в истории уже есть сообщения пользователя и
  ассистента
- WHEN клиент отправляет очередной запрос этому агенту
- THEN в DeepSeek передаются все сообщения истории вместе с новым запросом
  (а не только новый запрос), и ответ ассистента сохраняется в историю

#### Scenario: Обновлённая история возвращается в ответе

- GIVEN агент с двумя сообщениями истории
- WHEN клиент отправляет успешный запрос на генерацию
- THEN ответ содержит текст ответа, метрики (время, токены, `finish_reason`) и
  обновлённую историю — теперь из четырёх сообщений в хронологическом порядке

#### Scenario: Сбой API не портит историю

- GIVEN агент с сохранённым диалогом и недоступный DeepSeek (или отсутствующий
  ключ)
- WHEN клиент отправляет запрос на генерацию
- THEN бэкенд возвращает структурированную ошибку без traceback, а история
  агента остаётся прежней — без «повисшего» сообщения пользователя без ответа

### Requirement: Очистка истории агента

API SHALL очищать историю агента по запросу: все сообщения агента удаляются из
базы и из памяти, агент остаётся в списке, и дальнейший диалог начинается с
пустой истории. Очистка истории не SHALL изменять конфигурацию агента.

#### Scenario: Очистка и продолжение диалога с нуля

- GIVEN агент с диалогом из нескольких сообщений
- WHEN клиент очищает историю агента и затем отправляет новый запрос
- THEN история агента пуста, число сообщений равно 0, конфигурация не изменилась,
  а после нового запроса в истории ровно два сообщения (запрос и ответ)

### Requirement: API истории диалога

`GET /agents/{agent_id}/history` SHALL возвращать сообщения диалога агента в
хронологическом порядке (с ролями, текстом и временными метками). Ответы на
создание и запрос информации об агенте SHALL содержать текущее число сообщений
вместо числа записей-попыток. Списки агентов в API SHALL позволять интерфейсу
показывать число сообщений у каждого агента без отдельных запросов к истории.

#### Scenario: История читается как диалог

- GIVEN агент с тремя сообщениями: user, assistant, user
- WHEN клиент запрашивает историю
- THEN возвращаются ровно три сообщения в порядке их создания с ролями, текстом
  и временными метками


### Requirement: Чат-интерфейс Streamlit

Streamlit-приложение SHALL быть чатом: в основной области отображаются все
сообщения выбранного агента (роль и текст каждого), внизу — поле ввода и кнопка
«Отправить», а также кнопка очистки истории; в боковой панели — список агентов
для выбора с количеством сообщений у каждого и возможность создать/удалить
агента. После отправки сообщения и после очистки интерфейс SHALL показывать
актуальную историю из ответа бэкенда. При недоступности бэкенда приложение SHALL
показывать понятное предупреждение и оставаться работоспособным.

#### Scenario: Диалог виден и продолжается в интерфейсе

- GIVEN выбранный агент с сохранённой историей
- WHEN пользователь открывает приложение и отправляет новое сообщение
- THEN в основной области отображаются все сообщения диалога по порядку (роль и
  текст), включая новый запрос и ответ ассистента

#### Scenario: Очистка истории из интерфейса

- GIVEN выбранный агент с непустым диалогом
- WHEN пользователь нажимает кнопку очистки истории
- THEN основная область очищается, счётчик сообщений у агента становится 0, а
  новый запрос начинает диалог с пустой историей

#### Scenario: Список агентов показывает число сообщений

- GIVEN агенты с разным числом сообщений
- WHEN пользователь смотрит боковую панель
- THEN у каждого агента в списке указано число его сообщений

### Requirement: Изоляция приложения от дней 1–6

Приложение дня 7 SHALL быть автономным: все его файлы лежат в `day7/`, оно не
импортирует общий пакет `shared/` и не изменяет файлы `day1/`…`day6/` (день 6
используется только как основа для копии).

#### Scenario: Код дней 1–6 не изменён

- GIVEN реализованное приложение дня 7
- WHEN выполняется проверка `git status` по файлам `day1/`, `day2/`, `day3/`,
  `day4/`, `day5/`, `day6/` и `shared/`
- THEN отсутствуют изменения отслеживаемых файлов этих дней, а новые файлы
  появляются только в `day7/` и в артефактах этого change
