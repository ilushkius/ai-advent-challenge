# Day6 Agent Manager Specification

## Purpose

День 6 челленджа: веб-приложение `day6/`, в котором единый менеджер-синглтон
управляет множеством независимых агентов DeepSeek — у каждого своя модель,
температура, системный промпт, лимит токенов и история запросов — а управление
доступно через FastAPI-бэкенд (порт 8000) и Streamlit-интерфейс (порт 8501).

## Requirements

### Requirement: Конфигурация и создание агента

API SHALL позволять создать агента, передав конфигурацию: имя, модель
(`deepseek-chat` по умолчанию, допустима и `deepseek-reasoner`), температуру в
диапазоне 0.0–2.0, системный промпт и лимит токенов (1–8192). Успешное создание
SHALL возвращать уникальный идентификатор агента и его конфигурацию.

#### Scenario: Создание агента возвращает id и конфигурацию

- GIVEN рабочий бэкенд и корректная конфигурация агента
- WHEN клиент отправляет запрос на создание агента с именем, моделью,
  температурой, системным промптом и лимитом токенов
- THEN в ответе присутствуют уникальный идентификатор агента и все переданные
  параметры конфигурации

#### Scenario: Некорректная конфигурация отклоняется

- GIVEN рабочий бэкенд
- WHEN клиент отправляет конфигурацию с температурой вне диапазона 0.0–2.0 или
  пустым именем
- THEN бэкенд возвращает ошибку валидации, агент не создаётся

### Requirement: Список и информация об агентах

API SHALL возвращать список всех созданных агентов (идентификатор, имя,
модель) и полную информацию об отдельном агенте по его идентификатору
(конфигурация, дата создания, число записей истории). Запрос к несуществующему
агенту SHALL возвращать ошибку 404 с понятным сообщением.

#### Scenario: Список содержит всех созданных агентов

- GIVEN три созданных агента
- WHEN клиент запрашивает список агентов
- THEN ответ содержит ровно три записи с идентификаторами, именами и моделями

#### Scenario: Запрос информации о несуществующем агенте

- GIVEN рабочий бэкенд и идентификатор, которого нет в менеджере
- WHEN клиент запрашивает информацию об этом агенте
- THEN бэкенд возвращает ошибку 404 с понятным сообщением, сервер продолжает
  работу

### Requirement: Удаление агента

API SHALL удалять агента по идентификатору вместе с его историей запросов.
После удаления идентификатор SHALL быть недоступен для генерации и для запроса
истории.

#### Scenario: Агент исчезает после удаления

- GIVEN созданный агент с записанной историей
- WHEN клиент удаляет агента и затем запрашивает список агентов
- THEN удалённого агента нет в списке, а запросы к его идентификатору
  завершаются ошибкой 404

### Requirement: Генерация ответа DeepSeek

Запрос к агенту SHALL отправлять промпт в DeepSeek через OpenAI-совместимый
endpoint Chat Completions `https://api.deepseek.com`, используя конфигурацию
агента, и возвращать: текст ответа, затраченное время, токены
(входные/выходные/всего) и причину завершения (`finish_reason`). Модель
`deepseek-reasoner` может не учитывать температуру — такое поведение допускается
API провайдера и не является ошибкой.

#### Scenario: Успешная генерация с метаданными

- GIVEN агент, созданный с валидным ключом и доступной моделью
- WHEN клиент отправляет промпт на генерацию
- THEN возвращаются текст ответа, затраченное время, состав токенов и причина
  завершения, а запись о попытке добавляется в историю агента

#### Scenario: Ключ API не задан — структурированная ошибка

- GIVEN запущенный бэкенд, у которого ключ не задан ни в переменной окружения,
  ни в файле `.env`
- WHEN клиент отправляет промпт на генерацию
- THEN бэкенд возвращает структурированную ошибку с понятным текстом о
  необходимости ключа, без traceback; агент остаётся в менеджере, сервер
  продолжает работу

### Requirement: История запросов агента

API SHALL хранить историю попыток каждого агента — успешных и завершившихся
ошибкой — и возвращать её по запросу, отсортированную от новых к старым.
Каждая запись SHALL содержать промпт, результат или сообщение об ошибке,
время выполнения, токены и метку времени.

#### Scenario: История пополняется и читается

- GIVEN агент, которому ранее отправлено два запроса (один успешный, один с
  ошибкой)
- WHEN клиент запрашивает историю этого агента
- THEN ответ содержит две записи, упорядоченные от новых к старым, и у каждой
  записи есть промпт, результат или сообщение об ошибке и метаданные

### Requirement: Единый менеджер и массовое создание агентов

Все агенты SHALL храниться в одном экземпляре менеджера (синглтоне) внутри
бэкенда. Менеджер SHALL позволять создавать произвольное число агентов с
разными конфигурациями — вплоть до 100 и более; конфигурация и история каждого
агента SHALL быть независимыми.

#### Scenario: Создано 100 независимых агентов

- GIVEN работающий бэкенд
- WHEN клиент последовательно создаёт 100 агентов с разными конфигурациями
- THEN все 100 агентов присутствуют в списке, а генерация каждого использует
  только его собственную конфигурацию и пополняет только его историю

### Requirement: Streamlit-интерфейс управления агентами

Streamlit-приложение SHALL предоставлять: в боковой панели форму создания
агента (имя, модель, температура, системный промпт, лимит токенов), выбор
количества и кнопку массового создания агентов с разными параметрами, список
агентов с выбором активного и возможностью его удаления; в основной области —
поле запроса к активному агенту, ответ с метриками (время, токены) и историю
агента. При недоступности бэкенда приложение SHALL показать понятное
предупреждение и оставаться работоспособным.

#### Scenario: Создание агента из интерфейса

- GIVEN запущенные бэкенд и Streamlit-приложение
- WHEN пользователь заполняет форму в боковой панели и нажимает кнопку создания
- THEN новый агент появляется в списке и становится доступен для выбора,
  генерации и удаления

#### Scenario: Ответ с метриками и история в основной области

- GIVEN выбранный (активный) агент в интерфейсе
- WHEN пользователь вводит запрос и отправляет его
- THEN в основной области появляются текст ответа, время и токены, а запись
  пополняет историю агента

#### Scenario: Массовое создание агентов из интерфейса

- GIVEN запущенные бэкенд и Streamlit-приложение
- WHEN пользователь нажимает кнопку массового создания на выбранное число
  агентов (например, 10)
- THEN в списке появляется выбранное число новых агентов с разными параметрами
  конфигурации

#### Scenario: Бэкенд недоступен — интерфейс жив

- GIVEN запущенное Streamlit-приложение и остановленный бэкенд
- WHEN пользователь открывает приложение
- THEN страница отображается с понятным предупреждением о недоступности
  бэкенда, без traceback и без «падения» приложения

### Requirement: Изоляция приложения от дней 1–5

Приложение дня 6 SHALL быть автономным: все его файлы лежат в `day6/`, оно не
импортирует общий пакет `shared/` и не изменяет файлы `day1/`…`day5/`.

#### Scenario: Код дней 1–5 не изменён

- GIVEN реализованное приложение дня 6
- WHEN выполняется проверка `git status` по файлам `day1/`, `day2/`, `day3/`,
  `day4/`, `day5/` и `shared/`
- THEN отсутствуют изменения отслеживаемых файлов этих дней, а новые файлы
  появляются только в `day6/` и в артефактах этого change
