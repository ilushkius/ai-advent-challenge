# Architecture Specification

## Purpose

Архитектурный контракт проекта: моно-репозиторий из папок дней и общего пакета
`shared/`, ключевые паттерны приложений (params-dict, session_state, безопасный
вывод, двухэтапная оркестрация). Контракт подтверждён кодом day1..day3.

## Requirements

### Requirement: Моно-репозиторий с общим пакетом shared
Приложения дней SHALL лежать в папках `dayN/`; переиспользуемая логика работы с
DeepSeek SHALL быть вынесена в корневой пакет `shared/deepseek_utils.py`
(константа endpoint, чтение ключа из `.env`, разбор stop-строк, конвертация
`usage` в dict).

#### Scenario: Импорт общих утилит из дня
- GIVEN приложение day2 или day3
- WHEN приложение запускается из своей папки
- THEN корень репозитория добавляется в sys.path по `__file__` и утилиты из
  `shared/deepseek_utils.py` импортируются без копирования кода в день

### Requirement: Автономный консольный день
День 1 SHALL оставаться полностью автономным консольным скриптом без импорта
`shared/` и без веб-интерфейса.

#### Scenario: Чат без общего пакета
- GIVEN day1/deepseek_chat.py и свежее окружение с установленным `openai`
- WHEN скрипт запускается командой `python deepseek_chat.py`
- THEN работает потоковый консольный чат, не требуя других файлов репозитория

### Requirement: Params-dict как единый источник правды
Приложение дня 2/3 SHALL собирать полный словарь параметров запроса один раз и
использовать его и для вызова API, и для технического лога, чтобы лог
гарантированно совпадал с реальным запросом.

#### Scenario: Лог не расходится с вызовом
- GIVEN выполненный запрос
- WHEN пользователь открывает технический лог
- THEN значения в логе идентичны параметрам, отправленным в `chat.completions`

### Requirement: Состояние результата в session_state
Результат последнего запроса SHALL храниться в `st.session_state` и не теряться
при rerun Streamlit; при ошибке результат SHALL очищаться и показываться понятное
`st.error`-сообщение без traceback.

#### Scenario: Результат переживает rerun
- GIVEN выполненный запрос в приложении дня 2 или 3
- WHEN происходит любой rerun страницы (например, смена виджета)
- THEN вкладка «Результат» продолжает показывать ответ и метаданные

#### Scenario: Ошибка API показывается понятно
- GIVEN приложение с неверным/отсутствующим ключом или без сети
- WHEN пользователь запускает запрос
- THEN вместо traceback отображается st.error с объяснением причины

### Requirement: Конфигурация промптов словарями-константами
Поведение UI и промпты дня SHALL задаваться словарями-константами в начале
модуля; выбор стратегии в UI SHALL быть ключом такого словаря, чтобы добавление
новой стратегии было правкой словаря.

#### Scenario: Новая стратегия рассуждения
- GIVEN приложение дня 3
- WHEN в словари `REASONING_*` добавляется новая стратегия с ключом
- THEN стратегия появляется в `selectbox` и работает без изменения логики вызова

### Requirement: Двухэтапная оркестрация мета-промпта
Мета-промпт (Prompt-v-Prompt) SHALL выполняться в два этапа: скрытый Шаг А
(модель пишет «идеальный» промпт) и финальный Шаг Б (решение по сгенерированному
промпту); лог обоих этапов SHALL быть доступен пользователю.

#### Scenario: В логе видны оба этапа
- GIVEN приложение дня 3 и выбранный способ «Мета-промпт»
- WHEN пользователь запускает запрос и открывает технический лог
- THEN лог содержит инструкцию Шага А, сгенерированный промпт и параметры
  финального вызова Шага Б

### Requirement: Безопасный вывод текста модели
Текст модели перед выводом в markdown-карточку SHALL экранироваться
`html.escape`, чтобы ответ не ломал разметку и не вставлял HTML.

#### Scenario: Ответ с HTML-тегами не исполняется
- GIVEN приложение дня 2/3 в текстовом режиме
- WHEN модель возвращает текст, содержащий `<script>` или HTML-разметку
- THEN текст отображается как безопасный экранированный контент карточки

### Requirement: Устойчивость JSON-режима к невалидному ответу
В строгом JSON-режиме ответ SHALL парситься и показываться как структура через
`st.json`; если парсинг не удался, SHALL показываться предупреждение и «сырой»
текст ответа.

#### Scenario: Модель вернула не-JSON
- GIVEN приложение дня 2/3 в режиме «Строгий JSON»
- WHEN ответ модели не является валидным JSON
- THEN приложение показывает предупреждение «не удалось распарсить» и сырой текст
