# Day5 Model Comparison Specification

## Purpose

День 5 челленджа: автономное Streamlit-приложение `day5/app.py`, которое
выполняет один и тот же запрос через три модели Hugging Face разного размера,
измеряет время, токены и стоимость, показывает ответы и сравнительную таблицу
с оценками качества, а также умеет сохранять отчёт эксперимента в
`day5/results.md`.

## Requirements

### Requirement: Фиксированный набор из трёх моделей разного размера

Приложение SHALL сравнивать три модели в порядке «слабая → средняя →
сильная»: слабая `google/gemma-2-2b-it` (2B), средняя
`meta-llama/Llama-3.1-8B-Instruct` (8B), сильная `Qwen/Qwen2.5-72B-Instruct`
(72B). Все запросы SHALL отправляться в OpenAI-совместимый эндпоинт Hugging
Face Inference API с одним и тем же содержимым пользовательского сообщения.

#### Scenario: Один запрос уходит ко всем трём моделям

- GIVEN приложение запущено и введён текст запроса
- WHEN пользователь нажимает кнопку «Сравнить модели»
- THEN запрос последовательно отправляется каждой из трёх моделей набора в
  порядке «слабая → средняя → сильная», и для каждой модели показывается её
  ответ

### Requirement: Промпт по умолчанию

При первом открытии приложения поле ввода запроса SHALL быть предзаполнено
текстом: «Объясни, что такое RAG-система простыми словами, с примерами.
Ответ должен быть не длиннее 5 предложений.». Пользователь SHALL иметь
возможность заменить текст запроса.

#### Scenario: Поле ввода предзаполнено

- GIVEN приложение открыто впервые
- WHEN пользователь просматривает поле ввода запроса
- THEN в поле находится текст-задание про RAG-систему с ограничением «не
  длиннее 5 предложений»

### Requirement: Метрики ответа для каждой модели

Для каждой успешно ответившей модели приложение SHALL отображать: текст
ответа; время ответа (измеренное на стороне приложения); количество токенов —
входные, выходные и всего (если провайдер вернул `usage`); стоимость — цену,
если провайдер её предоставил, иначе текст «бесплатно». Время и токены SHALL
измеряться независимо для каждой модели.

#### Scenario: Карточка модели с ответом и метриками

- GIVEN три успешно выполненных запроса
- WHEN пользователь просматривает результаты
- THEN для каждой модели отображаются ответ, время ответа, токены
  (входные/выходные/всего) и стоимость

#### Scenario: Провайдер не вернул состав токенов

- GIVEN успешный ответ модели без данных `usage`
- WHEN приложение формирует карточку метрик
- THEN вместо количества токенов отображается пометка «недоступно», а время
  ответа и стоимость показываются как обычно

#### Scenario: Стоимость не предоставлена

- GIVEN ответ модели, для которого провайдер не вернул цену
- WHEN приложение отображает стоимость
- THEN показывается текст «бесплатно» с примечанием, что биллинг тарифа
  Inference API отсутствует

### Requirement: Изоляция ошибок отдельных моделей

Если запрос к одной из моделей завершился ошибкой (модель недоступна, ключ
без доступа, лимит запросов и т.п.), приложение SHALL показать понятное
сообщение об ошибке для этой модели и продолжить выполнение с остальными.
Показ метрик и сравнительной таблицы SHALL не прерываться из-за ошибки одной
модели.

#### Scenario: Модель недоступна — остальные отвечают

- GIVEN при запуске сравнения одна из трёх моделей возвращает ошибку
- WHEN пользователь нажимает «Сравнить модели»
- THEN запросы к двум другим моделям выполняются, для ошибочной модели
  показывается понятное сообщение об ошибке без traceback, а сравнительная
  таблица строится по успешно ответившим моделям

#### Scenario: Отсутствует ключ HF_TOKEN

- GIVEN приложение запущено, а ключ `HF_TOKEN` не задан ни в переменной
  окружения, ни в `day5/.env`
- WHEN пользователь нажимает «Сравнить модели»
- THEN запросы не выполняются и показывается понятное сообщение о том, что
  нужно задать ключ, без traceback и без «падения» приложения

### Requirement: Прогресс выполнения сравнения

Во время последовательного опроса моделей приложение SHALL отображать ход
выполнения (спиннер или прогресс-бар), отражающий состояние каждой модели из
набора.

#### Scenario: Виден прогресс по шагам

- GIVEN запущенное сравнение трёх моделей
- WHEN запросы выполняются последовательно
- THEN пользователь видит индикатор прогресса, который обновляется по мере
  завершения запроса к каждой модели

### Requirement: Сравнительная таблица с оценками качества

После выполнения сравнения приложение SHALL отображать сравнительную
таблицу, в которой для каждой модели (успешной или с ошибкой) есть колонки:
модель (с ролью «слабая/средняя/сильная»), время, токены (вход/выход/всего),
стоимость, оценка качества по шкале 0–10 с текстовым обоснованием и статус.
Оценка качества SHALL вычисляться по детерминированным правилам на основе
текста ответа и метаданных (соблюдение ограничения числа предложений, наличие
ключевых понятий темы, полнота завершения `finish_reason`).

#### Scenario: Таблица со всеми колонками

- GIVEN выполненное сравнение
- WHEN пользователь просматривает таблицу
- THEN для каждой модели отображаются роль и имя модели, время, токены,
  стоимость, оценка качества 0–10 с обоснованием и статус
  («успех»/«ошибка»)

#### Scenario: Оценка качества сопровождается обоснованием

- GIVEN ответ модели, оценённый приложением
- WHEN пользователь открывает пояснение к оценке
- THEN текст обоснования называет конкретные причины набранных баллов
  (например, число предложений относительно ограничения, найденные ключевые
  понятия, признак обрыва ответа)

### Requirement: Сохранение отчёта в day5/results.md

Приложение SHALL предоставлять кнопку сохранения результатов последнего
сравнения в файл `day5/results.md` (рядом с `app.py`). Файл отчёта SHALL
содержать: дату и полный текст запроса; для каждой модели — её имя и роль,
дословный ответ, время, токены, стоимость и оценку качества с обоснованием;
сводную сравнительную таблицу; выводы с практическими рекомендациями — для
каких задач лучше подходит каждая модель (слабая — для прототипов, средняя —
для продакшена, сильная — для сложных рассуждений).

#### Scenario: Кнопка сохраняет отчёт

- GIVEN выполненное сравнение с успешными ответами хотя бы одной модели
- WHEN пользователь нажимает кнопку сохранения отчёта
- THEN создаётся/перезаписывается файл `day5/results.md`, и пользователь видит
  подтверждение об успешной записи

#### Scenario: Отчёт содержит все разделы

- GIVEN сохранённый файл `day5/results.md`
- WHEN читатель просматривает документ
- THEN присутствуют текст запроса и дата, ответы всех моделей с их метриками и
  оценками, сводная сравнительная таблица и выводы-рекомендации по выбору
  модели (прототипы/продакшен/сложные рассуждения)

### Requirement: Изоляция приложения от дней 1–4

Приложение дня 5 SHALL быть полностью автономным: все его файлы лежат в
`day5/`, оно не импортирует общий пакет `shared/` и не изменяет файлы
`day1/`…`day4/`.

#### Scenario: Код дней 1–4 не изменён

- GIVEN реализованное приложение дня 5
- WHEN выполняется `git status --short` по файлам `day1/`, `day2/`, `day3/`,
  `day4/` и `shared/`
- THEN отсутствуют какие-либо изменения отслеживаемых файлов этих дней, а
  новые файлы появляются только в `day5/`
