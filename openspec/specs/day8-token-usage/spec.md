# Day8 Token Usage Specification

## Purpose

День 8 челленджа: веб-приложение `day8/` на основе дня 7 (FastAPI + Streamlit +
SQLAlchemy/SQLite), в котором каждый запрос агенту сопровождается **подсчётом
токенов**: токены текущего сообщения, всей истории контекста и ответа
оцениваются через tiktoken, фактические числа запроса/ответа берутся из
`usage` DeepSeek, метрики сохраняются в таблицу `token_usage` и показываются в
интерфейсе вместе с индикатором остатка до лимита контекста модели; при
переполнении контекста агент автоматически сокращает историю до влезающей в
лимит и предупреждает об этом.

## Requirements

### Requirement: Подсчёт токенов через tiktoken

Агент SHALL подсчитывать токены текста методом `count_tokens(text)` с
использованием tiktoken и кодировки `cl100k_base` (приближение к токенизатору
DeepSeek). Подсчёт SHALL работать для одиночного текста и для списка сообщений
(сумма токенов содержимого системного промпта и всех реплик). При каждом
запросе на генерацию приложение SHALL определять: токены входящего сообщения
пользователя, токены контекста истории (системный промпт + предыдущие
сообщения диалога), которые уйдут в запрос, и токены ответа модели. Если ответ
API содержит `usage`, числа запроса и ответа SHALL браться из него; при
отсутствии `usage` они SHALL оцениваться локальным подсчётом.

#### Scenario: Токены текста считаются кодировкой cl100k_base

- GIVEN агент с настроенным подсчётом токенов
- WHEN клиент вызывает метод подсчёта для произвольного русскоязычного и
  англоязычного текста
- THEN возвращается неотрицательное целое число токенов, совпадающее с числом
  элементов кодирования tiktoken (`cl100k_base`) этого текста

#### Scenario: Для запроса подсчитаны все составляющие

- GIVEN агент с историей из нескольких сообщений и непустым системным промптом
- WHEN клиент отправляет запрос на генерацию
- THEN бэкенд формирует значения токенов входящего сообщения, контекста
  истории (без учёта нового сообщения) и — после ответа — токенов ответа, причём
  при наличии `usage` в ответе API числа запроса и ответа берутся из него

### Requirement: Хранение метрик в таблице token_usage

Приложение SHALL хранить метрики токенов в SQLite в отдельной таблице
`token_usage` со связью один-ко-многим к агентам. Запись SHALL содержать
`agent_id` (внешний ключ к агенту), `timestamp`, `prompt_tokens`,
`completion_tokens`, `total_tokens`, `history_tokens`, `response_tokens` и
`cost` (стоимость запроса в долларах по тарифам модели). Одна успешная пара
реплик диалога SHALL порождать ровно одну запись `token_usage` с
`total_tokens`, равным сумме `prompt_tokens` и `completion_tokens`. Таблица
SHALL создаваться автоматически при старте бэкенда.

#### Scenario: Таблицы создаются при старте

- GIVEN запускаемый бэкенд дня 8 без существующего файла базы данных
- WHEN приложение стартует
- THEN в SQLite-файле появляются таблицы `agents`, `messages` и `token_usage`,
  и запись токенов ссылается на агента внешним ключом

#### Scenario: Каждый успешный ход диалога сохраняет запись токенов

- GIVEN агент с пустой историей
- WHEN клиент дважды успешно отправляет запрос на генерацию
- THEN в `token_usage` появляются две записи этого агента с метками времени,
  а у второй записи `total_tokens` равен сумме её `prompt_tokens` и
  `completion_tokens`

#### Scenario: Удаление агента удаляет его метрики токенов

- GIVEN агент с записями в `token_usage`
- WHEN агент удаляется через API
- THEN из базы удаляются и запись агента, и его сообщения, и его записи
  `token_usage` (каскад по внешнему ключу)

#### Scenario: Очистка истории сбрасывает счётчик токенов диалога

- GIVEN агент с записями в `token_usage` и непустым диалогом
- WHEN клиент очищает историю агента
- THEN диалог пуст, а записи `token_usage` этого агента удалены — новый диалог
  начинает счёт токенов с нуля, конфигурация агента не меняется

### Requirement: Метрики токенов и состояние контекста в ответе генерации

Ответ успешной генерации SHALL содержать помимо текста и прежних метрик
структурированные метрики токенов хода (`prompt_tokens`, `completion_tokens`,
`total_tokens`, `history_tokens`, `response_tokens`, `cost`) и состояние
контекста: лимит модели в токенах, оценочное число токенов запроса, остаток до
лимита, число обрезанных при переполнении сообщений и текст предупреждения при
его наличии. Значения SHALL согласовываться с записью, сохранённой в
`token_usage`.

#### Scenario: Ответ генерации содержит метрики токенов

- GIVEN агент с непустой историей
- WHEN клиент успешно отправляет запрос на генерацию
- THEN ответ содержит текст, метрики токенов (включая токены контекста
  истории, токены ответа и стоимость) и состояние контекста с неотрицательным
  остатком до лимита модели, согласованные с сохранённой записью `token_usage`

#### Scenario: При отсутствии usage в ответе API числа оцениваются локально

- GIVEN агент, чей API-ответ не содержит поля `usage` (имитация фейком)
- WHEN клиент успешно отправляет запрос на генерацию
- THEN в метриках ответа числа запроса и ответа вычислены локальным подсчётом
  токенов, а `total_tokens` равен их сумме

### Requirement: Контроль лимита контекста и автоматическая обрезка истории

Приложение SHALL знать лимит контекста модели агента в токенах
(`deepseek-chat` — 8 000, `deepseek-reasoner` — 32 000; значения заданы
константами и могут быть изменены). Перед вызовом DeepSeek приложение SHALL
оценивать токены запроса как сумму токенов контекста истории и токенов нового
сообщения. Если оценка превышает лимит, приложение SHALL перед вызовом удалить
самые старые целые пары реплик диалога (`user` + `assistant`) — из памяти и из
БД — до тех пор, пока контекст не влезет в лимит, отправить запрос с
сокращённой историей и вернуть предупреждение об обрезке с числом удалённых
сообщений. Если даже при пустой истории одно сообщение пользователя длиннее
лимита, приложение SHALL вернуть структурированную ошибку без вызова API.
Обрезка при отсутствии переполнения SHALL не выполняться.

#### Scenario: Переполнение контекста сокращает историю с предупреждением

- GIVEN агент с длинным диалогом, чья история вместе с новым сообщением
  превышает лимит модели
- WHEN клиент отправляет запрос на генерацию
- THEN агент удаляет самые старые целые пары сообщений до вписывания в лимит,
  генерирует ответ по сокращённой истории и возвращает предупреждение с числом
  удалённых сообщений, а в `token_usage` и диалоге агента отсутствуют удалённые
  сообщения

#### Scenario: История в пределах лимита не обрезается

- GIVEN агент с короткой историей, влезающей в лимит вместе с новым сообщением
- WHEN клиент отправляет запрос на генерацию
- THEN история не изменяется (сообщения не удаляются), предупреждение об
  обрезке отсутствует

#### Scenario: Сообщение длиннее лимита при пустой истории

- GIVEN агент с пустой историей и лимитом модели
- WHEN клиент отправляет сообщение, токенов которого больше лимита
- THEN бэкенд возвращает структурированную ошибку с понятным текстом о том,
  что сообщение длиннее контекста модели, не вызывая DeepSeek и не меняя
  историю

### Requirement: Эндпоинты статистики токенов

API SHALL предоставлять `GET /agents/{agent_id}/usage` со сводкой по токенам
агента: число запросов, суммарные `prompt_tokens`, `completion_tokens`,
`total_tokens`, общая стоимость и время последней записи. Эндпоинт
`GET /agents/{agent_id}/usage/graph` SHALL возвращать записи `token_usage`
агента в хронологическом порядке (метка времени и все числовые поля) для
таблицы и графика в интерфейсе. Оба эндпоинта SHALL отвечать ошибкой 404 для
несуществующего агента.

#### Scenario: Сводка токенов по агенту

- GIVEN агент с тремя записями в `token_usage`
- WHEN клиент запрашивает `GET /agents/{agent_id}/usage`
- THEN ответ содержит число запросов 3, суммы `prompt_tokens`,
  `completion_tokens` и `total_tokens` по всем записям, сумму стоимостей и метку
  времени последней записи

#### Scenario: Данные для графика в хронологическом порядке

- GIVEN агент с записями в `token_usage`
- WHEN клиент запрашивает `GET /agents/{agent_id}/usage/graph`
- THEN ответ содержит все записи токенов агента по возрастанию времени с
  метками времени и числовыми полями `token_usage`

#### Scenario: Статистика несуществующего агента

- GIVEN идентификатор агента, отсутствующий в менеджере
- WHEN клиент запрашивает статистику токенов или данные графика этого агента
- THEN бэкенд возвращает ошибку 404 с понятным сообщением, сервер продолжает
  работу

### Requirement: Панель токенов в интерфейсе

Streamlit-интерфейс выбранного агента SHALL показывать: общий счётчик токенов
за диалог (сумма `total_tokens` по записям `token_usage`), стоимость за диалог,
индикатор заполнения контекста с числом использованных и оставшихся до лимита
токенов, предупреждение при приближении к лимиту или после автоматической
обрезки, а также рост токенов по запросам — график (линия накопленной суммы
`total_tokens` по запросам) и таблицу записей с временными метками. Панель
SHALL обновляться после каждого запроса и после очистки истории.

#### Scenario: Счётчик и индикатор растут с каждым запросом

- GIVEN агент с записями токенов в базе
- WHEN пользователь выбирает агента и отправляет несколько запросов
- THEN панель токенов показывает выросший общий счётчик, заполненный индикатор
  контекста с уменьшившимся остатком до лимита и таблицу с новой записью

#### Scenario: Предупреждение об обрезке показывается в интерфейсе

- GIVEN агент, чей следующий запрос переполнит контекст
- WHEN пользователь отправляет такой запрос
- THEN интерфейс показывает предупреждение о сокращении истории с числом
  удалённых сообщений, а чат и таблица токенов отражают сокращённый диалог

#### Scenario: После очистки истории счётчик обнуляется

- GIVEN агент с накопленными записями токенов
- WHEN пользователь очищает историю агента
- THEN общий счётчик токенов и стоимость за диалог становятся нулевыми,
  таблица токенов пуста, а новый запрос начинает рост графика с нуля

### Requirement: Изоляция приложения от дней 1–7

Приложение дня 8 SHALL быть автономным: все его файлы лежат в `day8/`, оно не
импортирует общий пакет `shared/` и не изменяет файлы `day1/`…`day7/` (день 7
используется только как основа для копии).

#### Scenario: Код дней 1–7 не изменён

- GIVEN реализованное приложение дня 8
- WHEN выполняется проверка `git status` по файлам `day1/`, …, `day7/` и
  `shared/`
- THEN отсутствуют изменения отслеживаемых файлов этих дней, а новые файлы
  появляются только в `day8/` и в артефактах этого change
