# AGENTS.md — архитектурные цели проекта ai-challenge

Этот файл агент **omp.sh** читает на старте вместе с `.clauderules`. Здесь —
целевая архитектура новых приложений и правила её реализации. Общие конвенции
проекта, стек и команды проверки — в `.clauderules`, процедурные правила (FSM,
раскладка файлов, `shared/`, TDD, документация дня) — в скиллах проекта
(раздел «Скиллы проекта»).

## Архитектурные цели

1. **Явная стейт-машина на Python.** Логику новых приложений описываем как
   конечный автомат: состояния, события, переходы. Никакой разбросанной логики
   в `if/elif` по всему коду — переходы централизуются в одном месте.
2. **Состояния и события — через `enum.Enum`.** Состояния — члены `enum.Enum`
   (например, `IDLE`, `LOADING`, `DONE`, `ERROR`), а не «магические» строки.
   События — тоже `Enum`. Значения — строковые/читаемые, чтобы попадать в UI и
   в лог без дополнительного маппинга.
3. **Переходы — паттерном State.** Каждое состояние — отдельный класс с общим
   интерфейсом (например, `handle(event)`), возвращающий следующее состояние.
   Стейт-машина хранит текущее состояние и делегирует ему обработку события.
   Классы состояний не зависят от UI (Streamlit/FastAPI) — только от домена.
4. **Тесты — через `pytest`.** Переходы стейт-машины покрываются модульными
   тестами: пакет `pytest`, файлы `test_*.py` рядом с кодом дня или в `tests/`.
   Тест пишется **до** реализации (TDD): сначала падает, потом зеленеет.
5. **Обратная совместимость.** `day1`–`day8` остаются как есть; новые правила
   применяются к новым дням (начиная с `day9/`) и к тому коду, который осознанно
   рефакторится.

## Скиллы проекта

Процедурные правила вынесены в скиллы omp.sh (папка `.omp/skills/`). omp читает
их метаданные (name + description) и подгружает релевантный скилл лениво, когда
задача подходит под его триггеры; полный текст доступен по `skill://<name>` и
через `/skill:<name>`.

| Скилл | Когда применяется |
| --- | --- |
| `python-fsm-agent` | Работа с FSM: состояния, события, переходы, неизвестное событие. |
| `fastapi-streamlit-day-structure` | Создание нового дня (`day13/` и далее) или дробление крупного файла. |
| `shared-modules-usage` | Код, который может жить в `shared/` (клиент DeepSeek, база, токены, логи). |
| `tdd-pytest-workflow` | Написание тестов: `pytest`, TDD, таблицы переходов, негативные сценарии. |
| `day-docs-structure` | Завершение дня: `README.md`, `STRUCTURE.md`, `CHANGELOG.md`. |

**Детали — в самих скиллах, не дублировать здесь.** Этот файл задаёт цели и
границы проекта, скиллы — процедуры их реализации.

## Правила работы с `Enum` и паттерном State

Полные правила — в скилле **`python-fsm-agent`** (здесь не дублируются).
Кратко: состояния и события — только `Enum`, переходы — паттерн State, у каждого
события в состоянии ровно один результат, неизвестное событие — явная ошибка.

**Перед выполнением любого действия агент обязан проверить, соответствует ли оно
текущему этапу задачи и допустимым переходам. Попытка перейти в недопустимый
этап должна быть отклонена с объяснением.** Правила допуска живут одним модулем
(эталон — `day15/backend/domain/task_state_machine.py`: граф `ALLOWED_TRANSITIONS`
и guard-условия на флаги согласования этапов), а отказ — это данные: попытка
попадает в журнал (`task_transitions.accepted = false`) и состояние задачи не
меняет.

## Работа с внешними инструментами (MCP)

**Для получения списка инструментов от внешних сервисов использовать
MCP-клиент. Все MCP-соединения логировать и корректно закрывать после
использования.**

Правило в силе для новых дней (эталон — `day16/`):

- подключение к внешнему серверу — через клиент дня
  (`day16/backend/services/mcp_client.py`, `MCPClient`), а не «сырыми» вызовами
  SDK по месту: транспорт (stdio / SSE / Streamable HTTP) выбирается по цели,
  понятные тексты ошибок живут в одном модуле (`mcp_errors.py`);
- состояние подключения — стейт-машина (`day16/backend/domain/mcp_connection_fsm.py`),
  как требует скилл `python-fsm-agent`: состояния и события — `Enum`, переходы —
  паттерн State, недопустимый шаг — явная ошибка;
- соединение одно на процесс и держится реестром (`MCPRegistry`), а закрывается
  и при отключении, и при остановке приложения (`lifespan` → `close()`) — сервер
  stdio не остаётся висеть дочерним процессом;
- в работе агента инструменты не вызываются, пока это не оговорено отдельным
  заданием дня: `day16/` только читает каталог (`tools/list`).

**При реализации MCP-инструментов всегда указывать типизированные параметры и docstring,
чтобы input_schema генерировалась корректно. Инструменты должны выполнять реальные
действия (HTTP-запросы, работу с файлами, вызовы API) и возвращать структурированный
результат.**

Правило о вызове инструментов (эталон — `day17/`, свой MCP-сервер в
`day17/mcp_server/`):

- инструмент описывается типизированно: из аннотаций параметров SDK собирает
  `inputSchema`, из докстринга — описание для модели, из `TypedDict`-возврата —
  `outputSchema`, а `structuredContent` ответа равен самому словарю; поэтому
  возвращать нужно структуру, а не строку, склеенную руками;
- ошибка инструмента — это данные (`is_error`), а не исключение: текст причины
  («пользователя с id=999 нет») обязан доехать до модели понятной строкой;
- вызов идёт через правила допуска (`admission_reason`: соединение, каталог,
  обязательные/лишние аргументы, типы), а не «сырым» `tools/call` по месту;
- состояние вызова — стейт-машина (`day17/backend/domain/mcp_tool_call.py`), как
  требует скилл `python-fsm-agent`: `Enum`-состояния и события, паттерн State,
  недопустимый шаг — явная ошибка;
- результат, ушедший в промпт агента, добавляется системным блоком
  (`render_mcp_tool_block`) и входит в контроль лимита контекста; данные
  неудачного вызова в промпт не добавляются.

**При реализации периодических задач всегда использовать планировщик
(APScheduler), сохранять метаданные задач в БД и поддерживать восстановление
после перезапуска. Фоновые задачи не должны блокировать основной поток
приложения.**

Правило в силе для новых дней (эталон — `day18/`, планировщик в
`day18/backend/services/scheduler.py`):

- фон живёт в процессе приложения и поднимается на старте: `TaskScheduler` на
  `AsyncIOScheduler` запускается в `lifespan` (`day18/backend/api/lifespan.py`) и
  останавливается на выходе, а метаданные задач хранятся в таблице
  `scheduled_tasks` — после перезапуска задачи восстанавливаются
  (`sync_from_db`), а пропущенный запуск догоняется;
- **тик задачи — синхронная функция**: APScheduler 3.x выполняет не-корутины в
  пуле потоков, поэтому фон не блокирует цикл событий FastAPI; исключение внутри
  тика не валит планировщик — оно попадает в журнал запусков (`task_runs`) и в
  уведомление, а задача остаётся активной;
- фон не ходит через MCP-соединение пользователя: оно держит блокировку клиента,
  поэтому вызов инструмента из тика был бы дедлоком — тик выполняет действие
  инструмента напрямую (`day18/backend/services/scheduled_jobs.py`);
- единственный писатель в SQLite — процесс бэкенда, поэтому инструменты
  планировщика ставят задачу через API дня (`POST /scheduler/tasks`), а не пишут
  в БД сами (`day18/mcp_server/backend_api.py`).

## Структура файлов

Полные правила раскладки файлов и модулей — в скилле
**`fastapi-streamlit-day-structure`**. Ключевые лимиты: любой `.py` ≤ 400 строк,
`app.py` ≤ 100, `backend/api/main.py` ≤ 80; команда проверки лимита — в скилле.
Подключение общего кода дня — скилл `shared-modules-usage`.

Уточнение к `.clauderules` §3 («Один файл = одно приложение дня»): правило
описывает одностраничные демо (day2/day3/day5). В новых днях с бэкендом и UI
раскладка — по правилам скилла.

## Структура дня (обязательно для новых дней)

Раскладка дня 13 — образец: код разложен по слоям, файл лежит в папке **своего**
слоя, а не в «ближайшей».

```
dayN/
├── app.py            Streamlit, точка входа (≤ 100 строк): только вызовы секций
├── frontend/         интерфейс по секциям (или `app.py` в корне, если интерфейс одностраничный)
├── backend/
│   ├── __init__.py   пусто по смыслу: описание пакета (+ корень репозитория в sys.path для shared/)
│   ├── api/          FastAPI: роутеры по доменам + main.py (сборка app, ≤ 80 строк)
│   ├── core/         конфигурация (config) и зависимости роутов (dependencies)
│   ├── domain/       чистые правила и данные: без БД, LLM и HTTP
│   ├── services/     прикладная логика: оркестрация domain и storage
│   ├── storage/      доступ к БД: движок и сессии, хранилища, реэкспорт ORM
│   ├── agents/       агент, его память/профиль и менеджер (миксины — manager_*.py)
│   ├── models/       ORM-таблицы SQLAlchemy по доменам
│   ├── schemas/      Pydantic-схемы API по доменам
│   └── utils/        утилиты дня; пусто, если всё общее живёт в shared/
├── scripts/          прогоны демонстраций и сборка отчётов
├── tests/            unit/ (без БД), integration/ (временная БД и агент), e2e/ (TestClient)
└── docs/             architecture.md, usage.md, api.md, reports/ (отчёты прогонов)
```

Обязательный состав слоёв — девять папок в `backend/` (`api`, `core`, `models`,
`schemas`, `services`, `storage`, `domain`, `agents`, `utils`; папка может быть
пустой, если в дне нет таких сущностей, но `__init__.py` в ней есть). Состав
повторяет целевую архитектуру и не зависит от того, сколько модулей в дне
сегодня.

Правила:

- **Не допускать скопления файлов в корне `backend/`** — там только
  `__init__.py`; модуль без своей папки означает, что слой не определён.
- Каждый пакет слоя содержит `__init__.py` с реэкспортом публичных имён — это
  публичный контракт слоя.
- Имена модулей берутся по домену (`memory.py`, `profile_store.py`,
  `task_state.py`), а не по шаблону (`utils.py`, `helpers.py`, `stuff.py`).
- Отчёты прогонов — в `docs/reports/`, тесты — в подпапках `tests/`, потому что
  классификация по фикстурам читается с первого взгляда.

## Запрещено

- Складывать всю логику в один файл, если он превышает 400 строк — см. скилл
  `fastapi-streamlit-day-structure`.
- Создавать `utils.py` / `helpers.py` без чёткой доменной принадлежности — см.
  скилл `fastapi-streamlit-day-structure`.
- Копировать один и тот же код в `dayN/` и `dayN+1/`, если он не меняется между
  днями: неизменяемый между днями код живёт в `shared/` — см. скилл
  `shared-modules-usage`.
- Менять код предыдущих дней (`day1/` … `dayN-1/`) — они являются снимками.
  Правка снимка — только по прямому запросу пользователя.

## Обязательно

- Перед началом работы посмотреть структуру `dayN-1/` и переиспользовать её
  паттерны: имена модулей, слои, конвенции тестов. При конфликте «паттерн
  `dayN-1/`» и «правила структуры» приоритет у правил структуры — скилл
  `fastapi-streamlit-day-structure`.
- Вести `STRUCTURE.md` в папке каждого нового дня (содержание — скилл
  `day-docs-structure`): список модулей и назначение каждого, какие файлы
  импортируют `shared/`, известные превышения лимита строк. `README.md` и `docs/`
  он не заменяет.
- Новую сущность сразу определять в её слой (`frontend/`, `backend/api/`,
  `backend/core/`, `backend/domain/`, `backend/services/`, `backend/storage/`,
  `backend/agents/`, `backend/models/`, `backend/schemas/`, `scripts/`,
  `tests/{unit,integration,e2e}/`, `shared/`), а не в «ближайший» файл —
  скилл `fastapi-streamlit-day-structure` и раздел «Структура дня» выше.
- Задачи по новым приложениям запускать в Plan Mode: сначала предложить
  структуру файлов (модули и их обязанности), дождаться утверждения, потом
  реализовывать.
- После реализации прогнать проверки дня: `pytest` из папки дня (скилл
  `tdd-pytest-workflow`), `python -m py_compile` по изменённым файлам, лимит
  строк (скилл `fastapi-streamlit-day-structure`).
- **При добавлении новых функций или изменении архитектуры проверять, не нарушают ли они
  существующие инварианты. При необходимости обновлять список инвариантов.** Если инвариант
  нарушается намеренно, сначала обновить таблицу `invariants` (эндпоинты `/invariants...`
  или раздел «📏 Инварианты»), потом менять код.

### Зависимости: uv (day13 и далее)

**Правило.** Все проекты `dayN` используют `uv` для управления зависимостями.
Зависимости объявляются в `pyproject.toml`, точные версии фиксируются в
`uv.lock`. Для установки: `uv sync`. Для запуска: `uv run <команда>`.
`requirements.txt` не используется.

В корне дня лежат три файла, и все три коммитятся: `pyproject.toml` (прямые
зависимости + `requires-python`), `uv.lock` (точные версии всех прямых и
транзитивных пакетов), `.python-version` (интерпретатор для `uv sync`).
Окружение `.venv` создаёт `uv sync`, в Git оно не попадает. Активировать
окружение не нужно — `uv run` находит `.venv` проекта сам.

**Новый день (начиная с `day14`).** Сразу инициализировать проект через uv:

```powershell
cd dayN
uv init --no-package          # pyproject.toml + .python-version, без сборочного бэкенда
uv add <package>              # каждая зависимость — своим вызовом
uv add --dev pytest           # инструменты разработки — в dev-группу
```

Не создавать `requirements.txt` — использовать `pyproject.toml` и `uv.lock`.
Это правило обязательно для всех последующих дней челленджа. Созданный
`uv init` файл `main.py` удалять: точка входа дня — `app.py`.

**Миграция существующего дня на uv** (для `day1`–`day12` — только по прямому
запросу пользователя: это снимки). Порядок одинаков для любого дня:

1. из папки дня — `uv init --no-package --no-readme --vcs none` (создаёт
   `pyproject.toml` и `.python-version`; появившийся `main.py` удалить);
2. `uv add -r requirements.txt` — переносит зависимости; дополнительные файлы
   требований добавлять отдельными вызовами
   (`uv add --dev -r requirements-dev.txt`);
3. `uv sync` — создаёт `uv.lock` и `.venv`; сверить состав `pyproject.toml` с
   прежним `requirements.txt` (ничего не потерялось);
4. проверить работоспособность: `uv run pytest -q`,
   `uv run uvicorn <module>:app`, `uv run streamlit run app.py`;
5. удалить `requirements.txt`, обновить `README.md` дня (раздел «Установка и
   запуск»: `uv sync`, `uv run streamlit run app.py`,
   `uv run uvicorn <module>:app --reload`), `STRUCTURE.md` дня и `CHANGELOG.md`.

Флага `--requirements` у `uv init` **нет** (проверено на uv 0.12.15:
`error: unexpected argument '--requirements' found`) — перенос зависимостей
делает `uv add -r requirements.txt`.

### Скиллы библиотек: uvx library-skills

**Правило.** В проектах `dayN` для отслеживания версий библиотек используется
uvx library-skills. При добавлении новой библиотеки (uv add <package>) запускать
uvx library-skills для обновления скиллов. Скиллы хранятся в .agents/skills/ и
коммитятся в Git.

**Правило.** При обновлении библиотек через uv lock --upgrade или
uv add <package>@latest запускать uvx library-skills --check для проверки
целостности симлинков и uvx library-skills для их обновления, если требуется.

**Правило.** Все зависимости объявляются в pyproject.toml, точные версии
фиксируются в uv.lock. Запрещено редактировать uv.lock вручную. Для обновления
использовать uv lock --upgrade. Для проверки конфликтов использовать
uv lock --check. requirements.txt не используется.

Механика: библиотеки, которые везут AI-скиллы, кладут их внутрь пакета
(`<пакет>/.agents/skills/<имя>/SKILL.md`). `uvx library-skills` сканирует
зависимости дня, находит такие скиллы и создаёт в корне дня относительные
симлинки `.agents/skills/<имя>` → каталог внутри `.venv`; при обновлении
библиотеки содержимое симлинка меняется само. Скиллы не правят руками — их
пересобирает команда.

| Задача | Команда (из папки дня) |
|---|---|
| установить/обновить скиллы | `uvx library-skills --yes --all --tool-skill` |
| проверить целостность (дрейф → код 1) | `uvx library-skills --check --tool-skill` |
| посмотреть установленные | `uvx library-skills list --installed` |
| починить/убрать managed-симлинки | `uvx library-skills --yes` |

Ограничения: запускать **из папки дня** (корень проекта ищется по `cwd`); при
отсутствии символических ссылок (Windows без режима разработчика) — флаг
`--copy`, тогда авто-обновление не работает и команду нужно повторять после
апгрейда. Агент omp видит скиллы провайдером `agents`, который ищет
`<проект>/.agents/skills/<имя>/SKILL.md`, поднимаясь от `cwd` вверх, — сессию
дня запускать в папке дня. Для сессии, запущенной из корня репозитория, путь
прописан в `.omp/config.yml`:

```yaml
skills:
  customDirectories:
    - day13/.agents/skills
```

Новый день со своими симлинками требует добавить туда же ещё одну строку
(разбор каталогов у omp нерекурсивный: `<каталог>/<имя>/SKILL.md`).
