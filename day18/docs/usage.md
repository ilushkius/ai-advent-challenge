# День 18 — планировщик фоновых задач и MCP-инструменты с периодическим выполнением

Инструкция по приложению дня 18. День добавляет **планировщик фоновых задач**
(APScheduler) и **три MCP-инструмента с отложенным и периодическим выполнением**
поверх агента дня 17:

|Инструмент|Что делает|
|---|---|
|`schedule_reminder`|разовое напоминание через N секунд|
|`collect_data`|периодический сбор JSON по адресу каждые N секунд|
|`generate_summary`|регулярная сводка по накопленным данным каждые N секунд|

Задачи планировщика живут в процессе бэкенда, их метаданные — в SQLite
(таблица `scheduled_tasks`), поэтому после перезапуска приложения задачи
восстанавливаются. В приложении появился раздел «🗓 Планировщик» (задачи,
напоминания, сводки, история запусков) и очередь уведомлений в основной области
чата; API вырос на 14 эндпоинтов `/scheduler/*`; прогон дня — скриптами
`scripts/scheduler_demo.py` и `scripts/scheduler_report.py` с отчётом
[docs/reports/scheduler_demo.md](reports/scheduler_demo.md).

Как устроено внутри — [architecture.md](architecture.md), эндпоинты с примерами —
[api.md](api.md), карта модулей — [../STRUCTURE.md](../STRUCTURE.md).

## 1. Что нужно для запуска

|Компонент|Зачем|Проверка|
|---|---|---|
|Python 3.14 и `uv`|зависимости дня (в том числе `apscheduler`) и запуск|`uv --version`|
|Ключ `DEEPSEEK_API_KEY`|только ответ агента: распознавание реплики и генерация — часть хода агента|`day18/.env`|
|Порт 8000|API дня; на нём же живёт планировщик|`curl http://127.0.0.1:8000/scheduler/status` → `{"running": true, …}`|
|Сеть до источника сбора|данные для `collect_data`/`generate_summary` — не обязательна: у прогона есть детерминированный стенд|`curl -s -o /dev/null -w "%{http_code}" https://jsonplaceholder.typicode.com/posts` → `200`|

Сам планировщик и ручные вызовы инструментов от ключа **не зависят**: постановка
задачи, тики, таблицы и уведомления работают без DeepSeek. Ключ нужен только там,
где ход строит модель, — это чат и кнопка «🤖 Спросить агента» в разделе «🔌 MCP».
Автоматический прогон четырёх сценариев вообще обходится без сети: стенд отдаёт
свой JSON, поэтому `uv run python scripts/scheduler_demo.py` работает офлайн.

## 2. Установка и запуск

Менеджер зависимостей — `uv`: прямые зависимости в `pyproject.toml` (в том числе
`apscheduler`), точные версии — в `uv.lock`, интерпретатор — `.python-version`.
Активировать окружение не нужно, `uv run` сам находит `.venv`. Все команды — из
папки дня:

```bash
cd day18
uv sync                  # создать .venv по uv.lock (включая apscheduler)
cp .env.example .env     # затем впишите DEEPSEEK_API_KEY=sk-... (для ответа агента)
```

`uv sync` нужно выполнить **до** первого запуска: и бэкенд, и `uv run streamlit`
поднимаются в этом окружении.

Терминал 1 — бэкенд: в его процессе живёт планировщик (APScheduler стартует в
lifespan и останавливается при выходе), поэтому фон существует, пока работает
бэкенд:

```bash
uv run uvicorn backend.api.main:app --port 8000
```

Терминал 2 — интерфейс: <http://localhost:8501>

```bash
uv run streamlit run app.py
```

Ключ бэкенд читает так: `day18/.env` → переменная окружения `DEEPSEEK_API_KEY`
(файла нет — ключ можно задать только окружением). Адрес бэкенда фронтенд и
MCP-сервер берут из `DAY18_BACKEND_URL` (по умолчанию
`http://127.0.0.1:8000`); переменная нужна, только если порт нестандартный.
Проверка перед работой:

```bash
uv run python scripts/scheduler_demo.py   # четыре сценария планировщика в консоли
uv run pytest -q                          # автотесты дня
```

## 3. Планировщик и три инструмента

Планировщик — это `TaskScheduler` (`backend/services/scheduler.py`) поверх
`APScheduler` (`AsyncIOScheduler`, часовой пояс `UTC`). Метаданные задач лежат в
таблице **`scheduled_tasks`** — она источник правды; APScheduler держит задачи в
памяти. Раз в 5 секунд (`SCHEDULER_SYNC_SECONDS`) набор job'ов сверяется с
таблицей, поэтому задача, созданная через `POST /scheduler/tasks` (в том числе
MCP-сервером), подхватывается автоматически и переживает перезапуск процесса.

Три инструмента дня:

|Инструмент|Расписание|Что сохраняет|Что возвращает|
|---|---|---|---|
|`schedule_reminder`|**разовое** (`date`): через `delay_seconds` секунд|строку в `reminders` (`text`, `remind_at`, `status="scheduled"`, `task_id`); на тике — `status="done"` и уведомление `kind="reminder"` с текстом «Напоминание: …»|на регистрации — `{"reminder": …, "reminder_id": N}`; на тике — напоминание со `status="done"` и уведомление|
|`collect_data`|**периодическое** (`interval`): первый запрос сразу, дальше каждые `interval_seconds`|строку в `collected_data` (`name`, `source_url`, `payload` — ответ источника, `collected_at`)|`{"collection": {"name", "source_url", "records_saved": 1, "records_in_payload", "last_collected_at", "collected_id"}}`|
|`generate_summary`|**периодическое** (`interval`): первая сводка сразу за прошедший интервал, дальше каждые `interval_seconds`|строку в `periodic_summaries` (`content`, `period_start`…`period_end`, `total_records`, `key_metrics`) и уведомление `kind="summary"`|`{"summary": …, "aggregate": {"period_start", "period_end", "total_records", "summary_text", "key_metrics"}}`|

Аргументы инструментов и их границы (`GET /scheduler/tools` отдаёт то же самое —
интерфейс строит форму по этому каталогу):

|Инструмент|Аргумент|Тип|Обязательный|Границы|
|---|---|---|---|---|
|`schedule_reminder`|`text`|string|да|до 500 символов|
|`schedule_reminder`|`delay_seconds`|integer|да|1..86400 с|
|`collect_data`|`source_url`|string|да|http/https, до 500 символов|
|`collect_data`|`interval_seconds`|integer|да|1..86400 с|
|`collect_data`|`name`|string|да|до 100 символов|
|`generate_summary`|`name`|string|да|до 100 символов|
|`generate_summary`|`interval_seconds`|integer|да|1..86400 с (и период агрегации, и период повтора)|

Расписание выводится из инструмента (у напоминания — разовое, у двух других —
`interval`) и может быть переопределено вручную: `schedule_type` = `date` |
`interval` | `cron` (cron — выражение из пяти полей, например `*/5 * * * *`).

Две вещи, которые объясняют поведение фона:

- **Тик — синхронная функция.** APScheduler выполняет её в пуле потоков, поэтому
  сбор данных из сети идёт в фоне и не блокирует цикл событий FastAPI: интерфейс
  и API отвечают, пока задача работает.
- **Тик не ходит через MCP-соединение.** Оно принадлежит пользователю и держит
  блокировку клиента, поэтому вызов инструмента из тика был бы дедлоком. Тик
  вызывает функции домена напрямую, а MCP-инструмент — тонкая обёртка над
  `POST /scheduler/tasks` (единственный писатель в SQLite — процесс бэкенда).

Пропущенный запуск догоняется: если расчётный момент уже прошёл (приложение было
выключено), задача выполняется сразу при восстановлении. Ошибка тика не валит
планировщик: запуск пишется в `task_runs` со `status="error"`, пользователю уходит
уведомление `kind="error"`, задача остаётся активной и повторит попытку.
Разовая задача после успешного тика становится `completed` и снимается с
обслуживания. Таблица сводок названа `periodic_summaries`, а не `summaries`:
имя `summaries` занято конспектами сжатия истории (день 9).

## 4. Как запланировать задачу

### Через интерфейс

1. Откройте <http://localhost:8501> и выберите раздел **«🗓 Планировщик»**.
2. Раскройте форму **«➕ Запланировать задачу»** — она повторяет каталог
   инструментов: выберите инструмент (поле «Инструмент», подписи — «⏰
   Напоминание», «📥 Периодический сбор данных», «📊 Регулярная сводка»), и ниже
   появятся поля его аргументов —
   числовые с границами из `GET /scheduler/tools`, строковые — текстом. Значения
   по умолчанию: 30 с у напоминания, 10 с и
   `https://jsonplaceholder.typicode.com/posts` у сбора, 20 с у сводки.
3. При необходимости заполните «Имя задачи (необязательно)», оставьте флажок
   «Выполнить немедленно при регистрации» (тогда первый сбор или первая сводка
   выполняются сразу) и выберите расписание — «по инструменту» (как задумано
   доменом), `interval` или `cron` (при cron появится поле выражения,
   по умолчанию `*/5 * * * *`).
4. Нажмите **«🗓 Запланировать»** — задача появится в таблице выше со статусом
   «▶ активна» и временем следующего запуска.

### Через API

Тот же код-путь, что у MCP-инструментов: `POST /scheduler/tasks` принимает
`tool`, `arguments`, необязательные `name`, `run_now`,
`schedule_type`/`schedule_value`.

```bash
curl -X POST http://127.0.0.1:8000/scheduler/tasks \
     -H "Content-Type: application/json" \
     -d '{"tool": "collect_data",
          "arguments": {"source_url": "https://jsonplaceholder.typicode.com/posts",
                        "interval_seconds": 10, "name": "posts"}}'
```

Ожидаемо `201` и тело:

```json
{
  "task": {
    "id": 1,
    "name": "Сбор: posts",
    "tool_name": "collect_data",
    "arguments": {"source_url": "https://jsonplaceholder.typicode.com/posts",
                  "interval_seconds": 10, "name": "posts"},
    "schedule_type": "interval",
    "schedule_value": {"seconds": 10},
    "schedule_label": "каждые 10 с",
    "status": "active",
    "last_run_at": null,
    "next_run_at": "2026-09-23T10:00:10+00:00"
  },
  "result": {"collection": {"name": "posts", "source_url": "https://jsonplaceholder.typicode.com/posts",
                            "records_saved": 1, "records_in_payload": 100}},
  "immediate": true,
  "message": "Сбор «posts» запущен: первая запись собрана",
  "error": null
}
```

Поля ответа: `task` — созданная задача, `result` — результат немедленного
действия (`null`, если `run_now=false` или действие не удалось), `immediate` —
выполнялось ли оно, `message` — подтверждение для пользователя и модели, `error` —
причина, по которой немедленное действие не удалось (задача при этом остаётся
зарегистрированной).

Живой источник отвечает не мгновенно, поэтому первый сбор при недоступном адресе
даёт `error` с текстом причины, но не роняет запрос: `201` и рабочая задача. Коды
отказов: `400` — незнакомый инструмент, плохие аргументы, негодное расписание;
`422` — невалидное тело (Pydantic).

## 5. Напоминания

`schedule_reminder` — **разовая** задача: при регистрации она сохраняет строку в
`reminders` и запоминает её номер в аргументах задачи (`reminder_id`), а в момент
`remind_at` (сейчас + `delay_seconds`) тик помечает напоминание выполненным
(`status="done"`) и кладёт уведомление «Напоминание: …» в очередь. После этого
задача становится `completed` — напоминание выдаётся ровно один раз, повторный
тик для неё невозможен.

Где видно результат:

- **Основная область**: непрочитанные уведомления рисуются в самом верху
  страницы — до переключателя разделов, поэтому их видно из любого раздела.
  Фрагмент обновляется раз в 5 секунд, так что напоминание появляется **без
  перезагрузки страницы**. У каждого уведомления — кнопка **«✔ Прочитано»**:
  после неё оно уходит из основной области, но остаётся в истории раздела
  «🗓 Планировщик».
- **Раздел «🗓 Планировщик»**: таблица «⏰ Напоминания» (столбцы «текст»,
  «напомнить», «состояние», «создано» — то есть `text`, `remind_at`, `status`,
  `created_at` из `GET /scheduler/reminders`) и переключатель «Все / Ждут выдачи /
  Выданы»; рядом — таблица истории запусков выбранной задачи (фаза, результат,
  длительность, ошибка).

**Через API:** `GET /scheduler/reminders` (фильтр `status=scheduled|done`) и
`GET /scheduler/notifications` (`unread_only=true`, `POST
/scheduler/notifications/{id}/read` ставит отметку; повторная отметка —
безопасный no-op, неизвестный номер — `404`).

```bash
curl "http://127.0.0.1:8000/scheduler/reminders?status=done"
curl "http://127.0.0.1:8000/scheduler/notifications?unread_only=true"
```

Если ход агента поставил фоновую задачу, это видно и в чате: под ответом
появляется строка «🗓 Планировщик: …» из поля `schedule` ответа генерации.

## 6. Настройка сбора данных

`collect_data` читает JSON по `source_url` и складывает **весь ответ** одной
записью в таблицу `collected_data` (колонки `name`, `source_url`, `payload`,
`collected_at`). Первый запрос выполняется сразу при регистрации (если не сняли
флажок «Выполнить немедленно»), дальше — каждые `interval_seconds` секунд.
`name` — имя сбора: по нему записи отбираются сводкой и фильтруются в API
(`GET /scheduler/collected?name=posts`).

Что важно знать:

- **Источник** — адрес HTTP/HTTPS до 500 символов; не JSON или не-2xx — отказ.
  Таймаут запроса — 10 с, тело ответа больше 256 КиБ не принимается: гигантский
  JSON не должен раздувать базу.
- **Если источник недоступен**, тик завершается ошибкой: запуск попадает в
  `task_runs` со `status="error"`, пользователю уходит уведомление
  `kind="error"` («Сбор «posts»: …»), а задача **остаётся активной** и повторит
  попытку на следующем тике. Планировщик при этом не падает — падение одного
  сбора не останавливает остальные задачи.
- **Пустые ответы тоже сохраняются**: даже если источник вернул `[]`, это факт
  сбора — сводка за период посчитается и скажет «За период записей не собрано.».
- Чтобы не зависеть от внешнего API, в прогоне используется стенд с
  детерминированным источником (см. раздел 9); живой адрес задаётся параметром
  `--source-url`.

## 7. Как получить сводку

`generate_summary` агрегирует записи `collected_data` с этим `name`.
`interval_seconds` — **и период агрегации, и период повтора**: первая сводка
считается сразу за прошедший интервал, дальше — каждые `interval_seconds` секунд
(так одна настройка задаёт и «за какой период», и «как часто»).

В `key_metrics` попадает (`AGGREGATION_MAX_FIELDS = 30` полей,
`AGGREGATION_SAMPLES = 5` примеров значений):

- `period_seconds` и `sources` — длина периода и число записей по каждому имени
  сбора;
- `numeric` — числовые поля: `count`, `avg`, `min`, `max` (bool числовым полем не
  считается: в Python он подкласс `int`);
- `categorical` — строковые поля и прочие значения: `unique` — сколько уникальных
  и `samples` — примеры;
- `payload_types` — сколько записей было списком, объектом и скаляром.

Поля берутся по именам ключей (в том числе вложенных), без индексов: у ответа
jsonplaceholder это `id`, `userId`, `title`, `body`. Текст сводки
(`content` в таблице `periodic_summaries`) называет период, число записей,
числовые поля со статистикой и категориальные поля с числом уникальных значений.

Где смотреть: раздел «🗓 Планировщик» → таблица **«📊 Регулярные сводки»**
(«имя», «период», «записей», «метрики» одной строкой) и кнопка
**«📄 Показать текст»** — полный текст сводки; через API —
`GET /scheduler/summaries?name=posts`.

Агент узнаёт о сводке сам: уведомление `kind="summary"` (первые 200 символов
текста) видно в области чата, а когда ход агента сам поставил задачу, в системный
промпт дописывается блок **«## Данные планировщика»** — там и подтверждение
регистрации, и текст сводки, если она уже посчитана. Поэтому модель отвечает по
фактическим данным сводки, а не по общим словам.

## 8. Пауза, возобновление и удаление задачи

В разделе «🗓 Планировщик» выберите задачу в списке «Действие над задачей» и
нажмите кнопку:

|Кнопка|Что происходит|Эндпоинт|
|---|---|---|
|**«⏸ Пауза»**|`active` → `paused`: расписание сохраняется, запусков нет|`POST /scheduler/tasks/{task_id}/pause`|
|**«▶ Возобновить»**|`paused` → `active`: задача ставится в планировщик заново (даже если пауза пережила перезапуск)|`POST /scheduler/tasks/{task_id}/resume`|
|**«▶ Запустить сейчас»**|внеочередной тик тем же кодом, что и запуск по расписанию; запись попадает в историю|`POST /scheduler/tasks/{task_id}/run`|
|**«🗑 Удалить»**|задача снимается с обслуживания, её строка и журнал запусков удаляются каскадом; напоминания, сводки и уведомления остаются|`DELETE /scheduler/tasks/{task_id}`|

Ошибки состояний — это не «сломалось», а конфликт:

|Ситуация|Код|Смысл|
|---|---|---|
|задачи нет|`404`|такого номера в `scheduled_tasks` нет|
|пауза не активной задачи|`409`|например, задача уже `paused` или `completed`: снимать нечего|
|возобновление не стоящей на паузе|`409`|задача не в `paused` — возобновлять нечего|

Историю запусков видно в разделе (фаза `prepare` — немедленное действие при
регистрации, `tick` — запуск по расписанию; статус `ok`/`error`, длительность,
текст ошибки) и в API — `GET /scheduler/tasks/{task_id}/history`.

## 9. Сценарии тестирования

Все команды — из папки `day18`; бэкенд для API-сценариев запущен на порту 8000.

### 9.1 Напоминание на 30 секунд

1. Раздел «🗓 Планировщик» → инструмент «⏰ Напоминание», текст «позвонить
   клиенту», `delay_seconds` = 30 → «🗓 Запланировать».
2. Ожидаемо: в таблице задач строка со статусом «▶ активна» и временем выдачи;
   через ~30 с в основной области появляется уведомление с подписью
   «⏰ напоминание» и текстом «Напоминание: позвонить клиенту» (кнопка «✔
   Прочитано» убирает его из основной области), в таблице напоминаний состояние
   меняется на «✅ выдано», а задача — на «✅ выполнена».

Через API то же самое:

```bash
curl -X POST http://127.0.0.1:8000/scheduler/tasks \
     -H "Content-Type: application/json" \
     -d '{"tool": "schedule_reminder", "arguments": {"text": "проверить почту", "delay_seconds": 30}}'
curl "http://127.0.0.1:8000/scheduler/notifications?unread_only=true"
```

### 9.2 Периодический сбор каждые 10 секунд

```bash
curl -X POST http://127.0.0.1:8000/scheduler/tasks \
     -H "Content-Type: application/json" \
     -d '{"tool": "collect_data",
          "arguments": {"source_url": "https://jsonplaceholder.typicode.com/posts",
                        "interval_seconds": 10, "name": "posts"}}'
```

Ожидаемо: `201`, первая запись собрана сразу. Подождите ~35 с и проверьте, что
записей стало больше: `GET /scheduler/collected?name=posts` отдаёт `count` (в
ответе) и `total` (всего в базе) — `total` растёт примерно до 4, у каждой записи
свой `collected_at`, а `payload` содержит 100 постов jsonplaceholder.

### 9.3 Сводка с интервалом 20 секунд

```bash
curl -X POST http://127.0.0.1:8000/scheduler/tasks \
     -H "Content-Type: application/json" \
     -d '{"tool": "generate_summary", "arguments": {"name": "posts", "interval_seconds": 20}}'
curl "http://127.0.0.1:8000/scheduler/summaries?name=posts"
```

Ожидаемо: первая сводка в ответе сразу (за прошедшие 20 секунд; если сбор ещё не
набрал записей — `total_records: 0` и текст «За период записей не собрано.»), а
через ~20 с появляется следующая. В `key_metrics` у сводки есть `numeric` с
`avg`/`min`/`max` по `id` и `userId` и `categorical` с числом уникальных `title` и
`body`; `content` — тот же текст, что виден кнопкой «📄 Показать текст» в разделе.

### 9.4 Перезапуск бэкенда — задачи восстанавливаются

1. Остановите бэкенд (Ctrl+C) и запустите снова тем же `uv run uvicorn
   backend.api.main:app --port 8000` (база `day18/agents.db` та же).
2. Ожидаемо: `GET /scheduler/tasks` отдаёт те же задачи со `status="active"` и
   непустым `next_run_at`; в плашке состояния раздела — «Планировщик работает».
3. Подождите ~25 с: счётчик `GET /scheduler/collected?name=posts` продолжает
   расти — фон работает, а не просто «задача висит в базе». Пропущенные за время
   простоя запуски догоняются сразу при старте.

### 9.5 Автотесты

```bash
uv run pytest -q
```

Автотесты дня офлайн: источник подменяется фейком, APScheduler в e2e-тестах —
заглушкой, а реальная связка с таймерами проверяется отдельным тестом с
интервалом 1 с. Разделы планировщика покрывают таблицу переходов FSM, разбор
аргументов и расписаний, агрегацию, распознавание реплик, жизненный цикл
сервисов, тики, восстановление после перезапуска и контракт `/scheduler/*`.

### 9.6 Автоматический прогон четырёх сценариев

```bash
uv run python scripts/scheduler_demo.py --report docs/reports/scheduler_demo.md
```

Скрипт поднимает изолированный стенд (отдельная БД во временном каталоге, свой
порт, детерминированный источник — сеть не нужна), вызывает инструменты
по-настоящему через свой MCP-сервер и прогоняет те же четыре сценария: напоминание
на 30 секунд, сбор каждые 10 секунд с ожиданием 35 секунд, сводку с интервалом
20 секунд и перезапуск стенда. Ключ `--report` собирает по этому прогону отчёт —
в нём есть таблица «инструмент | расписание | что сохраняется | что возвращает |
пример вывода» с фактическими значениями прогона.

Полезные ключи:

```bash
uv run python scripts/scheduler_demo.py --source-url https://jsonplaceholder.typicode.com/posts
uv run python scripts/scheduler_demo.py --keep-db      # оставить БД прогона для разбора
uv run python scripts/scheduler_demo.py --tests        # добавить в отчёт сводку pytest
uv run python scripts/scheduler_demo.py --json         # итог прогона как JSON
```

Без `--source-url` источник подменён стендом; с ним стенд ходит в настоящий
интернет, и поведение то же (нужна сеть). Код выхода `1` — если какая-то проверка
сценария не прошла.
