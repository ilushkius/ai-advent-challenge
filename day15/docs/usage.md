# День 15 — контролируемые переходы состояний задачи: установка и использование

День 15 — агент DeepSeek: FastAPI-бэкенд, Streamlit-интерфейс, SQLite и ключ
DeepSeek. Главная возможность дня — **контролируемые переходы**: задача ходит по
этапам только по объявленному графу. Переход вперёд открывается согласованием
этапа (флагом), `done` терминален, а любая недопустимая попытка — кнопкой в
интерфейсе, вызовом API или предложением модели — отклоняется с причиной и
подсказкой и остаётся в журнале с меткой `accepted = false`; состояние задачи
при этом не меняется.

Эта инструкция самостоятельна: установка и запуск, правила допуска, панель
«🧭 Состояние задачи», разбор отказа, сценарии проверки и покадровый сценарий
видео — всё в одном месте, знания прошлых дней не требуются. Полное описание
приложения и всех его возможностей — в [`README.md`](../README.md).

## 1. Требования и установка

Нужен **Python 3.14+**. Все команды выполняются из папки дня в PowerShell.

```powershell
cd day15
uv sync
copy .env.example .env      # затем впишите DEEPSEEK_API_KEY=sk-...
```

Менеджер зависимостей — **uv**: прямые зависимости объявлены в `pyproject.toml`,
точные версии всех прямых и транзитивных пакетов — в `uv.lock`, версия
интерпретатора — в `.python-version`. `uv sync` создаёт `.venv` и приводит его
ровно к содержимому лока; отдельно создавать окружение и активировать его не
нужно — `uv run <команда>` сам находит `.venv` проекта.

Ключ DeepSeek нужен **только бэкенду** и лежит в файле `.env` в папке дня;
порядок поиска — файл, затем переменная окружения `DEEPSEEK_API_KEY`. В git
`.env` не коммитится.

Прогону кадров в настоящем браузере (режим `--auto`) нужен Chromium Playwright —
один раз на машину, в репозиторий он не попадает:

```powershell
uv run playwright install chromium
```

| Без ключа | Поведение |
|---|---|
| Задачи и переходы: `POST /agents/{id}/tasks`, `GET /tasks/{id}/state`, `GET /tasks/{id}/allowed-next`, `GET /tasks/{id}/history`, `PATCH /tasks/{id}/context`, `POST /tasks/{id}/transition`, `POST /tasks/{id}/pause`, `POST /tasks/{id}/resume`, `POST /tasks/{id}/advance`, `POST /tasks/{id}/rollback` | работают полностью — правила допуска и журнал от сети не зависят |
| Панель «🧭 Состояние задачи» в интерфейсе | работает полностью, кроме чата |
| `POST /agents/{id}/generate` | `502` со `status: "error"` и текстом «Ключ API не задан…»; в теле ответа при этом есть `task_state` (этап, шаг, `allowed_next`, `blocked`) и `system_prompt` с блоком состояния |
| Офлайн-демонстрации `scripts/controlled_transitions_demo.py` | работают: подменяют клиента DeepSeek заглушкой, сеть и ключ не нужны |

## 2. Запуск

Нужны **два процесса**, оба запускаются из папки дня.

**Терминал 1 — бэкенд (FastAPI + uvicorn, порт 8000):**

```powershell
cd day15
uv run uvicorn backend.api.main:app --port 8000
```

При старте создаётся файл базы `agents.db` в папке дня (если его ещё нет) и
таблицы приложения, включая `task_states` и `task_transitions`. Swagger со всеми
эндпоинтами и формами данных — на `http://127.0.0.1:8000/docs`.

**Терминал 2 — интерфейс (Streamlit, порт 8501 по умолчанию):**

```powershell
cd day15
uv run streamlit run app.py
```

Откройте адрес, который Streamlit напечатал в консоли (обычно
`http://localhost:8501`). В сайдбаре должно появиться
«🟢 Бэкенд: http://127.0.0.1:8000 · агентов: N», а среди разделов основной
области — «🧭 Состояние задачи».

Если бэкенд поднят на другом порту, задайте адрес перед запуском Streamlit:

```powershell
$env:DAY15_BACKEND_URL = "http://127.0.0.1:8019"
uv run streamlit run app.py
```

Проверка бэкенда из третьего терминала:

```powershell
curl.exe http://127.0.0.1:8000/
```

> [!] В Windows PowerShell `curl` — это алиас командлета `Invoke-WebRequest`, и
> привычные флаги (`-X`, `-H`, `-d`) у него означают другое. Примеры в этой
> документации используют **`curl.exe`** — вызывайте именно его либо работайте в
> bash-подобной оболочке (Git Bash, WSL).

В ответе есть ключ `task_transitions` со списком эндпоинтов переходов — это
подтверждает, что API живой.

## 3. Как устроены контролируемые переходы

Правила допуска живут в одном месте — `backend/domain/task_state_machine.py`.
Фронтенд их не повторяет: он рисует кнопки по полям `allowed_next` и `blocked` из
ответа бэкенда, поэтому интерфейс и API не могут «разъехаться».

### 3.1 Граф переходов

Пара, которой нет в таблице, — это **отказ**, а не «переход по умолчанию».

| Этап | Куда можно перейти | Что для этого нужно |
|---|---|---|
| `planning` | `execution`, `paused` | в `execution` — флаг `plan_approved` |
| `execution` | `validation`, `planning`, `paused` | в `validation` — флаг `implementation_complete` |
| `validation` | `done`, `execution`, `paused` | в `done` — флаг `validation_passed` |
| `done` | никуда | этап терминальный: переходов нет вовсе, даже на паузу |
| `paused` | `planning`, `execution`, `validation` | этап паузы — всегда; другой этап — только если он и так достижим из этапа паузы |

Граф целиком (вместе с шагами каждого этапа) панель показывает текстом —
ASCII-схемой без внешних библиотек:

```text
прямой ход:    planning -> execution -> validation -> done
откат:         execution -> planning;  validation -> execution
пауза:         planning|execution|validation -> paused
возобновление: paused -> planning|execution|validation
терминал:      done -> переходов нет
guards:        planning->execution: plan_approved
               execution->validation: implementation_complete
               validation->done: validation_passed
```

Внутри этапа задача движется по шагам; событие «следующий шаг» на последнем шаге
этапа означает переход на следующий этап — снова по графу и снова через guard.

| Этап | Шаги |
|---|---|
| `planning` | `gather_requirements` → `define_scope` → `create_plan` |
| `execution` | `implement` → `test_locally` |
| `validation` | `review` → `run_tests` → `finalize` |
| `done` | шагов нет (`current_step` остаётся `finalize`) |
| `paused` | шагов нет: сохраняется шаг, на котором задача встала |

### 3.2 Guard-условия: флаги-согласования

Три прямых перехода закрыты, пока пользователь не подтвердил этап явно. Флаги
лежат в `context` строки задачи и выставляются чекбоксами панели или запросом
`PATCH /tasks/{task_id}/context` — из текста реплики согласие не выводится.

| Флаг в `context` | Подпись в панели | Что открывает |
|---|---|---|
| `plan_approved` | 📝 План утверждён | `planning → execution` |
| `implementation_complete` | ⚙️ Реализация завершена | `execution → validation` |
| `validation_passed` | ✅ Валидация пройдена | `validation → done` |

Значение проверяется как булево `True`, а не «истинно»: строка `"true"` в
`context` согласием не считается, поэтому флаги надёжнее выставлять через API
(там тип проверяет схема) или чекбоксами панели.

**Движение назад сбрасывает согласования.** Откат отменяет флаг этапа-цели и всех
последующих этапов: `validation → planning` сбрасывает все три, `validation →
execution` — `implementation_complete` и `validation_passed`, `execution →
planning` — все три. Иначе после отката «план утверждён» остался бы выставленным
и следующий переход вперёд прошёл бы мимо согласования. Правило действует и для
`POST /tasks/{id}/rollback`, и для кнопки-этапа назад, и для продолжения из паузы
в более ранний этап.

### 3.3 Отказ называется причиной и подсказкой

Отказ — не «ничего не произошло», а два текста: **причина** (почему нельзя; она
же пишется в журнал и в текст исключения) и **подсказка** (что сделать). Пример
для перехода через два этапа:

```text
Нельзя перейти из planning в done: пропущены этапы execution и validation
Сначала перейдите в execution и пройдите этапы по порядку.
```

Каждая попытка — состоявшаяся или отклонённая — попадает в журнал
`task_transitions`. У отклонённой строки `accepted = false`, причина в поле
`reason`, а `to_stage`/`to_step` могут быть пустыми; состояние `task_states`
такая строка не меняет. Журнал читается целиком: `GET /tasks/{task_id}/history`.

## 4. Панель «🧭 Состояние задачи»

Раздел показывает состояние активного агента; если задачи ещё нет, панель
предлагает её завести формой (`task_id` + начальный этап из `planning`,
`execution`, `validation`). Ниже — сверху вниз — что делает каждый элемент.

**Карточка состояния:** «задача · агент · обновлено», текущий этап, текущий шаг,
ожидаемое действие и строка «**Допустимые следующие этапы:**», посчитанная
бэкендом. Если задача на паузе, добавляется плашка «⏸ Пауза с этапа …».

**Кнопки-этапы** (блок «Переходы по этапам») — по одной на каждый этап, кроме
текущего: «➡️ 🧭 planning — планирование», «➡️ ⚙️ execution — выполнение»,
«➡️ 🔍 validation — валидация», «➡️ ✅ done — завершено» и «⏸ Пауза». Кнопка
этапа, которого нет в `allowed_next`, **погашена**, а причина отказа видна двумя
способами: при наведении (подсказка) и списком в раскрывающемся блоке «🔒 Почему
часть переходов недоступна». Если ограничений нет, вместо списка стоит подпись
«🔓 Ограничений нет: доступны все объявленные переходы».

**Кнопка «⏭ Следующий шаг»** ведёт по шагам этапа, а с последнего шага — на
следующий этап. Она не гасится заранее: целевой этап выбирает не пользователь,
поэтому попытка выйти из несогласованного этапа возвращается объяснением, какого
флага не хватает.

**Пауза и продолжение.** На активном этапе доступна кнопка «⏸ Пауза»: она
сохраняет этап и шаг. Когда задача на паузе, вместо неё появляются подпись
«⏸ Пауза с этапа **validation**, шаг `review`: продолжение вернёт это место»,
селектор «Куда продолжить» (по умолчанию — этап паузы; другие значения доступны,
потому что из этапа паузы они достижимы) и кнопка «▶️ Продолжить».

**Флаги этапа (guard-условия).** Три чекбокса — «📝 План утверждён»,
«⚙️ Реализация завершена», «✅ Валидация пройдена» — и одна кнопка
«💾 Сохранить флаги», которая отправляет все три значения сразу
(`PATCH /tasks/{task_id}/context`).

**Журнал — три вкладки:**

| Вкладка | Что показывает |
|---|---|
| «📜 Журнал переходов» | состоявшиеся переходы (`accepted = true`): откуда, куда, причина, время; первая строка — создание задачи |
| «🚫 Попытки недопустимых переходов» | отклонённые попытки (`accepted = false`): этап, шаг, цель, причина отказа, время — видно, что именно пробовали и почему нельзя |
| «🧩 Блок в системном промпте» | текст блока состояния ровно в том виде, в каком он уходит последним блоком системного сообщения каждого запроса |

## 5. Что происходит при недопустимом переходе

Состояние задачи при отказе **не меняется** — меняется только журнал, и в каждом
канале пользователь видит причину:

| Канал | Что видно |
|---|---|
| Интерфейс | красное сообщение (`st.error`) в начале основной области: «Переход не выполнен: \<причина\>». Так отвечают все мутации панели — и кнопки-этапы, и «Следующий шаг», и сохранение флагов |
| API, `POST /tasks/{task_id}/transition` | `400`, в `detail` — причина **и** подсказка: «Нельзя перейти в execution: план не утверждён Утвердите план: отметьте флаг «📝 План утверждён» в панели задачи.» |
| API, `pause` / `resume` / `advance` / `rollback` | `400` с причиной; подсказки нет, потому что целевой этап выбирает система, а не пользователь |
| Ответ агента, неприменённое намерение реплики | «⚠️ Переход по реплике «advance» не выполнен: Нельзя перейти в execution: план не утверждён Доступные следующие этапы: paused.» — реплика обрабатывается как обычно, диалог не падает |
| Ответ агента, предложение модели | «🚧 Ответ предлагает переход в done, но это недопустимо. Нельзя перейти в done: валидация не пройдена Отметьте флаг «✅ Валидация пройдена» в панели задачи.» — предложение не выполняется и в ответе не остаётся |

Короткие причины отказа (дословно, они же попадают в журнал):

| Попытка | Причина | Подсказка |
|---|---|---|
| `planning → done` | Нельзя перейти из planning в done: пропущены этапы execution и validation | Сначала перейдите в execution и пройдите этапы по порядку. |
| `planning → execution` без флага | Нельзя перейти в execution: план не утверждён | Утвердите план: отметьте флаг «📝 План утверждён» в панели задачи. |
| `execution → validation` без флага | Нельзя перейти в validation: реализация не завершена | Отметьте флаг «⚙️ Реализация завершена» в панели задачи. |
| `validation → done` без флага | Нельзя перейти в done: валидация не пройдена | Отметьте флаг «✅ Валидация пройдена» в панели задачи. |
| из `done` куда угодно | Нельзя перейти из done: этап done терминальный | Завершённая задача изменению не подлежит: заведите новую задачу. |
| повторная пауза | Нельзя перейти из paused в paused: задача уже на этом этапе | Выберите другой этап. |
| `paused → done` | Нельзя перейти из paused в done: из паузы возвращаются только в planning, execution или validation | Продолжите задачу в этап, откуда её поставили на паузу, и доведите до нужного этапа. |
| `paused → validation`, пауза была на `planning` | Нельзя перейти из paused в validation: пауза была на этапе planning | Продолжите задачу в этап, откуда её поставили на паузу (или в доступный следующий этап). |
| откат через два этапа: `validation → planning` | Нельзя перейти из validation в planning: откат идёт по одному этапу (сначала execution) | Откатывайтесь по одному этапу (кнопка «Откат»). |

Коды ответов API:

| Код | Когда |
|---|---|
| `400` | переход недопустим: пропуск этапа, откат не по одному этапу, отсутствие флага, повторная пауза, пауза завершённой задачи, неверная цель отката |
| `404` | задачи или агента с таким идентификатором нет |
| `409` | повторный `task_id` при создании задачи — состояние не перезаписывается |
| `422` | невалидное тело: неизвестный этап или шаг, пустое тело флагов (`{}`), не-булево значение флага |

Неизвестный этап в теле запроса отклоняет схема (422), а тот же случай внутри
скриптов даёт отказ «Неизвестный этап задачи: 'нет-такого'. Допустимые: planning,
execution, validation, done, paused».

## 6. Пауза и продолжение после перезапуска приложения

Пауза ничего не «забывает»: этап возврата хранится в колонке
`task_states.paused_from_stage`, а шаг — в `current_step`, который пауза не
меняет. Поэтому точка возврата переживает перезапуск и бэкенда, и интерфейса, и
всего компьютера — она в SQLite, а не в памяти процесса.

Проверка «на себе»:

1. доведите задачу до `execution` (или `validation`) и нажмите «⏸ Пауза» —
   в карточке появится «⏸ Пауза с этапа …», а `resume` вернёт ровно это место;
2. остановите бэкенд (`Ctrl+C` в терминале 1) и поднимите снова той же командой
   `uv run uvicorn backend.api.main:app --port 8000`;
3. запросите состояние — этап `paused`, шаг прежний, `paused_from_stage`
   заполнен:

```powershell
curl.exe http://127.0.0.1:8000/tasks/tz/state
curl.exe -X POST http://127.0.0.1:8000/tasks/tz/resume
```

`POST /tasks/{task_id}/resume` (в панели — кнопка «▶️ Продолжить») вернёт тот же
этап и шаг. Продолжение в **другой** разрешённый этап — это осознанный переход
кнопкой этапа или `POST /tasks/{task_id}/transition`; продолжение в свой этап
флаги не сбрасывает, а движение назад из паузы — сбрасывает.

То же доказательство воспроизводимо офлайн: `scripts/controlled_transitions_demo.py`
прогоняет две **разные** фазы в разных процессах (`subprocess`) и печатает pid
каждой: первая оставляет задачу на паузе, вторая читает состояние из БД и
продолжает с того же этапа и шага. Отчёт —
[`reports/controlled_transitions_demo.md`](reports/controlled_transitions_demo.md),
разделы «Продолжение после паузы» и «Журнал попыток». Управление прогоном:

```powershell
uv run python scripts/controlled_transitions_demo.py --all       # прогон и отчёт
uv run python scripts/controlled_transitions_demo.py --phase 1   # только фаза 1
uv run python scripts/controlled_transitions_demo.py --phase 2   # только фаза 2
uv run python scripts/controlled_transitions_demo.py --reset     # очистить прогон
```

Демонстрация работает на своей базе `controlled_transitions_demo.db` — базу
приложения `agents.db` она не трогает.

| Стенд для записи видео (браузер + UI) | `uv run python scripts/video_scenario.py --ui` | поднят живой `streamlit run app.py` на том же изолированном бэкенде, адрес открыт в браузере, напечатан чек-лист кадров §8; кадр 5 — по Enter (стенд перезапускает бэкенд и печатает состояние из SQLite) |
| Кадры в браузере без человека (`--auto`) | `uv run python scripts/video_scenario.py --auto` | Chromium с видимым окном сам проходит кадры §8 в темпе демонстрации (по умолчанию 2 с на действие, 120 мс на символ; **весь прогон 3–4 минуты** — замерено 3 мин 37 с в окне и 3 мин 34 с без окна), печатает строки «▸ …» и проверки `✓`/`✗`; код возврата 0 — все кадры сошлись. Медленнее/быстрее — `--pace` и `--typing` (`--pace 6` — спокойный показ, `--pace 0.15 --typing 1` — машинная проверка за минуту); без окна: `--headless` |
| Проверка, что API живой | `curl.exe http://127.0.0.1:8000/` | в ответе ключи `tasks`, `task_transitions`, `invariants` |
| Пропуск этапов | `curl.exe -X POST http://127.0.0.1:8000/tasks/tz/transition -H "Content-Type: application/json" -d "{\"stage\":\"done\"}"` на `planning` | `400`, `detail` начинается с «Нельзя перейти из planning в done: пропущены этапы execution и validation» |
| Переход вперёд без согласования | тот же запрос с `{"stage":"execution"}` | `400`: «Нельзя перейти в execution: план не утверждён Утвердите план: отметьте флаг «📝 План утверждён» в панели задачи.» |
| Пустое тело флагов | `curl.exe -X PATCH http://127.0.0.1:8000/tasks/tz/context -H "Content-Type: application/json" -d "{}"` | `422`; в теле ответа — причина «нужен хотя бы один флаг задачи» |
| Неизвестный этап | `-d "{\"stage\":\"нет-такого\"}"` в `transition` | `422` — значение не проходит валидацию схемы (значение вне Enum) |
| Согласование и переход | `curl.exe -X PATCH http://127.0.0.1:8000/tasks/tz/context -H "Content-Type: application/json" -d "{\"plan_approved\":true}"`, затем `POST /tasks/tz/transition` с `{"stage":"execution"}` | `200` и `200`: `stage` = `execution`, `allowed_next` содержит `planning` и `paused`, а `blocked` — причину для `validation` |
| Неизвестная задача | `POST /tasks/nope/transition`, `GET /tasks/nope/state` | `404` |
| Отклонённая попытка в журнале | `curl.exe http://127.0.0.1:8000/tasks/tz/history` | среди записей есть строки с `accepted: false`, причиной отказа и пустым `to_stage` |

Цепочка для последних сценариев — агент и задача заводятся двумя вызовами
(`agent_id` возьмите из ответа первого):

```powershell
curl.exe -X POST http://127.0.0.1:8000/agents -H "Content-Type: application/json" -d "{\"name\":\"Демо-агент\"}"
curl.exe -X POST http://127.0.0.1:8000/agents/<agent_id>/tasks -H "Content-Type: application/json" -d "{\"task_id\":\"tz\"}"
```

Тот же набор проверок «руками» в интерфейсе: нажмите погашенную кнопку
`done` — увидите причину в подсказке и в списке «🔒 Почему часть переходов
недоступна»; отметьте «📝 План утверждён» и сохраните флаги — кнопка
`execution` станет активной; после отклонённой попытки загляните во вкладку
«🚫 Попытки недопустимых переходов».

## 8. Сценарий демонстрации для видео (день 15)

Покадрово, 5–7 минут. Числа, цитаты отказов и журнал для сверки —
[`reports/controlled_transitions_demo.md`](reports/controlled_transitions_demo.md);
задача в кадрах — `tz-transitions`, как в отчёте. Кадры автоматизированы:
`uv run python scripts/video_scenario.py --all` проходит их сам (HTTP плюс
реальный рендер интерфейса через Streamlit AppTest, перезапуск бэкенда —
отдельным процессом) и печатает доказательство каждого кадра; `✗` и код
возврата 1 означают расхождение кода с этим описанием. Для самой записи есть два
режима. Стенд `--ui` поднимает живой `streamlit run app.py` на изолированном
бэкенде (своя БД, свой порт), открывает адрес в браузере и печатает чек-лист
кадров, а кадр 5 доказывает по Enter — перезапускает бэкенд на той же БД и
печатает прочитанное из SQLite состояние (два разных pid). Проход `--auto` идёт
дальше: Chromium с видимым окном сам кликает кадры в том же темпе, что и человек
(пауза между действиями, набор по символам), и в терминале видно и действие
(«▸ …»), и проверку результата — запись идёт без участия человека, а сверка идёт
по реальному интерфейсу. База приложения `agents.db` не трогается ни в одном
режиме.

**Кадр 0 — интро (30 сек).** Задание дня: задача ходит по этапам только по
объявленному графу, поэтому «перескочить» этап нельзя ни кнопкой, ни вызовом
API, ни предложением модели. Показать `backend/domain/task_state_machine.py` —
таблицу `ALLOWED_TRANSITIONS`, guard-условия `GUARDS` и тексты отказа
`_REFUSAL_TEXTS`; переключатель четырёх разделов («💬 Чат и память» / «👤 Профиль
пользователя» / «🧭 Состояние задачи» / «📏 Инварианты»); таблицы `task_states` и
`task_transitions` (раздел «Схема БД» в [`architecture.md`](architecture.md)).

**Кадр 1 — завести задачу (45 сек).** Раздел «🧭 Состояние задачи»: форма
«Новая задача (task_id)» (`tz-transitions`), селектор «Начальный этап» →
«➕ Создать задачу». В карточке: «Текущий этап: 🧭 planning — планирование»,
«Текущий шаг: `gather_requirements`», ожидаемое действие, ASCII-схема графа и
«**Допустимые следующие этапы:** `paused`». Развернуть «🔒 Почему часть переходов
недоступна» — три строки с причинами: `execution` («Нельзя перейти в execution:
план не утверждён»), `validation` («Нельзя перейти из planning в validation:
пропущен этап execution»), `done` («Нельзя перейти из planning в done: пропущены
этапы execution и validation»). Кнопки `execution`, `validation`, `done` погашены,
«⏸ Пауза» активна.

**Кадр 2 — «⏭ Следующий шаг» упирается в guard (1 мин).** Два нажатия:
`gather_requirements → define_scope → create_plan`. Третье нажатие — красное
«Шаг вперёд не выполнен: Нельзя перейти в execution: план не утверждён»,
состояние остаётся `planning/create_plan`. Открыть вкладку «🚫 Попытки
недопустимых переходов»: строка с целью `execution`, причиной отказа и временем —
этап и шаг задачи прежние.

**Кадр 3 — реплика не подставляет флаг (45 сек).** В чате отправить
«подтверждаю»: ответ начинается с «⚠️ Переход по реплике «advance» не выполнен:
Нельзя перейти в execution: план не утверждён Доступные следующие этапы: paused.»,
диалог продолжается, состояние не меняется. Проговорить: согласие этапа — это
данные (`context` строки задачи), а не вывод из текста реплики.

**Кадр 4 — флаг открывает ровно тот же переход (1 мин).** Чекбокс «📝 План
утверждён» → «💾 Сохранить флаги» (флеш «Флаги задачи сохранены.»). Кнопка
«➡️ ⚙️ execution — выполнение» становится активной, в «🔒 Почему часть переходов
недоступна» строкой меньше → нажать её: `execution/implement`. Затем два нажатия
«⏭ Следующий шаг»: первое даёт `test_locally`, второе — отказ «Нельзя перейти в
validation: реализация не завершена».

**Кадр 5 — пауза переживает перезапуск бэкенда (1 мин).** «⏸ Пауза» →
`paused/test_locally`, `paused_from_stage = execution`, в карточке «⏸ Пауза с этапа
…». Ctrl+C в терминале 1, снова `uv run uvicorn backend.api.main:app --port 8000`
на той же `day15/agents.db`, затем

```powershell
curl.exe http://127.0.0.1:8000/tasks/tz-transitions/state
```

— `"stage": "paused"`, `"paused_from_stage": "execution"`, `"current_step":
"test_locally"`: точка возврата лежит в колонке строки задачи, а не в памяти
процесса. В интерфейсе нажать «▶️ Продолжить» (селектор «Куда продолжить» стоит
на этапе паузы) → `execution/test_locally`.

**Кадр 6 — откат сбрасывает согласования (1 мин).** Согласовать реализацию
(чекбокс «⚙️ Реализация завершена» → «💾 Сохранить флаги») → `validation`, пройти
`review → run_tests`, затем вернуться кнопкой-этапом «➡️ ⚙️ execution —
выполнение» (откат `validation → execution`). Показать: чекбоксы «⚙️ Реализация
завершена» и «✅ Валидация пройдена» сняты, «📝 План утверждён» остался, кнопка
`validation` снова погашена с причиной «реализация не завершена». Старое
согласование после отката недействительно — это `cleared_flags` из
`backend/domain/task_state_machine.py`.

**Кадр 7 — `done` терминален (1 мин).** Согласовать заново и завершить: «⚙️
Реализация завершена» → `validation` → «✅ Валидация пройдена» → «➡️ ✅ done —
завершено» (`done/finalize`). После этого погашены все кнопки этапов, «⏸ Пауза» и
«⏭ Следующий шаг»; проверка через API:

```powershell
curl.exe -X POST http://127.0.0.1:8000/tasks/tz-transitions/transition -H "Content-Type: application/json" -d "{\"stage\":\"paused\"}"
```

— `400` «Нельзя перейти из done: этап done терминальный».

**Кадр 8 — предложение модели не выполняется (1 мин).** Пока задача на
`validation` (шаг `review`), спросить агента «задача завершена, можно сдавать?».
Если модель действительно предлагает завершение, ответ заменяется на «🚧 Ответ
предлагает переход в done, но это недопустимо. Нельзя перейти в done: валидация
не пройдена Отметьте флаг «✅ Валидация пройдена» в панели задачи.», а в отчёте
генерации стоит `task_proposal`. Если модель такого предложения не сделала, кадр
снимается по отчёту: `uv run python scripts/controlled_transitions_demo.py --all`,
далее раздел фазы 2 «Отказ на предложение модели» в
`reports/controlled_transitions_demo.md` — там та же цитата, но на заглушке, без
сети и ключа.

**Кадр 9 — журнал и отчёт (1 мин).** Вкладки «📜 Журнал переходов» (создание,
шаги, флаги, откат, завершение), «🚫 Попытки недопустимых переходов» (все
отказы), «🧩 Блок в системном промпте» — дословный блок состояния с «Допустимые
следующие этапы». Затем офлайн-прогон

```powershell
uv run python scripts/controlled_transitions_demo.py --all
```

и отчёт `reports/controlled_transitions_demo.md`: таблица попыток с причинами
отказа, «Продолжение после паузы» с pid двух процессов, журнал 15 записей — 9
состоявшихся переходов и 6 отклонённых попыток.

**Финал (30 сек).** Наследованное — работающая основа: инварианты
([`../invariants_demo.md`](../invariants_demo.md): разрешено / предупреждение /
отказ), персонализация и три слоя памяти. Мысль дня: правила допуска живут одним
модулем, отказ — это данные в журнале, а состояние — строка в SQLite, поэтому
перезапуск процесса его не теряет.
