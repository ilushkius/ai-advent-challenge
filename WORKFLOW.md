# Рабочий процесс проекта: от сырого задания до коммита с тегом

Маршрут для сложной задачи (эталон — день 21, папка `day21/`). Простые задачи
(кнопка, текст, правка документации) можно выполнять без архитектурной ступени —
сразу к исполнению.

```
1. Сырое задание           2. Архитектурный план        3. Исполнение            4. Фиксация
   из челленджа       →       ARCHITECT_PROMPT.md   →    omp.sh (day21/)    →     commit + tag dayN
   (размытое ТЗ)              отдельный чат DeepSeek     пункты плана             + документация дня
```

| Ступень | Что делаем | Инструмент |
|---|---|---|
| 1. Задание | Берём текст задания дня из челленджа как есть: цель, критерии, ограничения | — |
| 2. План | Прогоняем задание через шаблон [`ARCHITECT_PROMPT.md`](ARCHITECT_PROMPT.md) в **отдельном** чате с DeepSeek: получаем декомпозицию и DoD, пошаговый план, риски и план Б, проверки, команды фиксации | DeepSeek (вне omp) |
| 3. Исполнение | Передаём структурированный план в omp.sh как постановку дня. Агент работает в `day21/`, исполняет пункты плана и не пересказывает задание | omp.sh в папке `day21/` |
| 4. Фиксация | Чек-лист «Обязательное завершение дня» ([`day21/AGENTS.md`](day21/AGENTS.md)): тесты и `py_compile`, лимиты строк, **раздел в `docs/usage.md` с инструкцией запуска новой функциональности**, схема в `docs/architecture.md`, ссылка в `README.md`, отчёт в `docs/reports/`, проверка UI; затем коммит и тег | `git commit`, `git tag dayN` |

## Когда нужен архитектурный этап

**Нужен:** новые модули и слои, интеграции с внешними системами, изменения
архитектуры, работа с MCP (клиент, свой сервер, флот), планировщик, индексация,
оптимизация затрат.

**Не нужен:** правка кнопки или текста, обновление документации, мелкая правка в
существующем модуле.

## Почему план идёт отдельной ступенью

Размытое ТЗ даёт размытый Definition of Done, и агент начинает решать «похожую»
задачу вместо поставленной. Структурированный план фиксирует цель и критерии
**до** первой правки файлов, поэтому исполнение сводится к проверке пунктов плана,
а не к догадкам о том, что имелось в виду.

## Пример полного цикла

Задание: «ускорить тесты, которые идут слишком долго».

1. **Задание** — текст из челленджа, как есть.
2. **План** — через `ARCHITECT_PROMPT.md` в отдельном чате: получились шаги
   «диагностика → параллельный запуск → маркер медленных тестов → фикстуры →
   замер эффекта → документация», критерии (полный прогон быстрее, покрытие не
   падает) и риски (гонки на общей БД, потеря покрытия при «удалении дублей»).
3. **Исполнение** — агент в `day21/`: замер (`--durations`), `pytest-xdist`,
   session-scoped схема БД, маркер `slow`, отчёт
   [`day21/docs/reports/test_optimization.md`](day21/docs/reports/test_optimization.md).
4. **Фиксация** — тесты дня зелёные (быстрый прогон ~30 с, полный ~70 с при
   покрытии 96 %), документация обновлена, коммит
   `feat: add architect prompt, workflow, and optimize tests`, тег
   `day21-optimized`.

## Связанные правила

- [`AGENTS.md`](AGENTS.md) — короткие правила для агента (границы, тесты, git).
- [`RULES.md`](RULES.md) — sticky-правила, переприкрепляются к каждому запросу.
- [`docs/project-rules.md`](docs/project-rules.md) — архитектурные цели, раскладка
  слоёв, лимиты, история расхождений со снимками.
- `day21/AGENTS.md` и `day21/.omp/RULES.md` — правила конкретного дня (действуют
  в сессиях из `day21/`).
