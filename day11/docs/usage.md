# День 11 — установка и использование

Практическое руководство по приложению дня 11 «Трёхслойная модель памяти
агента». Задание дня — разложить память агента минимум на три типа, хранить их
раздельно и **явно** выбирать, что и куда сохраняется. Здесь: установка, запуск,
маршрутизация «действие → слой», две проверки из задания (какие данные попадают
в каждый слой и как слои влияют на ответы) и сценарий видео.

Устройство — в [architecture.md](architecture.md), контракты HTTP — в
[api.md](api.md), результат прогона по слоям — в
[memory_layers_comparison.md](../memory_layers_comparison.md).

Три слоя живут в трёх таблицах и различаются не только содержимым, но и ключом,
к которому привязаны: 👤 **краткосрочная** (`short_term_messages`, `session_id`)
— реплики текущего диалога, 🗂 **рабочая** (`working_memory`, `task_id` + `key`)
— данные активной задачи, 🧠 **долговременная** (`long_term_memory`, `category`
+ `key`) — профиль, предпочтения, решения, знания. Что и куда попадает — в §4.

## 1. Установка зависимостей

Нужен **Python 3.14+**. Все команды выполняются из папки `day11` в PowerShell.

```powershell
cd day11
python -m venv .venv
.venv/Scripts/python -m pip install --upgrade pip
.venv/Scripts/python -m pip install -r requirements.txt
```

Проверка, что все зависимости импортируются (одна команда, ничего не запускает):

```powershell
.venv/Scripts/python -c "import fastapi, uvicorn, streamlit, openai, requests, sqlalchemy, tiktoken, httpx, pytest, pandas; print('ok')"
```

Ожидаемый вывод — `ok`. Если какой-то пакет не найден, повторите
`pip install -r requirements.txt` (убедитесь, что активирован именно `.venv`).

## 2. Переменные окружения: ключ DeepSeek

Ключ DeepSeek нужен **только бэкенду**. Фронтенд ключ не читает — он общается с
бэкендом по HTTP, поэтому вводить ключ в интерфейсе нигде не нужно.

Порядок поиска ключа:

1. файл `day11/.env` (строка `DEEPSEEK_API_KEY=...`);
2. переменная окружения `DEEPSEEK_API_KEY`.

Создайте `.env` из шаблона и впишите свой ключ:

```powershell
copy .env.example .env
```

```dotenv
# day11/.env
DEEPSEEK_API_KEY=sk-ваш-ключ
```

Файл `day11/.env` не коммитится в git. Если ключа нет:

| Без ключа | Поведение |
|---|---|
| Создание/список/правка/удаление агентов и **все операции со слоями памяти** (`/memory/...`) | работают полностью |
| `POST /agents/{id}/generate` (реальный ответ модели) | `502` со `status: "error"` и понятным текстом вроде «Ключ API не задан…» |
| `POST /agents/{id}/compare` без `call_api` | работает: считаются только токены |

Дополнительно фронтенд понимает переменную `DAY11_BACKEND_URL` — адрес бэкенда,
по умолчанию `http://127.0.0.1:8000`. Менять её нужно, если бэкенд поднят на
другом порту:

```powershell
$env:DAY11_BACKEND_URL = "http://127.0.0.1:8019"
.venv/Scripts/python -m streamlit run app.py
```

## 3. Запуск

Нужны **два процесса**, оба запускаются из папки `day11`.

**Терминал 1 — бэкенд (FastAPI + uvicorn, порт 8000):**

```powershell
cd day11
.venv/Scripts/python -m uvicorn backend.main:app --port 8000
```

При старте бэкенд создаёт файл базы `day11/agents.db` (если его ещё нет) и
восемь таблиц: `agents`, `short_term_messages`, `working_memory`,
`long_term_memory`, `summaries`, `token_usage`, `facts`, `checkpoints`. Слои
памяти, диалог, факты, ветки и метрики переживают перезапуск (активные сессия и
задача лежат в строке `agents`). Swagger — на `http://127.0.0.1:8000/docs`.

**Терминал 2 — интерфейс (Streamlit, порт 8501 по умолчанию):**

```powershell
cd day11
.venv/Scripts/python -m streamlit run app.py
```

Откройте адрес, который Streamlit напечатал в консоли (обычно
`http://localhost:8501`). В сайдбаре должно появиться
«🟢 Бэкенд: http://127.0.0.1:8000 · агентов: N».

Проверка бэкенда из третьего терминала:

```powershell
curl.exe http://127.0.0.1:8000/
```

> [!] В Windows PowerShell `curl` — это алиас командлета `Invoke-WebRequest`, и
> привычные флаги (`-X`, `-H`, `-d`) у него означают другое. Примеры в этой
> документации используют **`curl.exe`** — вызывайте именно его либо работайте в
> bash-подобной оболочке (Git Bash, WSL).

`GET /` вернёт список эндпоинтов — это подтверждает, что API живой.

### Порядок блоков в основной области

Сверху вниз идёт: **карточка агента** (имя, `agent_id`, модель, температура,
`max_tokens`, стратегия и `window_size`; рядом — «🗑 Удалить агента») → **панель
текущей стратегии** (только одна: «🗜 Сжатие контекста» при `summary`, «📌 Факты»
при `sticky_facts`, «🌿 Ветвление истории» при `branching`) → **«📊 Токены
диалога»** → **«🧠 Слои памяти агента»** (три вкладки, §5.2–§5.4) → **«🧭 Что ушло
в последний запрос»** (§5.6) → разделитель, кнопка «🎬 Прогнать сценарий дня 11»
и панель «📋 Итог сценария дня 11» (§5.8) → **«💬 Диалог»** → expander «⚖️ Сравнить
режимы» → форма отправки
(поле «Сообщение агенту» + кнопка «🚀 Отправить»), отдельной строкой под ней —
кнопка «🧹 Очистить историю». Сайдбар: создание агента, «⚙️ Стратегия
контекста», «🗂 Задача и сессия».

То есть панели слоёв и индикатор стоят **выше** диалога и поля ввода, а не под
ними.

## 4. Модель памяти: что и куда сохраняется

### 4.1 Три слоя: таблица, ключ, жизненный цикл

| Слой | Таблица | Ключ | Что хранит | Когда очищается |
|---|---|---|---|---|
| 👤 Краткосрочная | `short_term_messages` | `session_id` | реплики текущего диалога (роль + текст + время) | `new_session()`, `DELETE /agents/{id}/memory/short-term`, `DELETE /agents/{id}/history` |
| 🗂 Рабочая | `working_memory` | `task_id` + `key` | данные активной задачи: цель, ограничения, решения, критерии | вручную (перезапись ключа) или сменой задачи; новая сессия её не трогает |
| 🧠 Долговременная | `long_term_memory` | `category` + `key` | профиль, устойчивые предпочтения, важные решения, знания | только вручную: `DELETE /agents/{id}/memory/long-term/{entry_id}` |

Активные `session_id` и `task_id` агента хранит строка `agents`
(`current_session_id` / `current_task_id`) — поэтому после перезапуска бэкенда
диалог продолжается в той же сессии, а рабочая память — в той же задаче.

### 4.2 Правило маршрутизации: действие → слой

Это и есть ответ на «вы явно выбираете, что и куда сохраняется»: ни одна запись
не попадает в рабочую или долговременную память «сама».

| Действие | Слой | Что происходит |
|---|---|---|
| Ход диалога (`POST /agents/{id}/generate`) | краткосрочная | после успешного ответа сохраняется пара реплик `user` + `assistant` текущей сессии |
| Форма вкладки «🗂 Рабочая» (`POST /memory/working`) | рабочая | upsert по `task_id` + `key`: повторный ключ перезаписывает значение |
| `POST /memory/working` с `task_id` в теле | рабочая | запись уходит в **указанную** задачу, не обязательно в активную |
| Форма вкладки «🧠 Долговременная» (`POST /memory/long-term`) | долговременная | upsert по `category` + `key`, с уверенностью 0…1 |
| `POST /memory/session` («🆕 Новая сессия») | краткосрочная | реплики прошлой сессии (плюс конспекты `summaries` и факты `facts`) удаляются; рабочая и долговременная память остаются |
| `PUT /memory/task` («🔀 Переключить задачу») | рабочая | меняется активная задача: в контекст идут записи только новой задачи; диалог и краткосрочный слой не трогаются |

**Автоматического извлечения профиля и предпочтений LLM нет.** Рабочая и
долговременная память наполняются только решением пользователя — через формы
вкладок или соответствующие `POST`-запросы (что видно в §6, шаги 1 и 3).

### 4.3 Что именно уходит в контекст

| Слой | Как попадает в запрос |
|---|---|
| 🗂 Рабочая | **все** записи активной задачи, блоком «Рабочая память (данные текущей задачи, используй как опорные; при противоречии важнее свежая реплика):» |
| 🧠 Долговременная | до `LONG_TERM_LIMIT = 5` записей: сначала совпавшие по ключевым словам запроса или по упоминанию категории, затем добор самыми уверенными; блок «Долговременная память (профиль, предпочтения, решения, знания — устойчивые данные о пользователе):» |
| 👤 Краткосрочная | по наследованной из дня 10 стратегии: последние `window_size` реплик, последние `keep_last_messages` непокрытых конспектом или вся история активной ветки |

Порядок блоков системного сообщения: `system_prompt` → рабочая память →
долговременная память → конспект (если есть) → факты (только `sticky_facts`).
Все блоки вкладываются в **одно** системное сообщение: если ни один блок не
заполнен, отдельного system-сообщения в запросе нет вовсе.

## 5. Работа со слоями в интерфейсе

### 5.1 Создать агента и задачу

Создание агента — в сайдбаре, блок **«➕ Новый агент»** (форма
`create_agent_form`, очищается после отправки): «Имя агента», «Модель»,
«Температура», «Системный промпт (роль)», «max_tokens», «Сжимать историю в
конспект», «Последних реплик «как есть»», «Сжимать каждые N новых реплик» →
кнопка «Создать агента». Новый агент сразу становится активным; в сайдбаре
появляется строка вида `Конспектёр · deepseek-chat · 0 сообщений · 🗜 сжатие`.

Задача нужна рабочей памяти. В сайдбаре, в блоке «🗂 Задача и сессия», введите
идентификатор в поле **«Новая задача (task_id)»** (например, `tz-portal`) и
нажмите **«➕ Создать задачу»** — задача станет активной с нулём записей.
Идентификатор по умолчанию — `default`.

### 5.2 Вкладка «👤 Краткосрочная»

* Подзаголовок — **«👤 Краткосрочная память (текущая сессия)»**.
* Подпись: `Сессия **session_id** · реплик: **N** · слой очищается кнопкой
  «🆕 Новая сессия» и командой ниже.`
* Таблица — **«роль / текст / создано»** (текст обрезан до 200 символов).
* Кнопка **«🧹 Очистить краткосрочную память»** (`DELETE /memory/short-term`)
  удаляет реплики текущей сессии; рабочая и долговременная память не
  затрагиваются. Пустой слой показывает подсказку, что реплики появятся после
  первого сообщения.

### 5.3 Вкладка «🗂 Рабочая»

* Подзаголовок — **«🗂 Рабочая память (текущая задача)»**.
* Подпись: `Задача **task_id** · записей: **N** · слой переживает смену сессии и
  очищается только вручную (или сменой задачи).`
* Форма **«Добавить/обновить запись»** (ввод существующего ключа перезапишет
  значение — upsert): поля **«Ключ»** (placeholder «например: цель») и
  **«Значение»**, кнопка **«💾 Сохранить»** → `POST /memory/working`.
* Таблица — **«ключ / значение / обновлено»**.

Держите записи короткими и по делу: они уходят в **каждый** запрос задачи.

### 5.4 Вкладка «🧠 Долговременная»

* Подзаголовок — **«🧠 Долговременная память (между сессиями)»**, подпись про
  устойчивые данные о пользователе.
* Селектор **«Фильтр по категории»**: «все категории» плюс `👤 профиль`,
  `⭐ предпочтение`, `✅ решение`, `📚 знание` — фильтрует и таблицу, и селектор
  удаления.
* Форма **«Добавить/обновить запись»** (upsert по категории и ключу):
  **«Категория»**, **«Ключ»** (placeholder «например: язык_интерфейса»),
  **«Значение»** и слайдер **«Уверенность»** (0.0–1.0, шаг 0.05, по умолчанию
  1.0). Кнопка **«💾 Сохранить»** → `POST /memory/long-term`.
* Таблица — **«id / категория / ключ / значение / уверенность»**.
* Удаление: селектор **«Удалить запись по id»** + кнопка **«🗑 Удалить»**
  (`DELETE /memory/long-term/{entry_id}`); если записи нет, бэкенд отвечает
  `404`.

### 5.5 Задача и сессия (сайдбар, блок «🗂 Задача и сессия»)

* Подпись: `Сессия: **session_id** · задача: **task_id**`.
* Селектор **«Активная задача»** + кнопка **«🔀 Переключить задачу»**
  (`PUT /memory/task`): в следующих запросах фильтруется рабочая память; диалог
  и краткосрочный слой не меняются. Список задач наполняется из
  `GET /memory/working` (`tasks`).
* Поле **«Новая задача (task_id)»** + кнопка **«➕ Создать задачу»** — то же
  переключение, но на новый идентификатор.
* Кнопка **«🆕 Новая сессия»** (`POST /memory/session`): реплики прошлой сессии,
  конспекты и факты удаляются, у агента появляется новый `session_id`. **Рабочая
  и долговременная память сохраняются** — это и показывает §7.

### 5.6 Индикатор «🧭 Что ушло в последний запрос»

Заголовок **«🧭 Что ушло в последний запрос»**, сразу под панелями слоёв, читает
`record["memory"]` последнего **успешного** ответа `POST /generate`:

* три метрики — **«👤 Краткосрочная»**, **«🗂 Рабочая»**, **«🧠 Долговременная»**
  — со значением «N записей · M токенов»; подсказка метрики содержит подробности
  слоя (`details`);
* подпись: `Сессия **session_id** · задача **task_id** · всего по слоям:
  **total_tokens** токенов (короткая X + рабочая Y + долговременная Z)`;
* строка **«Использованы в запросе: …»** — только те слои, у которых
  `used = true`;
* строка **«Ключевые слова запроса (отбор долговременных записей): …»**.

До первого сообщения (и сразу после «🆕 Новая сессия») блок пишет: «Слои памяти:
индикация появится после первого сообщения». Токены самого нового промпта не
принадлежат слоям — реплика становится памятью только после успешного хода,
поэтому в **первой** реплике новой сессии краткосрочный слой даёт `0` токенов
(рабочая и долговременная при этом уже на месте).

Источник полей — `record["memory"]` ответа `POST /agents/{id}/generate`:
`session_id`, `task_id`, `layers[{layer, used, entries, tokens, details}]`,
`short_term_tokens` / `working_tokens` / `long_term_tokens` / `total_tokens`,
`keywords`.

### 5.7 Первый диалог: что ввести и что ожидать

Диалог — в самом низу страницы: заголовок **«💬 Диалог»**, под ним поле
**«Сообщение агенту»** и кнопка **«🚀 Отправить»** (отдельной строкой ниже —
**«🧹 Очистить историю»**). Пока агент не создан, полей нет вовсе.

1. Создайте агента (§5.1) — поле ввода появляется сразу, никаких
   дополнительных шагов не нужно.
2. Введите первую реплику, например:
   `Привет! Начинаем собирать требования к корпоративному порталу.`
3. Нажмите **«🚀 Отправить»** (в поле работает и Ctrl+Enter) — текст уходит как
   есть, терять фокус полю не нужно.
4. Что ожидать:
   * под полем появляется плашка `Ответ получен за N с · токены … · стоимость
     … · finish_reason … · слои: короткая 0 / рабочая 0 / долговременная 0
     токенов`;
   * в «💬 Диалог» добавляется пара `🧑 Вы` / `🤖 Ассистент` с временем;
   * в «🧭 Что ушло в последний запрос» появляются три метрики по слоям.

На **первой** реплике сессии краткосрочный слой даёт `0 записей · 0 токенов`
(сам новый промпт в слой ещё не входит) — это ожидаемо, а не ошибка. Со второй
реплики там `2 записи`, дальше `4`, `6` и так до `keep_last_messages` (по
умолчанию `6`). Рабочая и долговременная метрики показывают записи, сохранённые
формами вкладок: если ничего не сохраняли — там `0 записей · 0 токенов`.

Если нажать «🚀 Отправить» с пустым полем, ничего не отправляется и появляется
подпись «Пустое сообщение не отправлено: введите текст.»

### 5.8 Кнопка «🎬 Прогнать сценарий дня 11»

Одно нажатие вместо ручного наполнения слоёв и 12 реплик вручную: тот же маршрут,
что в офлайн-скрипте `memory_layers_demo.py`, но через HTTP-API и с живыми
ответами DeepSeek (нужен ключ, §2). Кнопка стоит между индикатором слоёв и
диалогом, под `help`-подсказкой.

Что делает по шагам:

1. ставит агенту активную задачу `tz-portal` (`PUT /agents/{id}/memory/task`);
2. пишет **6 записей рабочей памяти** задачи `tz-portal`: `цель`
   (`Корпоративный портал`), `стек` (`Python 3.14 + FastAPI`), `срок`
   (`3 месяца`), `бюджет` (`5000 долларов`), `ограничение`
   (`только on-premise`), `критерий_приёмки` (`pytest, покрытие не ниже 80%`);
3. пишет **4 записи долговременной памяти**: `profile / роль_пользователя`
   (`аналитик`, 0.9), `knowledge / стек_команды` (`Python 3.14 + FastAPI`, 0.7),
   `decision / бд` (`PostgreSQL`, 0.8), `preference / язык_интерфейса`
   (`русский`, 0.95);
4. отправляет **12 реплик** «собираем ТЗ» (`Название проекта: …` …
   `Тестирование: pytest с покрытием не ниже 80%`), по одному `POST /generate`
   на реплику; под прогрессбаром видно, сколько записей/токенов ушло из каждого
   слоя на этом ходу;
5. в конце вызывает `POST /agents/{id}/memory/session` — «Новая сессия».

Ожидаемый итог (числа записей — из отчёта
[`memory_layers_comparison.md`](../memory_layers_comparison.md); ниже — прогон на
агенте, в сессии которого ещё нет реплик):

* краткосрочная `24 → 0` (удалено 24 реплики), рабочая `6 → 6`,
  долговременная `4 → 4`, задача остаётся `tz-portal`;
* плашка `Сценарий дня 11 пройден: краткосрочная 24 → 0 (удалено 24), рабочая
  6 → 6, долговременная 4 → 4.`

Число записей каждого шага на свежем агенте совпадает с таблицей отчёта один в
один, а токены короткосрочного слоя в живом прогоне больше: в слой входят
фактические ответы DeepSeek, тогда как отчёт снят офлайн на фейковом клиенте с
короткими заглушками.

Где смотреть результат:

* панель **«📋 Итог сценария дня 11»** — сессия `до → после`, счётчики слоёв и
  таблица 12 строк (шаг · реплика · маршрутизация · значения слоёв
  «записей/токенов»);
* вкладки «🧠 Слои памяти агента»: «👤 Краткосрочная» — 0 реплик, «🗂 Рабочая» —
  6 записей задачи `tz-portal`, «🧠 Долговременная» — 4 записи;
* «💬 Диалог» — пусто, «🧭 Что ушло в последний запрос» — подсказка «индикация
  появится после первого сообщения» (новая сессия сбросила и диалог, и индикатор).

Предупреждения:

* сценарий завершается новой сессией, поэтому диалог агента обнуляется — это и
  есть демонстрация жизненного цикла слоёв; для чистого прогона создайте
  отдельного агента (§5.1);
* одноимённые ключи задачи и категории долговременной памяти перезаписываются
  (upsert), а не дублируются;
* повторный прогон на том же агенте даёт тот же итог (`краткосрочная → 0`,
  рабочая — 6 записей, долговременная — 4): записи устойчивых слоёв
  перезаписываются по ключу, дублей нет. Счётчик краткосрочного слоя при этом
  будет больше 24, если в текущей сессии уже был диалог: сценарий удаляет и его
  реплики тоже (например, 2 реплики чата + 24 реплики сценария = `28 → 0`);
* если нажать кнопку и уйти со страницы, прогон прервётся — сессия при этом не
  начнётся (кнопка «🆕 Новая сессия» в сайдбаре для этого и остаётся).

Это быстрый путь к доказательствам §6 и §7 на живом API.

## 7. Проверка 2: как слои влияют на ответы

Здесь нужен ключ DeepSeek (§2) — сравнение идёт по смыслу ответа. Числа из
`record["memory"]` детерминированы и проверяются всегда, формулировка модели
свободная: сверяйте смысл, а не строку.

### 7.1 Долговременная память

Начинайте на свежем агенте, чтобы числа слоёв были однозначны.

| Шаг | Действие | Что должно быть в индикаторе | Что в ответе |
|---|---|---|---|
| а | задать вопрос «На каком языке должен быть интерфейс портала?» | «🧠 Долговременная» — `0 записей · 0 токенов` | модель ничего не знает о предпочтении (уточняет или отвечает обобщённо) |
| б | сохранить `preference / язык_интерфейса: русский` и задать тот же вопрос | «🧠 Долговременная» — `1 запись` (и токены > 0) | ответ учитывает русский язык интерфейса |
| в | нажать «🆕 Новая сессия» и задать тот же вопрос | краткосрочная `0` токенов, долговременная — по-прежнему `1 запись` | предпочтение снова учтено, хотя диалог пуст |

Примеры фактических ответов (формулировка свободная, сверяйте смысл): (а) общий
ответ про аудиторию портала, без упоминания русского; (б) «Судя по вашему
профилю — язык интерфейса: **русский**»; (в) «Интерфейс портала должен быть на
русском языке.»

Шаг «в» — главное доказательство: сессии сменились, диалога нет, а ответ
по-прежнему опирается на долговременный слой.

### 7.2 Рабочая память

| Шаг | Действие | Что должно быть в индикаторе | Что в ответе |
|---|---|---|---|
| а | в задаче `tz-portal` сохранить `ограничение: только on-premise`, спросить «Можно ли разместить в облаке?» | «🗂 Рабочая» — `1 запись` | ответ учитывает ограничение (облако не подходит: «у вас зафиксировано ограничение — только on-premise») |
| б | нажать «🆕 Новая сессия», переключиться на задачу `tz-cloud` (§5.5) и задать тот же вопрос | «🗂 Рабочая» — `0 записей · 0 токенов`, краткосрочная — `0` токенов | ограничение не упоминается — оно принадлежит другой задаче, а диалог пуст |
| в | нажать «🆕 Новая сессия», вернуться на `tz-portal` и задать тот же вопрос | «🗂 Рабочая» — `1 запись` | ограничение снова в ответе |

Примеры фактических ответов: (а) «Нет, нельзя. Есть ограничение: только
on-premise.»; (б) общий ответ про размещение в облаке, ограничение не
упомянуто; (в) «Нет. У вас зафиксировано ограничение — только on-premise.»

Так видно, что рабочая память привязана к `task_id`, а не к диалогу: сам диалог
при переключении задачи не теряется.

> [i] Шаги «🆕 Новая сессия» в (б) и (в) обязательны. В той же сессии
> предыдущий ответ про on-premise остаётся в **краткосрочном** слое, и модель
> цитирует ограничение из диалога — тогда опыт доказывает работу диалога, а не
> рабочей памяти. С пустой сессией единственный источник ограничения — записи
> задачи, и разница между `tz-portal` и `tz-cloud` видна однозначно.

## 11. FAQ и возможные проблемы

Сначала — вопросы про слои памяти.

| Проблема | Решение |
|---|---|
| После «🆕 Новая сессия» диалога нет, но рабочая и долговременная память на месте | Так и задумано: сессия — это границы краткосрочной памяти. `POST /memory/session` удаляет реплики прошлой сессии, конспекты и факты, а рабочая (по `task_id`) и долговременная (профиль/предпочтения/решения/знания) память к диалогу не привязаны. Индикатор после новой сессии показывает `0` записей в краткосрочном слое и прежние числа в двух других. |
| После новой сессии пропал конспект старого диалога — почему? | Конспект (`summaries`) — сжатие **краткосрочного** слоя, то есть производное от конкретного диалога. Если оставить его при смене сессии, устаревшее содержание продолжало бы подставляться в системное сообщение. Факты (`facts`) удаляются по той же причине. Если данные нужно сохранить между сессиями, перенесите их в долговременную память (категория `knowledge` или `preference`) — автоматического переноса нет. |
| Запись рабочей памяти «не сохранилась», а значение изменилось | Это upsert: пара «задача + ключ» уникальна, поэтому повторное сохранение того же ключа перезаписывает значение. Хотите две записи — используйте разные ключи (`цель` и `критерий_приёмки`). |
| Переключил задачу — рабочая память «опустела» | Записи привязаны к `task_id`, поэтому у новой задачи свой набор. Вернитесь к прежней задаче селектором «🔀 Переключить задачу» — записи на месте. Диалог при переключении не теряется. |
| Записей в долговременной памяти больше, чем видно в контексте | В запрос уходит до 5 записей (`LONG_TERM_LIMIT`): сначала совпавшие по ключевым словам запроса (и по упоминанию категории), затем самые уверенные. Поднять лимит — правка `LONG_TERM_LIMIT` в `backend/config.py`. |
| `422` при сохранении долговременной записи | Проверьте: категория — только `profile` / `preference` / `decision` / `knowledge`, `confidence` — от 0 до 1, ключ и значение непустые. |
| Записал в рабочую память, а индикатор показывает `0 записей` | Проверьте активную задачу (§5.5): запись ушла в другую задачу, либо это первая реплика сессии — в ней краткосрочный слой всегда `0` токенов, а рабочая метрика появится только после успешного хода. |

Общие вопросы:

| Проблема | Решение |
|---|---|
| «🔌 Бэкенд недоступен» в интерфейсе | Запустите бэкенд из папки `day11`: `.venv/Scripts/python -m uvicorn backend.main:app --port 8000`. Проверьте адрес: он должен совпадать с `DAY11_BACKEND_URL` (по умолчанию `http://127.0.0.1:8000`). |
| Порт 8000 (или 8501) занят | Запустите на другом порту: `uvicorn backend.main:app --port 8019` и, для фронтенда, задайте `$env:DAY11_BACKEND_URL="http://127.0.0.1:8019"`; Streamlit — `--server.port 8502`. |
| Генерация вернула `502` «Ключ API не задан» | Ключа нет ни в `day11/.env`, ни в переменной `DEEPSEEK_API_KEY`. Сделайте `copy .env.example .env` и впишите `DEEPSEEK_API_KEY=sk-...`, затем перезапустите бэкенд. Слои памяти и CRUD работают и без ключа. |
| Ошибка `429` (rate limit) от DeepSeek | Слишком много запросов подряд. Подождите и повторите; для демонстрации делайте паузы между ходами. Сравнение с галочкой «Вызвать DeepSeek дважды» тратит два запроса сразу. |
| `404` на агента | Агент был удалён или `agent_id` указан неверно. Обновите список кнопкой «🔄 Обновить список» и выберите агента заново. |
| `404` при удалении долговременной записи | Записи с таким `id` уже нет (например, её удалили в другой вкладке). Обновите страницу — селектор «Удалить запись по id» перечитает список. |
| `422` при создании/правке агента | Проверьте значения: `temperature` 0.0–2.0, `max_tokens` 1–8192, `keep_last_messages` 2–20, `summarize_every` 2–40. Такой ответ означает ошибку валидации тела запроса. |
| `agents.db` попал в git | Не должен: файлы `*.db` игнорируются. Если он уже отслеживается, уберите из индекса (`git rm --cached day11/agents.db`) — файл останется на диске. |
| Как сбросить эксперимент | «🧹 Очистить историю» удаляет реплики, конспекты, факты, ветки и метрики, сохраняя конфигурацию агента, рабочую и долговременную память. Полный сброс — «🗑 Удалить агента» и создать заново; можно также остановить бэкенд и удалить `day11/agents.db` (таблицы создадутся заново). |

Вопросы по наследованным панелям дня 9–10:

| Проблема | Решение |
|---|---|
| Кнопка «Сжать сейчас» отвечает «Сжимать пока нечего» | Это нормально: непокрытых реплик меньше порога `summarize_every`, либо истории нет вовсе. Наберите диалог или уменьшите порог. Отчёт приходит с `created: false` и текстом причины. |
| «Чистая экономия» отрицательная | Конспект оказался дороже заменённых реплик — типично для коротких сообщений. Экономия контекста есть, но на сам конспект ушло больше токенов. Увеличьте `summarize_every` и/или `keep_last`, либо пишите более длинные реплики. |
| Где посмотреть состояние FSM сжатия | В панели «🗜 Сжатие контекста» — подпись «Состояние процесса: …» (`tracking`, `summary_pending`, `summarizing`, `error`). В БД оно не хранится: выводится из watermark, числа непокрытых реплик и порога. Подробнее — [`../../day10/docs/usage.md`](../../day10/docs/usage.md). |
| Оценки tiktoken не совпадают с `usage` API | Это ожидаемо: tiktoken (`cl100k_base`) — приблизительная оценка, у DeepSeek свой токенизатор. Для конкретного запроса/ответа верьте фактическим `usage` из API; на tiktoken построены расчёты контекста, экономии и разбивка по слоям. |
