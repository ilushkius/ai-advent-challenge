# День 9 — Агент со сжатием истории (FastAPI + Streamlit + SQLite + tiktoken)

Приложение развивает день 8: агент по-прежнему ведёт **полный диалог с памятью**
(SQLite, история переживает рестарт), но теперь **в запрос уходит не вся история**.
Последние N реплик отправляются «как есть», а всё, что старше, заменяется
**конспектом** (таблица `summaries`) — например, каждые 10 новых реплик. Полная
история при этом сохраняется: сжатие уменьшает запрос, а не хранилище.

День 9 — первый день проекта с настоящими автотестами (`pytest`, 167 тестов) и
первой явной стейт-машиной (`Enum` + паттерн State), как требует `AGENTS.md`.

## Архитектура

```
Streamlit (порт 8501) ── HTTP (requests) ──► FastAPI (порт 8000) ──► DeepSeek API
   панели сжатия и токенов,                    │                      https://api.deepseek.com
   сравнение режимов                           ▼
                                    AgentManager (синглтон)
                                      └─ Agent × N
                                         ├─ self.messages (полная история в памяти)
                                         ├─ подсчёт токенов (tiktoken)
                                         ├─ ContextMachine (Enum + State)
                                         └─ ContextCompressor ──► вызов суммаризации
                                              │
                                              ▼
                                    SQLAlchemy → SQLite (day9/agents.db)
                                    таблицы: agents     (конфигурация + настройки сжатия)
                                             messages   (ПОЛНАЯ история, не удаляется)
                                             summaries  (конспекты, append-only, watermark)
                                             token_usage (метрики хода + экономия)
```

Что уходит в DeepSeek при включённом сжатии:

```
[system: роль + "Конспект предыдущей части диалога …"]
+ последние N непокрытых реплик (как есть)
+ новое сообщение пользователя
```

Поток одного сообщения: **пользователь → сборка двух payload (полный и сжатый) →
аварийная обрезка при переполнении → API → метрики экономии в БД → сжатие после
хода (FSM) → ответ** (детали — [docs/architecture.md](docs/architecture.md)).

## Возможности

- **Сжатие истории**: последние `keep_last_messages` реплик уходят дословно,
  остальные заменяются конспектом, который обновляется каждые
  `summarize_every` новых реплик. Конспект хранится отдельно (`summaries`) и
  подставляется в запрос вместо старой истории.
- **Полная история не теряется**: таблица `messages` не очищается, сжатие влияет
  только на то, что уходит в модель; API `GET /history` помечает покрытые реплики
  флагом `summarized`.
- **Стейт-машина**: IDLE → TRACKING → SUMMARY_PENDING → SUMMARIZING →
  TRACKING/ERROR; неизвестное событие — явная ошибка, состояние выводится из БД.
- **Экономика токенов**: `saved_tokens` (полная история против отправленной) и
  `net_saved_tokens` (за вычетом стоимости вызовов суммаризации), таблица
  `token_usage` расширена полями режима и экономии.
- **Сравнение режимов**: `POST /agents/{id}/compare` и блок «⚖️ Сравнить режимы»
  считают токены двух вариантов (и, по желанию, отправляют два реальных запроса),
  не изменяя историю.
- **Управление на живом агенте**: `PATCH /agents/{id}` и кнопки в интерфейсе
  переключают сжатие без потери диалога.
- **Аварийный предохранитель**: если даже сжатый запрос не влезает в лимит,
  самые старые реплики не отправляются в этом запросе (`trimmed_messages`), но
  остаются в БД и попадут в следующий конспект.
- Ошибки без traceback, при сбое генерации история не портится, UI жив при
  недоступном бэкенде (паттерн дней 6–8).

## Ограничения

- Один процесс бэкенда и один файл `day9/agents.db` (в `.gitignore` по `*.db`).
- Оценки tiktoken (`cl100k_base`) приблизительны: DeepSeek использует свой
  токенизатор; для запроса/ответа приоритет — фактические `usage` API.
- Лимиты контекста 8K/32K демонстрационные (как в задании дня 8); реальный
  контекст DeepSeek шире. Правка — `MODEL_TOKEN_LIMITS` в `backend/config.py`.
- Суммаризация всегда идёт на `deepseek-chat` (temperature 0.2): `deepseek-reasoner`
  может игнорировать `temperature` и дороже для задачи извлечения фактов.
- При очень коротких репликах конспект может оказаться дороже заменяемых
  сообщений — чистая экономия станет отрицательной. Пороги `keep_last_messages`
  и `summarize_every` подбираются под длину сообщений.
