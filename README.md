# AI-челлендж

## О проекте

Персональный практикум по LLM и промпт-инжинирингу на реальных API: **DeepSeek**
(OpenAI-совместимый endpoint), **Hugging Face** и **локальная модель на Ollama**
(второй провайдер рядом с облаком — на этой машине или удалённо в Google Colab).
Челлендж рассчитан на 35 дней; сейчас пройден **день 35**. В `day21/` к этому дню
собрана агентная система — агент с трёхслойной памятью и профилем пользователя,
состояние задачи как конечный автомат (FSM), инварианты, MCP-клиент и флот
MCP-серверов, планировщик фоновых задач, декларативные пайплайны и оркестрация, —
и поверх неё подсистемы дней 21–35:

- **день 21** — индексация документов (две стратегии чанкинга, FAISS + SQLite) и
  оптимизация затрат на LLM (кэш контекста, PromptBuilder, сжатие промпта, непиковые
  часы, выбор модели);
- **день 22–24** — RAG по корпусу документов: ответ по фрагментам и сравнение с
  ответом без RAG, второй этап отбора (переформулировка запроса моделью,
  реранкер-кросс-энкодер, порог отсечения), обязательные источники и цитаты с режимом
  «не знаю» при слабом контексте;
- **день 25, 26, 28, 29** — отдельный мини-чат с RAG и памятью задачи, локальная LLM
  как второй провайдер ответа (переключатель в интерфейсе, HTTP к Ollama), локальный RAG
  бок о бок с облачным, профили настройки локальной модели и сравнение квантов;
- **день 30** — та же Ollama, но не на этой машине: сервис в Google Colab за туннелем
  Cloudflare, программа ходит на выданный адрес по HTTP (формат OpenAI), прогон —
  одной кнопкой;
- **день 31** — **ассистент разработчика**: `/help <вопрос>` отвечает по документации
  проекта (RAG-индекс) и по состоянию репозитория через свой MCP-сервер `dev_server`
  (ветка, коммит, diff, структура);
- **день 32** — **автоматическое AI-ревью PR**: diff двух ref через MCP или реального
  GitHub PR по URL и номеру, RAG-контекст документации и кода изменённых файлов,
  структурированное ревью с приоритетами `P0`–`P3`, GitHub Action и публикация ревью
  комментарием в PR;
- **день 33** — **ассистент поддержки пользователей**: ответ клиенту по FAQ и
  документации поддержки (RAG) с контекстом его профиля и тикета из своего MCP-сервера
  `support_server`, раздел интерфейса с селекторами клиента и тикета, демо из пяти
  сценариев и отчёт;
- **день 34** — **ассистент файлов**: цель вместо команды («найди», «обнови»,
  «сгенерируй ADR») превращается в план шагов, а шаги выполняет свой MCP-сервер
  `file_server` (чтение, поиск, запись и правка файлов папки дня), с режимом `dry_run`,
  журналом шагов и предполагаемым diff-ом;
- **день 35** — **AI-ассистент релиза**: коммиты диапазона тегов через пять
  инструментов git-истории того же сервера, версия по SemVer (тип изменения предлагает
  модель, число считается от шапки `CHANGELOG.md`), раздел CHANGELOG и заметки о
  релизе, проверки готовности (тесты и покрытие подпроцессами) и запись трёх файлов —
  раздел CHANGELOG, `day21/docs/RELEASE_NOTES.md` и раздел результата в этом README.

Проект ведётся вместе с терминальным агентом **omp.sh**.

## Результат 35-дневного челленджа

Челлендж завершён релизом **1.1.0** (2026-10-16): тридцать пять дней практикума по LLM сведены в одну агентную систему.

**Что построено:** память агента и FSM состояния задачи с инвариантами; MCP-клиент и флот серверов; планировщик фоновых задач; декларативные пайплайны и оркестрация нескольких серверов; индексация корпуса документов (FAISS) и RAG со ссылками на источники; мини-чат по корпусу; локальная и удалённая LLM как второй провайдер; ассистенты — разработчика, ревью кода, поддержки пользователей, файлов и подготовки релиза.

**Стек:** Python 3.14, FastAPI, Streamlit, SQLAlchemy + SQLite, FAISS, sentence-transformers, MCP SDK (stdio), DeepSeek API, Ollama, pytest.

**Метрики:** 14 тегов, 70 коммитов, 579 файлов .py, 1797 тестов, 7 MCP-серверов, 5 ассистентов

Полная история — [`CHANGELOG.md`](CHANGELOG.md), заметки о релизе — [`day21/docs/RELEASE_NOTES.md`](day21/docs/RELEASE_NOTES.md).

**Главное правило проекта:** разработка идёт в **одной** папке `day21/`, новые
папки `dayN` не создаются, а история версий фиксируется **git-коммитами и
тегами** (`day22`…`day35` по дням челленджа и `v1.1.0` — релиз, собранный
ассистентом дня 35). Поэтому ссылки вида
`day21/...` стабильны.

## Быстрый старт

Все команды — из папки дня (`day21/`), потому что приложение ищет `.env`
в текущей рабочей директории.

```bash
cd day21
uv sync                                   # зависимости из pyproject.toml + uv.lock
copy .env.example .env                    # затем впишите DEEPSEEK_API_KEY=sk-...

uv run uvicorn backend.api.main:app --port 8000   # терминал 1 — бэкенд
uv run streamlit run app.py                       # терминал 2 — интерфейс (localhost:8501)
uv run streamlit run mini_chat/app.py --server.port 8502  # отдельный мини-чат (день 25)

# Ассистент разработчика (день 31): индекс с документацией проекта, затем пять вопросов /help
uv run python scripts/reindex_with_docs.py
uv run python scripts/demo_dev_assistant.py

# AI-ревью PR (день 32): локальные ref-ы или реальный PR через GitHub REST API
uv run python scripts/run_local_pr_review.py --base day30 --head day31
uv run python scripts/run_github_pr_review.py \
  --repo-url https://github.com/fastapi/fastapi --pr-number 16481
#   --post-comment публикует ревью комментарием в PR — нужен GITHUB_TOKEN
#   с правом pull requests: write (переменная окружения или GITHUB_TOKEN в day21/.env)

# Ассистент поддержки (день 33): индекс с документацией поддержки, затем пять сценариев
uv run python scripts/reindex_with_support.py
uv run python scripts/demo_support.py

# Ассистент файлов (день 34): цель вместо команды — план шагов и правка файлов day21/
uv run python scripts/demo_file_assistant.py --dry-run --no-report   # репетиция без правок
uv run python scripts/demo_file_assistant.py                         # реальный прогон + отчёт

# Подготовка релиза (день 35): версия, CHANGELOG, заметки, проверки готовности
uv run python scripts/demo_release.py                # предпросмотр + проверки + отчёт
uv run python scripts/demo_release.py --no-checks    # быстро, без двух прогонов pytest
uv run python scripts/demo_release.py --no-dry-run   # ЗАПИСАТЬ CHANGELOG, README и заметки
uv run python scripts/compare_changelog.py           # ручные формулировки против модели

# Локальная LLM (дни 26, 28, 29) — необязательна: без Ollama приложение работает
# на DeepSeek, а локальная модель включается переключателем «🤖 Провайдер LLM».
winget install --id Ollama.Ollama -e        # служба на http://localhost:11434
ollama pull qwen2.5-coder:14b               # 9.0 GB — корзина «8–12 GB VRAM»
uv run python scripts/demo_local_llm.py     # три запроса из программы (факт/логика/код)

# Удалённая LLM (день 30) — та же Ollama в Google Colab (GPU T4) за туннелем Cloudflare:
# ячейка `uvx collab-ollama --model qwen2.5-coder:7b` печатает Base URL, затем
uv run python scripts/demo_remote_llm.py --url https://xxxx.trycloudflare.com/v1

uv run pytest -m "not slow"    # быстрый прогон тестов при разработке (~30 с)
uv run pytest                  # то же самое: -m "not slow" уже стоит в pytest.ini
uv run pytest -m ""            # полный прогон, все тесты (~70 с)
```

Первый запуск скачивает веса модели эмбеддингов и модель реранкера RAG
(~470 МБ каждая) в `day21/index/models/` — это кэш Hugging Face, в Git он не
попадает. Ключ DeepSeek нужен для чата, ответа RAG, мини-чата, ассистента
разработчика и AI-ревью; сама индексация работает и без ключа. Локальная модель
(дни 26, 28, 29) — необязательный второй провайдер: без установленной Ollama приложение
отвечает через DeepSeek, а переключатель провайдера просто вернёт 502 «Ollama
недоступен». Удалённый сервис (день 30) и GitHub PR (день 32) тоже необязательны:
первый включается в своём разделе, второй работает анонимно с лимитом 60 запросов
в час, а с `GITHUB_TOKEN` — 5000 и с публикацией комментария.

## Как работать над новым днём

1. **Возьмите задание** из челленджа (или из промпта другой нейросети) — как есть.
2. **Сложную задачу сначала спланируйте.** Откройте
   [`ARCHITECT_PROMPT.md`](ARCHITECT_PROMPT.md), вставьте задание в поле
   `{{ЦЕЛЬ}}` и отправьте в **отдельный чат с DeepSeek**: на выходе — декомпозиция
   с Definition of Done, пошаговый план, риски и план Б, проверки и команды
   фиксации.
3. **Передайте план в omp.sh** как промпт дня: агент работает в `day21/` и
   исполняет пункты плана, а не пересказ задания.
4. **Зафиксируйте результат:** `git commit -m "dayN: краткое описание"`,
   `git tag dayN`, затем обновите документацию дня (только текущее состояние).

Сложные задачи (нужен архитектурный этап): новые модули и слои, интеграции,
изменения архитектуры, работа с MCP, планировщик, индексация, оптимизация затрат.
Простые задачи (кнопка, текст, правка документации) можно делать сразу.
Подробности и пример полного цикла — в [`WORKFLOW.md`](WORKFLOW.md).

| Удалённая LLM (опция) | та же Ollama в Google Colab за туннелем Cloudflare — OpenAI-совместимый HTTP `/v1/chat/completions` с клиентским пределом частоты (день 30) |
| GitHub (день 32) | REST API через `httpx` (diff PR, список файлов, публикация отзыва), GitHub Actions, `gh` CLI для публикации комментария |
| Секреты в окружении | `.env` дня: `DEEPSEEK_API_KEY`, `GITHUB_TOKEN` (опция), `HF_TOKEN` (день 5) |
| Фон и планирование | APScheduler, фоновые потоки FastAPI, MCP-серверы по stdio |
| Тесты | `pytest` + `pytest-xdist` (параллельно, `-n auto`) + `pytest-cov` (покрытие) |
| Агент | omp.sh (модель `deepseek/deepseek-flash`), скиллы проекта в `.omp/skills/` |

## Требования

- Windows, **Python 3.14+**, менеджер зависимостей **`uv`**
  (`irm https://astral.sh/uv/install.ps1 | iex`).
- API-ключ DeepSeek (<https://platform.deepseek.com> → API Keys) — для чата,
  сводок, плана оркестрации, ассистента разработчика и AI-ревью PR.
- ~1,5 ГБ диска: `torch` и веса двух моделей (эмбеддинги и реранкер,
  ~470 МБ каждая) для индексации и RAG.
- Необязательно: **Ollama** (`winget install Ollama.Ollama`) и ~9 ГБ под модель
  (`ollama pull qwen2.5-coder:14b`) — второй провайдер ответа; нужен ~9,5 ГБ VRAM
  под GPU-инференс (на этой машине — RTX 5070 12 GB).
- Необязательно для дня 30: аккаунт Google и Colab с GPU T4 — там поднимается
  удалённая Ollama за туннелем Cloudflare (локально ничего ставить не нужно).
- Необязательно для дня 32: `GITHUB_TOKEN` (fine-grained, `Contents: read` и
  `Pull requests: write` для публикации комментария); без него публичные PR
  читаются анонимно с лимитом 60 запросов в час. Для GitHub Action нужен раннер
  с `gh` CLI.
- **`git` в `PATH`** (обычный Git for Windows) — нужен MCP-инструментам, которые
  читают историю и diff репозитория: git-контекст ассистента разработчика (день 31),
  diff для ревью PR (день 32), diff файла у ассистента файлов (день 34) и вся
  подготовка релиза (день 35: теги, коммиты диапазона, изменённые файлы, метрики).
- Для агента omp.sh: CLI `omp`, Python LSP `pyright`, дебаггер `debugpy`.

## Запуск архивных дней

Снимки `day1`–`day13` запускаются каждый по своему README — команды там
актуальны и не менялись. Общая схема:

```bash
# day1 — консольный чат
```

`day4` — документный день без кода: результат в `day4/results.md`. Файлы `.env`
приложения ищут в текущей рабочей директории, поэтому команды выполняйте из папки

## Секреты

- Файлы `.env` **не коммитятся** (правило в корневом `.gitignore`); в Git лежат
  только шаблоны `.env.example` — по одному на день.
- Ключ DeepSeek начинается с `sk-`; заглушки вида `sk-вставьте-сюда-ваш-ключ`
  приложения распознают как неподходящие.
- Токен Hugging Face (день 5) начинается с `hf_` и хранится только в `.env`
  (`HF_TOKEN`).
- Токен GitHub (день 32) — `GITHUB_TOKEN` в окружении или в `day21/.env`
  (fine-grained, `Contents: read` для чтения PR и `Pull requests: write` для
  публикации комментария). Приложение печатает его только маской; для Action тот же
  токен приходит от GitHub (`${{ github.token }}`).

## Процесс разработки (omp.sh)

Перед стартом агент автоматически читает правила из корня:

- [`AGENTS.md`](AGENTS.md) — короткие always-apply правила: где работаем,
  что не читать (архив), как фиксировать результат;
- [`RULES.md`](RULES.md) — sticky-правила (переприкрепляются к каждому запросу);
- [`docs/project-rules.md`](docs/project-rules.md) — архитектурные цели и
  раскладка слоёв (полная версия прежнего `AGENTS.md`);
- [`.clauderules`](.clauderules) — конвенции кода, команды проверок, секреты;
- [`.omp/config.yml`](.omp/config.yml) — модель по умолчанию и роли моделей;
- [`.omp/skills/`](.omp/skills/) — скиллы проекта (FSM, раскладка файлов дня,
  `shared/`, TDD, документация дня): читаются лениво, по триггерам задачи.

Метаданные моделей уточняются в `~/.omp/agent/models.yml` (файл пользовательский,
в репозиторий не попадает) — там для `deepseek-flash` включён приём изображений,
потому что у модели есть зрение, а встроенный каталог omp считает этот SKU
текстовым:

```yaml
providers:
  deepseek:
    modelOverrides:
      deepseek-flash:
        input: [text, image]
        compat:
          stripImageInput: false
```

### Как проходит работа

1. **Разведка и план** — агент читает файлы дня и правила проекта.
2. **Планирование сложной задачи** — через [`ARCHITECT_PROMPT.md`](ARCHITECT_PROMPT.md)
   (см. [`WORKFLOW.md`](WORKFLOW.md)).
3. **Реализация по TDD** — сначала падающий тест (`pytest`), затем реализация до
   зелёного; изменения минимальны и в рамках задачи.
4. **Проверка перед «готово»** — тесты дня, `py_compile` изменённых файлов,
   smoke-запуск приложения, лимиты строк.

### Где искать контекст

- Правила дня: `day21/AGENTS.md` и `day21/.omp/RULES.md` (для сессий из `day21/`).
- Правила проекта: `AGENTS.md`, `RULES.md`, `docs/project-rules.md`,
  `.clauderules`, скиллы в `.omp/skills/`.
- Устройство и инструкции дня: `day21/README.md`, `day21/docs/`,
  `day21/STRUCTURE.md`.
- История: `CHANGELOG.md` и `README.md` конкретного дня.

## Общие модули (`shared/`)

`shared/` — код, который не меняется между днями: день добавляет корень
репозитория в `sys.path` и импортирует модули как `from shared.<module> import ...`.

| Модуль | Что делает |
|---|---|
| `shared/deepseek_utils.py` | Endpoint DeepSeek, ключ из `.env`, stop-строки, `usage_to_dict` |
| `shared/deepseek_client.py` | `make_client(api_key, base_url, timeout)` — клиент OpenAI SDK (ленивый импорт) |
| `shared/db_base.py` | SQLAlchemy: `Base`, `make_engine`, `init_db`, `make_session_factory` |
| `shared/token_counter.py` | `count_tokens` через tiktoken (`cl100k_base`, кодировка кэшируется) |
| `shared/logging_utils.py` | `get_logger`, `configure_logging` |

Модули `shared/` подключают дни 2, 3 (частично) и все дни с `day13`; подробнее —
[`docs/architecture.md`](docs/architecture.md) и [`docs/usage.md`](docs/usage.md).

## Проверки перед «готово»

```bash
cd day21
uv run pytest -m ""                        # весь набор тестов (~70 с)
uv run pytest -m "" --cov=backend --cov-report=html   # покрытие → htmlcov/index.html
uv run python -m py_compile <изменённые .py>          # синтаксис
```

Лимиты структуры: любой `.py` ≤ 400 строк, `app.py` ≤ 100,
`backend/api/main.py` ≤ 80 — правила в [`docs/project-rules.md`](docs/project-rules.md),
проверка описана в скилле `fastapi-streamlit-day-structure`.

Те же проверки — готовность релиза: ассистент дня 35 запускает их сам и показывает
результат в разделе «🚀 Подготовка релиза (Day 35)», в `GET /release/health` и в
отчёте `uv run python scripts/demo_release.py` (признак «тесты пройдены», процент
покрытия из `pytest --cov`, наличие `README.md` и `day21/docs/architecture.md`).
