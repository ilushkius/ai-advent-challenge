````text
# Как ускорить медленный SQL-запрос в PostgreSQL, Илья 🚀

Отличный вопрос! Давай разберём это по шагам — от простого к сложному. Представь, что запрос — это ты в огромной библиотеке: если ты идёшь наугад по всем полкам, это долго, а если есть каталог и указатели — быстро. Индексы и планы запросов работают примерно так же.

## 1. Сначала — диагностика, а не «пальцем в небо» 🔍

**Золотое правило:** не оптимизируй, пока не измерил. Используй `EXPLAIN ANALYZE`:

```sql
EXPLAIN (ANALYZE, BUFFERS, VERBOSE)
SELECT *
FROM orders o
JOIN users u ON u.id = o.user_id
WHERE o.created_at > now() - interval '30 days';
```

Что смотреть в выводе:
- **Seq Scan** на большой таблице — плохой знак (полный перебор).
- **Nested Loop** с огромным числом строк — часто узкое место.
- **Rows estimate vs actual** — если расходится в разы, статистика устарела.
- **Buffers** — сколько страниц читается из диска (`read`) vs из кэша (`hit`).

## 2. Индексы — главный ускоритель ⚡

### Обычный B-tree индекс
```sql
CREATE INDEX idx_orders_created_at ON orders (created_at);
CREATE INDEX idx_orders_user_id ON orders (user_id);
```

### Составной индекс (порядок колонок важен!)
```sql
-- Для WHERE user_id = ? AND status = ?
CREATE INDEX idx_orders_user_status ON orders (user_id, status);
```
Правило: сначала колонки из `WHERE` с равенством, потом диапазоны/сортировка.

### Частичный индекс — когда нужна только часть данных
```sql
CREATE INDEX idx_orders_active
ON orders (user_id)
WHERE status = 'active';
```
Меньше размер → быстрее и дешевле.

### Индекс для поиска по подстроке
```sql
CREATE EXTENSION pg_trgm;
CREATE INDEX idx_users_name_trgm ON users USING gin (name gin_trgm_ops);
-- теперь LIKE '%иван%' будет быстрым
```

### Индекс для JSONB / массивов
```sql
CREATE INDEX idx_data_gin ON events USING gin (payload jsonb_path_ops);
```

## 3. Обнови статистику 📊

Планировщик принимает решения на основе статистики. Устарела — получишь плохой план:

```sql
ANALYZE orders;
-- или для всей базы
VACUUM ANALYZE;
```

Проверь настройки автоочистки — иногда `autovacuum` не успевает на горячих таблицах.

## 4. Перепиши сам запрос ✍️

Часто это даёт больше, чем индексы:

- **Убирай `SELECT *`** — тяни только нужные колонки (меньше I/O, возможен index-only scan).
- **Избегай функций над индексируемой колонкой:**
  ```sql
  -- ❌ индекс не используется
  WHERE date(created_at) = '2024-01-01'
  -- ✅ используется
  WHERE created_at >= '2024-01-01' AND created_at < '2024-01-02'
  ```
- **`EXISTS` вместо `IN` для больших подзапросов:**
  ```sql
  WHERE EXISTS (SELECT 1 FROM logs l WHERE l.user_id = u.id)
  ```
- **`UNION ALL` вместо `UNION`**, если дубликаты не важны (не нужна сортировка).
- **Ограничивай выборку** через `LIMIT`, если нужны только первые строки.
- **Разбивай гигантские JOIN** на этапы через CTE — иногда планировщик справляется лучше.

## 5. Работа с соединениями (JOIN) 🔗

- Убедись, что **колонки в JOIN проиндексированы** с обеих сторон.
- Следи за **типами данных** — `int` vs `bigint` или `text` vs `varchar` могут убить индекс.
- Для больших агрегаций подумай о **материализованном представлении**:
  ```sql
  CREATE MATERIALIZED VIEW mv_daily_stats AS
  SELECT date_trunc('day', created_at) AS day, count(*)
  FROM orders GROUP BY 1;

  REFRESH MATERIALIZED VIEW CONCURRENTLY mv_daily_stats;
  ```

## 6. Настройки сервера ⚙️

Если железо позволяет — крутим `postgresql.conf`:

| Параметр | Что делает | Ориентир |
|---|---|---|
| `shared_buffers` | Кэш страниц БД | ~25% RAM |
| `work_mem` | Память на сортировку/хэш | осторожно, на соединение |
| `effective_cache_size` | Подсказка планировщику | ~50–75% RAM |
| `random_page_cost` | Стоимость случайного чтения | 1.1 для SSD |
| `max_parallel_workers_per_gather` | Параллелизм | 2–4 |

Изменения можно применить без рестарта:
```sql
SET work_mem = '64MB';  -- для сессии
ALTER SYSTEM SET work_mem = '64MB';  -- глобально
SELECT pg_reload_conf();
```

## 7. Продвинутые трюки 🧙

- **Партиционирование** больших таблиц по дате:
  ```sql
  CREATE TABLE orders_2024 PARTITION OF orders
  FOR VALUES FROM ('2024-01-01') TO ('2025-01-01');
  ```
  Запросы с фильтром по дате будут читать только нужную партицию (partition pruning).

- **`pg_stat_statements`** — расширение, которое покажет топ медленных запросов:
  ```sql
  SELECT query, mean_exec_time, calls
  FROM pg_stat_statements
  ORDER BY mean_exec_time DESC LIMIT 10;
  ```

- **Кэширование** на уровне приложения (Redis, memcached) — если данные меняются редко.

- **`CLUSTER`** — физически упорядочить таблицу по индексу (разово, блокирует таблицу):
  ```sql
  CLUSTER orders USING idx_orders_created_at;
  ```

## 8. Порядок действий — чек-лист ✅

1. `EXPLAIN ANALYZE` — найди узкое место.
2. Проверь статистику (`ANALYZE`) и наличие индексов.
3. Перепиши запрос (убери функции над колонками, лишние JOIN).
4. Добавь/поправь индексы (частичные, составные, GIN/GiST).
5. Если данных очень много — партиционирование или материализованные вью.
6. Тюнинг `postgresql.conf` под железо.
7. Мониторь через `pg_stat_statements` и `auto_explain`.

## Аналогия напоследок 🏛️

Представь, что БД — это склад:
- **Индекс** — это стеллаж с ярлыками, а не куча коробок на полу.
- **Статистика** — это карта склада, по которой кладовщик (планировщик) решает, где искать.
- **Партиционирование** — это разбить склад на секции «одежда», «обувь» — и не бегать по всему зданию.
- **work_mem** — размер стола, на котором можно разложить коробки для сортировки.

Если хочешь — скинь конкретный запрос и `EXPLAIN ANALYZE`, разберём его вместе и найдём, что именно тормозит. 💪
````

````text
- Ограничения: объём до 100k строк на файл; при превышении — постраничная выгрузка или стриминг.
- Нефункциональные: генерация ≤ 5 c на 10k строк, отсутствие блокировки основного потока запроса.

2. Разработчик — Вариант A: синхронный экспорт (малые/средние отчёты)
- Стек: Python + `openpyxl` (write_only) или `pandas.to_excel`.
- Поток: GET `/reports/{id}/export?format=xlsx` → сборка DataFrame → `BytesIO` → `StreamingResponse`.
- Плюсы: простота, нет инфраструктуры очередей.
- Минусы: таймаут на больших объёмах, память O(n).

```python
from io import BytesIO
from fastapi import APIRouter
from fastapi.responses import StreamingResponse
import pandas as pd

router = APIRouter()

@router.get("/reports/{report_id}/export")
def export_report(report_id: int, format: str = "xlsx"):
    df = build_report(report_id)  # ваш слой данных
    buf = BytesIO()
    with pd.ExcelWriter(buf, engine="openpyxl") as w:
        df.to_excel(w, index=False, sheet_name="Report")
    buf.seek(0)
    filename = f"report_{report_id}.xlsx"
    return StreamingResponse(
        buf,
        media_type="application/vnd.openxmlformats-officedocument.spreadsheetml.sheet",
        headers={"Content-Disposition": f'attachment; filename="{filename}"'},
    )
```

3. Разработчик — Вариант B: асинхронный экспорт (крупные отчёты)
- Стек: Celery/RQ + объектное хранилище (S3/MinIO) + `openpyxl` write_only.
- Поток: POST `/reports/{id}/export` → task_id → воркер генерирует файл → сохраняет в S3 → клиент опрашивает статус / получает ссылку.
- Плюсы: не блокирует API, масштабируется, поддерживает большие объёмы.
- Минусы: сложнее инфраструктура, задержка выдачи.

```python
@router.post("/reports/{report_id}/export")

4. Тестировщик
- Функциональные: корректность колонок/типов, пустой отчёт, отчёт с 1 строкой, 100k строк, кириллица/эмодзи, спецсимволы в именах.
- Граничные: превышение лимита строк, отмена задачи, повторный экспорт.
- Безопасность: проверка прав на `report_id`, отсутствие утечки чужих данных, rate limiting.
- Производительность: время генерации 10k строк ≤ 5 c, память (вариант A) — контроль O(n).
- Совместимость: открытие в Excel, LibreOffice, Google Sheets; корректный MIME и `Content-Disposition`.
````

## Наблюдаемые эффекты профилей

| Проверка | Результат | Факт из ответа |
|---|---|---|
| Строгий технический: ответ держится у лимита 600 символов (constraints.max_response_length; допуск 1.5×, потому что модель соблюдает ограничение приблизительно) | ✅ да | 606 символов при лимите 600 |
| Строгий технический: ответ без markdown-разметки (preferences.format = plain text) | ✅ да | разметка: нет |
| Дружелюбный наставник: ответ в markdown (preferences.format = markdown) | ✅ да | разметка: заголовки, списки, жирный текст, блоки кода |
| Дружелюбный наставник: ответ подробнее, чем у строгого профиля (preferences.verbosity = подробно) | ✅ да | 5583 против 606 символов |
| Оркестратор процесса: роли идут в порядке аналитик → разработчик → тестировщик (custom_instructions) | ✅ да | порядок в ответе: аналитик → разработчик → тестировщик |

Проверки стиля, формата и длины — это наблюдения, а не гарантии: модель вероятностная, и ограничение из профиля сдвигает ответ (промпт «жёсткое ограничение: весь ответ не длиннее N символов»), но не обязывает её соблюсти лимит символ в символ. Факт этого прогона: 606 символов при лимите 600 у строгого профиля против 5583 символов у «подробного» — ограничение работает как управление объёмом, а не как обрезка текста. Проверки, которые обязаны выполняться всегда, — подстановка профиля в системный промпт (видно в разделе с промптами) и следование кастомной инструкции о порядке ролей.


## Вывод

Профиль — это часть системного промпта, а не подсказка в UI: один и тот же вопрос получает разные ответы по стилю (technical → friendly), формату (plain text → markdown), длине (кратко → подробно) и структуре (обычный ответ → разложенный по ролям аналитик → разработчик → тестировщик). Ограничения тоже работают как ограничения: max_response_length держит ответ в заданном пределе, forbidden_topics уводит разговор от запрещённых тем, required_disclaimers добавляет обязательную вставку.
