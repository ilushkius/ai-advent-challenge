# День 20 — оркестрация MCP-серверов: три сервера, план шагов и журнал

Инструкция по приложению дня 20. День добавляет к агенту дня 19 **флот из трёх
независимых MCP-серверов** и **оркестратор**, который строит для реплики план шагов
и выполняет его:

|Сервер|Инструменты|Роль в цепочке|
|---|---|---|
|`search_server`|`search_web`, `search_local`, `fetch_url`|найти данные|
|`data_server`|`summarize`, `extract_keywords`, `filter_by_date`, `aggregate`|обработать|
|`storage_server`|`save_to_file`, `save_to_db`, `list_saved`, `load_from_file`|сохранить и выдать|

Всего флот публикует **11 инструментов**. Каждый сервер — отдельный процесс по
stdio со своим пакетом в `mcp_servers/`, а состав флота лежит в `mcp_servers.json`:
поэтому четвёртый сервер добавляется правкой файла, без изменения кода. Реестр
`backend/services/mcp_registry.py` держит соединение с каждым сервером и
**маршрутизирует вызов по имени инструмента**, а оркестратор
`backend/services/orchestrator.py` выполняет шаг в порядке «подстановка аргументов →
условие → выбор сервера → подключение → вызов инструмента → запись в журнал → событие
FSM» и пишет каждый шаг в таблицу `orchestration_steps` вместе с именем сервера.

Реплика с фразой про сохранение **именно в базу** («…и сохрани в базу») распознаётся
доменом и запускает оркестрацию до обращения к модели: результат прогона уходит в
системный промпт отдельным блоком «## Результат оркестрации». Прогон дня и отчёт по
пяти сценариям — скриптами `scripts/orchestration_demo.py` и
`scripts/orchestration_report.py`, результат — [reports/orchestration_demo.md](reports/orchestration_demo.md).

Как устроено внутри — [architecture.md](architecture.md), эндпоинты с примерами —
[api.md](api.md), карта модулей — [../STRUCTURE.md](../STRUCTURE.md).

## 1. Что это

Три сервера не знают друг о друге: их связывают протокол MCP и конфигурация флота, а
не импорты. Из этого следует всё остальное устройство дня:

- **Состав флота — данные.** `mcp_servers.json` читает слой
  `backend/core/mcp_server_config.py` (домен — `backend/domain/mcp_server_spec.py`),
  поэтому новый сервер — это запись в файле (`name`, `command`, `args`,
  `description`, `tools_cache`), а не новый код.
- **Соединений столько, сколько серверов.** Одно активное соединение дня 17 никуда не
  делось (раздел «🔌 MCP»), но флот живёт рядом: `GET /mcp/servers` показывает все
  серверы сразу, а нужный сервер шага поднимается динамически (`ensure_connected`).
- **Маршрутизация — по имени инструмента.** `find_tool_by_name` возвращает **первый**
  сервер в порядке файла; если два сервера публикуют инструмент с одним именем,
  выигрывает первый, а в лог уходит `logger.warning`.
- **План — тоже данные, и у него есть источник.** `plan_source` в ответе равен
  `given` (план прислал клиент), `llm` (шаги предложила модель по каталогу флота) или
  `heuristic` (встроенный сценарий дня, отфильтрованный по доступным инструментам —
  так работает прогон без ключа DeepSeek).
- **Ошибка шага — данные, а не падение процесса.** У остановившегося шага есть
  `status` (`failed` / `stopped`), `reason_code` (`unknown_tool`, `not_connected`,
  `tool_error`), `error_message` и `output_result` той же формы, что у шага пайплайна:
  `{"reason_code", "structured", "text", "is_error", "duration_ms"}`.
- **Журнал лежит в SQLite.** Запуск — строка `orchestration_runs`, шаг — строка
  `orchestration_steps` (связь по `run_id`, удаление запуска уносит его шаги
  каскадом). Поэтому интерфейс может опрашивать прогресс, а история переживает
  перезапуск бэкенда.
- **Одна реплика — один автоматизм.** Если оркестрация по реплике распознана,
  пайплайн дня 19 и одиночный MCP-вызов на этом ходу пропускаются: иначе один запрос
  породил бы два независимых похода во флот.

### Что нужно для запуска

|Компонент|Зачем|Проверка|
|---|---|---|
|Python 3.14 и `uv`|зависимости дня и запуск серверов флота|`uv --version`|
|Ключ `DEEPSEEK_API_KEY`|не обязателен: включает ветку LLM в `summarize` сервера `data_server`, планирование плана моделью и ответы чата. Без ключа сводку собирает агрегация (`engine: "aggregation"`), а план строит эвристика дня|`day20/.env`|
|Порт 8000|API дня; в его процессе живут планировщик и фоновые прогоны пайплайна и оркестрации, а на старте поднимается флот MCP-серверов|`curl http://127.0.0.1:8000/` → в ответе группы `"orchestration"` и `"mcp_servers"`|
|Сеть до jsonplaceholder|нужна только источнику `posts`/`users` инструмента `search_web`; `search_local`, `fetch_url`, `data_server` и `storage_server` работают офлайн, а демо-прогон и автотесты сети не требуют|`curl -s -o /dev/null -w "%{http_code}" https://jsonplaceholder.typicode.com/posts` → `200`|
|Три сервера флота|поднимаются самим бэкендом при старте (`connect_all()` в `backend/api/lifespan.py`); вручную их запускать не нужно|раздел «🌐 Оркестрация» → таблица «🧩 Флот серверов», колонка «состояние»|

## 2. Установка и запуск

Менеджер зависимостей — `uv`: прямые зависимости в `pyproject.toml`, точные версии — в
`uv.lock`, интерпретатор — `.python-version`. Активировать окружение не нужно, `uv run`
сам находит `.venv`. Все команды — из папки дня:

```bash
cd day20
uv sync                  # создать .venv по uv.lock
cp .env.example .env     # затем впишите DEEPSEEK_API_KEY=sk-... (не обязательно)
```

`uv sync` нужно выполнить **до** первого запуска: и бэкенд, и `uv run streamlit`
поднимаются в этом окружении.

Терминал 1 — бэкенд. В его процессе живут планировщик, фоновые прогоны и флот
MCP-серверов, поэтому фон существует, пока работает бэкенд:

```bash
uv run uvicorn backend.api.main:app --port 8000
```

Терминал 2 — интерфейс: <http://localhost:8501>

```bash
uv run streamlit run app.py
```

Ключ бэкенд читает так: `day20/.env` → переменная окружения `DEEPSEEK_API_KEY` (файла
нет — ключ можно задать только окружением). Тем же ключом пользуется инструмент
`summarize` сервера `data_server`: он читает файл `day20/.env` сам, потому что работает
отдельным процессом. Адрес бэкенда фронтенд берёт из `DAY20_BACKEND_URL`
(по умолчанию `http://127.0.0.1:8000`); переменная нужна, только если порт
нестандартный.

Флот поднимается на старте приложения: `lifespan` после планировщика зовёт
`get_mcp_registry().connect_all()`, и реестр запускает по дочернему процессу на каждый
сервер из `mcp_servers.json`, читая каталог его инструментов. Команды флота выполняются
от корня дня (`MCP_FLEET_CWD` = `day20/`), поэтому в `args` можно писать относительные
пути (`mcp_servers/search_server/server.py`). Сбой отдельного сервера старту не мешает:
он виден в своей записи как `error`, остальные работают.

Проверка сразу после запуска:

```bash
curl http://127.0.0.1:8000/mcp/servers        # count: 3, connected: 3, total_tools: 11
curl http://127.0.0.1:8000/                   # группы "orchestration" (6) и "mcp_servers" (3)
```

Собственный сервер дня 19 (`mcp_server/`, девять инструментов) никуда не исчез: он
обслуживает разделы «🔌 MCP» (активное соединение дня 17) и «🔀 Пайплайны» и
подключается вручную — в разделе «🔌 MCP» формой подключения или через API:

```bash
curl -X POST http://127.0.0.1:8000/mcp/connect \
     -H "Content-Type: application/json" \
     -d '{"target": "uv run python mcp_server/server.py"}'
```

Флот оркестрации — отдельный механизм: три сервера поднимаются бэкендом и не требуют
ручного подключения.

## 3. Три MCP-сервера и их инструменты

|Сервер (имя в файле)|Команда запуска|Инструменты|Что делает|
|---|---|---|---|
|`search_server`|`uv run python mcp_servers/search_server/server.py`|`search_web`, `search_local`, `fetch_url`|ищет данные: лента jsonplaceholder или Википедия, файл внутри папки дня, страница по HTTP → текст|
|`data_server`|`uv run python mcp_servers/data_server/server.py`|`summarize`, `extract_keywords`, `filter_by_date`, `aggregate`|обрабатывает данные: сводка, ключевые слова, отбор по дате, группировка с метрикой|
|`storage_server`|`uv run python mcp_servers/storage_server/server.py`|`save_to_file`, `save_to_db`, `list_saved`, `load_from_file`|сохраняет и выдаёт: файл в `output/`, строка в `storage.db`, список сохранённого, чтение файла|

Имена серверов в протоколе (ответ `initialize`): `day20-search`, `day20-data`,
`day20-storage`, версия у всех `1.0.0`. Каждый сервер создаётся как
`MCPServer(name=…, version=…, instructions=…)` из `mcp.server.mcpserver`, инструменты
объявляются декоратором `@mcp.tool()`: из аннотаций SDK собирает `inputSchema`, из
докстринга — описание для модели, из `TypedDict` возврата — `outputSchema`
(`mcp_servers/<сервер>/schemas.py`), а ошибка инструмента приходит данными
(`ToolError` с понятным текстом).

### `search_server` — поиск данных

|Инструмент|Параметры|Что возвращает|Где читает|
|---|---|---|---|
|`search_web`|`query` (строка, подстрока без учёта регистра; пустая — первые записи); `source` (`posts` — по умолчанию, `users`, `wikipedia`); `limit` (1..20, по умолчанию 5)|`query`, `source`, `source_kind` (`api`/`wiki`), `count`, `items` (у элемента `id`, `title`, `content`, `url`, `metadata`)|лента jsonplaceholder (`/posts`, `/users`) или `ru.wikipedia.org/w/api.php` (opensearch)|
|`search_local`|`query` (подстрока в блоке); `path` (по умолчанию `mcp_server/data/notes.md`); `limit` (1..20, по умолчанию 5)|`query`, `path`, `count`, `items` (`title` — первая строка блока, `content` — блок целиком, `metadata` — путь и номер блока)|файл внутри корня источников; по умолчанию корень — папка дня (`--file-root`)|
|`fetch_url`|`url` (только `http://` или `https://`); `max_chars` (200..20000, по умолчанию 4000)|`url`, `status`, `content_type`, `chars`, `truncated`, `text` (HTML очищен от `<script>`/`<style>` и тегов)|страница по HTTP|

Источники `posts`/`users` фильтруются подстрокой по `title` + `body` (для
пользователей — по `name`, `username`, `email`), читается страница целиком и режется
фильтром. Неизвестный источник, путь вне корня, неразбираемая схема и не-2xx-ответ
приходят ошибкой инструмента с причиной, а не падением сервера.

Флаги сервера: `--api-base` (по умолчанию `https://jsonplaceholder.typicode.com`,
стенды и тесты подменяют его локальным адресом), `--wiki-base`,
`--timeout` (10 с), `--file-root` (по умолчанию папка дня).

### `data_server` — обработка данных

|Инструмент|Параметры|Что возвращает|
|---|---|---|
|`summarize`|`items` (список словарей, обязателен); `style` (`short` — по умолчанию, `detailed`, `bullets`); `max_length` (50..4000, по умолчанию 600)|`summary_text`, `key_points`, `total_items`, `style_used`, `engine` (`llm` или `aggregation`)|
|`extract_keywords`|`text` (обязателен); `limit` (1..20, по умолчанию 7)|`keywords` (по убыванию частоты, при равенстве — по алфавиту), `count`, `joined`, `engine` (`frequency`)|
|`filter_by_date`|`items`; `field` (по умолчанию `created_at`); `since`, `until` (ISO-8601 или `ДД.ММ.ГГГГ`, пустая граница — без ограничения); `limit` (1..200, по умолчанию 20)|`items` (в исходном порядке), `count`, `skipped` (записи без разобранной даты), `field`, `since`, `until`|
|`aggregate`|`items`; `group_by` (пусто — одна группа `все`); `metric` (`count` — по умолчанию, `sum`, `avg`, `min`, `max`); `value_field` (обязателен для всех метрик кроме `count`); `limit` (1..200, по умолчанию 20)|`groups` (ключ и значение, по убыванию значения), `count`, `metric`, `group_by`|

`summarize` вызывает DeepSeek (`deepseek-chat`, температура 0.2) только если ключ найден
и сервер не запущен с `--llm off`; иначе — и при любом сбое модели — сводка собирается
агрегацией по заголовкам, и это не ошибка шага. Остальные три инструмента считают
локально. Пропущенные записи без даты — не ошибка; ошибкой отвечает только неразобранная
непустая граница, чужой стиль, чужой вид метрики и отсутствие `value_field`.

Флаги сервера: `--llm` (`auto` — по умолчанию, `off` — всегда агрегация), `--timeout`
(30 с — таймаут вызова модели).

### `storage_server` — сохранение и выдача

|Инструмент|Параметры|Что возвращает|Где пишет/читает|
|---|---|---|---|
|`save_to_file`|`content` (до 20000 символов); `filename` (по умолчанию `orchestration_result.md`); `format` (`md` — по умолчанию, `txt`, `json`)|`filename`, `filepath`, `size_bytes`, `format`, `saved_at`|только в `day20/output/` (`--output-dir`); расширение заменяется на запрошенный формат|
|`save_to_db`|`kind` (вид записи, до 64 символов); `title` (до 200); `content` (до 20000); `source` (до 200); `metadata` (объект, сохраняется JSON-строкой)|`row_id`, `kind`, `title`, `source`, `size_bytes`, `created_at`|только в `day20/storage.db`, таблица `saved_records` (`--db-path`)|
|`list_saved`|`kind` (`all` — по умолчанию, `file`, `row`); `limit` (1..50, по умолчанию 10)|`files` (свежие сверху), `rows` (свежие сверху), `count`, `kind`|каталог вывода и база сервера|
|`load_from_file`|`filename` (имя без пути и `..`)|`filename`, `filepath`, `chars`, `format`, `text`|файл внутри каталога вывода|

Имя файла чистится: путь и `..` запрещены, поэтому сервер не может выйти за каталог
вывода, даже если модель передала `../../etc/passwd`. Отдельный файл базы — не прихоть:
в `agents.db` пишет ровно один процесс (бэкенд дня), а `storage_server` работает
отдельным процессом, поэтому общий файл сделал бы двух писателей.

Флаги сервера: `--output-dir` (по умолчанию `day20/output`), `--db-path` (по умолчанию
`day20/storage.db`).

## 4. Как запустить демо-сценарий одной кнопкой

1. Откройте <http://localhost:8501> и выберите раздел **«🌐 Оркестрация»**.
2. В верхней таблице «🧩 Флот серверов» убедитесь, что все три сервера в состоянии
   «🟢 подключён» — они поднимаются бэкендом вместе с приложением.
3. Нажмите большую кнопку **«🚀 Запустить демо-сценарий»** (кнопка `primary`, во всю
   ширину). Прогон стартует **в фоновом потоке бэкенда**, поэтому внизу появится
   сообщение «Оркестрация запущена (запуск №N, план: …)», где источник плана —
   `heuristic` без ключа DeepSeek или `llm` с ключом: форма сразу получает номер
   запуска, а страница не блокируется на время пяти реальных вызовов.
4. Под кнопкой идёт блок прогресса с заголовком «Запуск №N · план demo-scenario»: строку
   статуса («⏳ выполняется») сменяет итоговая («✅ выполнена»), а полоса показывает
   **«шагов пройдено: N из 5»**. Прогресс обновляется раз в секунду.
5. По мере выполнения появляются пять раскрывающихся строк — по одной на шаг: «✅ 0.
   search_server · search_web — 320 мс». Внутри видны входные аргументы (JSON) и
   выходные данные шага (структурированный результат или текст), а у упавшего шага —
   ещё и текст ошибки.
6. Когда прогон получил терминальный статус, под строками появляется итог: сообщение,
   сколько серверов задействовано и их имена и суммарная длительность в миллисекундах;
   ниже рисуются диаграмма флоу и таблица шагов (раздел 5).

Сценарий выполняет ровно пять шагов по трём серверам, и данные в нём переходят из
сервера в сервер по ссылкам на выход предыдущего шага:

|Шаг|Сервер|Инструмент|Что делает|
|---|---|---|---|
|0|`search_server`|`search_web`|берёт первые 5 постов jsonplaceholder (`query` пустой — «без фильтра»; русская реплика не фильтруется по латинской ленте, поэтому запрос уходит в заголовок записи в базе)|
|1|`data_server`|`summarize`|сводит `items` шага 0 стилем `short` (до 600 символов)|
|2|`data_server`|`extract_keywords`|выделяет 7 ключевых слов из `summary_text` шага 1|
|3|`storage_server`|`save_to_file`|пишет `output/demo-scenario.md`: сводку и ключевые слова|
|4|`storage_server`|`save_to_db`|пишет строку `kind="orchestration"` в `storage.db`, метаданные — путь файла и ключевые слова|

Реплика, план и аргументы запуска демо-сценария живут в
`backend/domain/orchestration_spec.py` (`DEMO_QUERY`, `DEMO_PLAN`, `demo_arguments`:
`limit` 5, `filename` `demo-scenario`, `format` `md`). Поэтому кнопка интерфейса,
CLI-прогон `scripts/orchestration_demo.py` и автотесты запускают один и тот же
сценарий, а не три похожих.

Тот же запуск через API (полезно для проверки без браузера):

```bash
curl -X POST http://127.0.0.1:8000/orchestration/demo \
     -H "Content-Type: application/json" -d '{"background": true}'
# {"run_id": 1, "status": "running", ...}

curl http://127.0.0.1:8000/orchestration/runs/1     # status: completed, 5 шагов, 3 сервера
```

При `background: false` шаги выполняются в этом же запросе и весь отчёт возвращается
сразу — так ходит агент и так удобно проверять сценарии скриптами.

Свой запрос можно отправить формой «Свой запрос (план построит бэкенд)»: план для такой
реплики предложит модель по каталогу флота, а без ключа DeepSeek — эвристика дня
(встроенный сценарий, из которого выпадают невыполнимые шаги).

## 5. Как читать диаграмму флоу и таблицу шагов

Под прогрессом рисуются две формы одного и того же следа прогона.

**Диаграмма флоу** — `flowchart LR` (`frontend/orchestration_steps.py`): узел на шаг
подписан сервером и инструментом (`S0["✅ search_server<br/>search_web"]`), а подпись
ребра — это то, что ушло следующему серверу:

|Шаг отдал|Подпись ребра|Пример|
|---|---|---|
|`search_web` / `search_local`|`N элементов`|«5 элементов»|
|`summarize`|`N знаков` (длина `summary_text`)|«178 знаков»|
|`extract_keywords`|`N ключевых слов`|«7 ключевых слов»|
|`save_to_file`|`файл <имя>`|«файл demo-scenario.md»|
|`save_to_db`|`строка <row_id>`|«строка 7»|

Под диаграммой идёт **текстовая цепочка** того же потока — например
`0. ✅ search_server · search_web  →[5 элементов]→ 1. ✅ data_server · summarize …`. Она
нужна не «на всякий случай»: диаграмму рисует js-mermaid уже в браузере, а текстовый
след читается всегда — в том числе там, где этот код не выполняется.

**Таблица шагов** собирается из тех же строк журнала и имеет ровно семь колонок
требования дня:

|Колонка|Что в ней|Источник|
|---|---|---|
|шаг|номер шага с нуля (`step_index`)|`orchestration_steps.step_index`|
|сервер|имя сервера, который получил вызов|`orchestration_steps.server_name`|
|инструмент|имя инструмента|`orchestration_steps.tool_name`|
|входные данные|аргументы вызова, обрезанные до 90 символов|`orchestration_steps.input_args`|
|выходные данные|структурированный результат (или текст, или код ошибки)|`orchestration_steps.output_result`|
|время|длительность шага в миллисекундах|`orchestration_steps.duration_ms`|
|статус|значок и значение: `✅ ok`, `❌ failed`, `⏹ stopped`|`orchestration_steps.status`|

Для машинного чтения журнал отдаёт `output_result` одной и той же формы у успеха и
неудачи: `{"reason_code", "structured", "text", "is_error", "duration_ms"}` (у шага,
упавшего на подстановке аргументов, результата нет вовсе — `null`, и это тоже данные).
Именно поэтому ссылки вида `$steps.1.structured.summary_text` в плане всегда определены.

```bash
curl http://127.0.0.1:8000/orchestration/runs/1/steps   # те же колонки, но из API
```

## 6. Как посмотреть историю запусков и статистику

Ниже прогресса идёт блок «🕓 История запусков» — он опрашивает бэкенд раз в пять секунд
(частый опрос нужен прогрессу, а не истории).

|Колонка таблицы истории|Что означает|
|---|---|
|№|номер запуска (`orchestration_runs.id`)|
|запрос|реплика запуска, обрезанная до 60 символов|
|статус|`⏳ выполняется`, `✅ выполнена`, `⏹ остановлена досрочно`, `❌ ошибка`|
|серверы|имена серверов, которых коснулся прогон|
|шагов|сколько шагов в плане запуска|
|начало|время старта (местное время интерфейса)|
|длительность, мс|полное время прогона|

Над таблицей выводятся три метрики по всему журналу: **запусков**, **шагов** и
**среднее время шага, мс**. В раскрывающемся блоке «Статистика по серверам и
инструментам» — две таблицы: сервер / вызовов / среднее время и инструмент / сервер /
вызовов. Все числа считает хранилище (`OrchestrationStore.stats()`) по таблице
`orchestration_steps`, а не интерфейс.

Под таблицей выбирается запуск («Детали запуска»), и его шаги показываются теми же
раскрывающимися строками, что и в прогрессе. Рядом — кнопка **«🗑 Удалить запуск»**:
удаление уносит запуск вместе с шагами (каскад) и очищает номер в состоянии сессии.

То же через API:

```bash
curl "http://127.0.0.1:8000/orchestration/runs?limit=10"        # runs + stats
curl "http://127.0.0.1:8000/orchestration/runs?status=failed"   # фильтр по статусу
curl -X DELETE http://127.0.0.1:8000/orchestration/runs/1       # {"status": "deleted", "run_id": 1}
```

Неизвестный статус в фильтре — `400` с перечнем допустимых, удаление несуществующего
запуска — `404`.

## 7. Как посмотреть инструменты сервера и обновить кэш

Раздел «🌐 Оркестрация» начинается с таблицы флота: колонки **сервер**, **цель**
(`command` + `args`, то есть та команда, которой поднимается процесс), **описание**,
**инструментов**, **состояние** (`🟢 подключён`, `🟡 подключается`, `⚪ не подключён`,
`❌ ошибка`) и **ошибка** (текст причины у того сервера, который не поднялся). Под
таблицей — сводка «Всего серверов / подключено / инструментов в флоте».

Правее кнопки «🔄 Обновить кэш инструментов» выбирается сервер, и под таблицей
показываются его инструменты: **инструмент**, **описание**, обязательные **аргументы**,
а в раскрывающемся блоке «Схема аргументов инструментов сервера» — полные
`input_schema` всех инструментов в виде JSON. Если сервер не подключён, каталог берётся
из `tools_cache` файла, и об этом честно сообщается подписью: это последний известный
каталог, а не прочитанный сейчас.

Кэш нужен именно для этого: без него у неподнявшегося сервера не было бы каталога, и
маршрутизация по имени инструмента не смогла бы найти его инструменты. Кнопка
«🔄 Обновить кэш инструментов» перечитывает `tools/list` у каждого подключённого сервера
и **записывает результат в `mcp_servers.json`** (`tools_cache` каждого сервера; файл
переписывается атомарно — через временный файл и `os.replace`). Ответ `200` приходит
всегда: сбой одного сервера — это данные его записи, а не отказ всего обновления.

```bash
curl http://127.0.0.1:8000/mcp/servers                       # состав флота и состояние
curl http://127.0.0.1:8000/mcp/servers/data_server/tools     # 4 инструмента этого сервера
curl -X POST http://127.0.0.1:8000/mcp/servers/refresh       # перечитать каталоги и записать кэш
```

Неизвестное имя сервера — `404` с перечнем известных. Заметьте: `GET /mcp/servers` — это
флот, а `GET /mcp/status` — по-прежнему одно активное соединение раздела «🔌 MCP»; в
разделе «🔌 MCP» таблица тех же серверов устроена иначе (там есть кнопка, которая
открывает активное соединение с выбранным сервером, чтобы вызвать его инструмент
вручную).

## 8. Как добавить новый сервер

Новый сервер — это запись в `mcp_servers.json`; код реестра, оркестратора, API и
интерфейса менять не нужно. Поля записи:

|Поле|Смысл|
|---|---|
|`name`|имя сервера в флоте: им адресуют инструменты (`GET /mcp/servers/{name}/tools`), оно же пишется в журнал шагов колонкой `server_name`. Имена должны быть уникальными и непустыми|
|`command`|программа запуска (`uv`, `python`, абсолютный путь к интерпретатору)|
|`args`|аргументы команды: путь к точке входа сервера и его собственные флаги. Команда выполняется от корня дня, поэтому относительные пути считаются от `day20/`|
|`description`|человеческое описание для таблицы флота («что этот сервер умеет»); его видит и модель в каталоге|
|`tools_cache`|кэш каталога инструментов; заполняется сам кнопкой «🔄 Обновить кэш инструментов» (`POST /mcp/servers/refresh`). Пустой список — нормальное начальное значение|

Пример: в ассетах тестов дня лежит сервер-эхо `tests/mcp_echo_server.py` с инструментами
`echo` и `add`. Чтобы добавить его в флот, допишите четвёртую запись:

```json
{
  "name": "echo_server",
  "command": "uv",
  "args": ["run", "python", "tests/mcp_echo_server.py"],
  "description": "Сервер-эхо: echo и add (добавлен без правки кода)",
  "tools_cache": []
}
```

Дальше:

1. Перезапустите бэкенд: состав флота перечитывает `connect_all()` при старте
   приложения — он подключает новые записи, переподключает упавшие и закрывает
   исчезнувшие из файла. Уже подключённые серверы при этом не перезапускаются.
2. Проверьте `GET /mcp/servers` (серверов станет четыре) и
   `GET /mcp/servers/echo_server/tools` (два инструмента) — или нажмите «🔄 Обновить кэш
   инструментов», чтобы каталог нового сервера попал в `tools_cache`.
3. Маршрутизация найдёт инструмент по имени сразу: `find_tool_by_name("echo")` вернёт
   `echo_server`, и такой шаг можно включать в план (или просто попросить агента про
   «echo»). Если имя инструмента совпало с инструментом другого сервера, вызов уйдёт
   **первому** серверу в порядке файла, а в лог — предупреждение.

Ровно этот сценарий прогоняется и в отчёте (сценарий 5): копия `mcp_servers.json` во
временном каталоге плюс четвёртая запись — и реестр отдаёт 4 сервера и 13 инструментов,
хотя код не менялся.

Сценарии описаны в `scripts/orchestration_scenarios.py` (1–3) и
`scripts/orchestration_fleet.py` (4–5), а поднимает их и собирает отчёт
`scripts/orchestration_demo.py`.

Автотесты дня (те же пять сценариев плюс модульные и stdio-тесты серверов):

```bash
uv run pytest -q
```

Сквозной прогон с отчётом (офлайн, без ключа: `data_server` запускается с `--llm off`,

```bash
uv run python scripts/orchestration_demo.py --tests --report docs/reports/orchestration_demo.md
```

Скрипт печатает трассировку шагов каждого сценария и завершает вывод строкой «проверок
пройдено: N/M»; код возврата `0` — все проверки прошли, `1` — есть `✗`.

|Флаг|По умолчанию|Смысл|
|---|---|---|
|`--report`|`docs/reports/orchestration_demo.md`|куда записать markdown-отчёт (разделы: проверки прогона, три сервера и их инструменты, сценарии 1–5, схема таблиц журнала, диаграмма флоу, автотесты дня, что осталось за рамками)|

|`--tests`|—|прогнать `pytest -q` и вписать его итог в отчёт|
|`--llm`|`off`|`off` — сводка агрегацией, `auto` — разрешить DeepSeek в `data_server`|
|`--json`|—|напечатать итог сценариев как JSON|
|`--output-dir`|`day20/output`|куда `save_to_file` пишет файлы прогона|
|`--db`|временный файл|файл SQLite для журнала прогона|
|`--servers-file`|временный файл|конфигурация флота; по умолчанию собирается временная, с абсолютными путями к трём серверам дня|

Артефакты прогона остаются в репозитории: `output/demo-scenario.md`; файл `storage.db`
в git не попадает (`*.db` в корневом `.gitignore`), поэтому его создаёт прогон.

## Частые вопросы и ошибки

- **Сервер в состоянии `❌ ошибка`.** Смотрите колонку «ошибка» таблицы флота или
  поле `error` ответа `GET /mcp/servers`: там текст причины (обычно команда не найдена
  или путь к серверу указан не от корня дня). Остальные серверы при этом работают, а
  шаги плана, адресованные упавшему серверу, получат `unknown_tool` — инструмента
  упавшего сервера нет в каталоге, и оркестратор прямо это подсказывает.
- **Шаг остановился, в тексте «Не подключены серверы: …».** Это тот же случай: план
  требует инструмент сервера, который не поднялся. Проверьте команду и её аргументы в
  `mcp_servers.json`; при `not_connected` в `reason_code` сервер не поднялся и при
  попытке подключения шага.
- **Флот пуст.** Если `mcp_servers.json` нет или в нём пустой список, интерфейс
  предупреждает «Флот пуст», а `POST /orchestration/demo` отвечает `400` с текстом «Ни
  один шаг сценария не выполним: флот не публикует нужных инструментов». Добавьте
  запись в файл (раздел 8) — код менять не нужно.
- **`summarize` вернул `engine: "aggregation"`.** Так и должно быть: ключа DeepSeek нет
  или сервер запущен с `--llm off`. Это не ошибка шага — сводка собрана по заголовкам.
- **Не нашли файл прогона.** Демо-сценарий пишет `output/demo-scenario.md` в каталоге,
  который задан `--output-dir` процесса `storage_server` (по умолчанию `day20/output`).
  Строка прогона лежит отдельно — в `storage.db` (`--db-path`), а не в `agents.db`.
- **Реплика про поиск со сводкой и файлом ушла в пайплайн, а не в оркестрацию.** Так
  задумано: узкое правило распознавания срабатывает на фразу про сохранение именно в
  базу или на явное упоминание оркестрации. Реплика «найди статьи про RAG, сделай
  сводку и сохрани в файл» остаётся пайплайном дня 19, и её контракт закреплён тестом.
- **У плана из своего запроса полоса прогресса считается иначе.** «шагов пройдено: N
  из 5» показывается для демо-сценария — в его плане пять шагов; у плана, построенного
  моделью или эвристикой, знаменатель — число шагов, уже записанных в журнал: строка
  шага появляется в нём сразу со своим итоговым статусом (`ok`/`failed`/`stopped`), а
  не в состоянии «выполняется».
