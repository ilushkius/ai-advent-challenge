# День 12 — установка и использование

Практическое руководство по приложению дня 12: **три слоя памяти агента**
(структура дня 11 — краткосрочная, рабочая, долговременная) плюс
**персонализация**: профиль пользователя, который подключается к системному
промпту **каждого** запроса агента. Здесь: установка, запуск, маршрутизация
«действие → слой», работа с профилем в интерфейсе (создание, редактирование,
переключение, кастомные инструкции), три проверки и сценарий видео.

Устройство — в [architecture.md](architecture.md), контракты HTTP — в
[api.md](api.md). Персонализацию доказывает прогон
[`personalization_comparison.md`](../personalization_comparison.md) (скрипт
`personalization_comparison.py`); отчёт дня 11 по трём слоям памяти остался в
дне 11 — [`../../day11/memory_layers_comparison.md`](../../day11/memory_layers_comparison.md)
(в `day12/` его нет).

Слои живут в трёх таблицах и различаются не только содержимым, но и ключом, к
которому привязаны: 👤 **краткосрочная** (`short_term_messages`, `session_id`) —
реплики текущего диалога, 🗂 **рабочая** (`working_memory`, `task_id` + `key`) —
данные активной задачи, 🧠 **долговременная** (`long_term_memory`, `category` +
`key`) — профиль, предпочтения, решения, знания. Что и куда попадает — в §4.

Профиль пользователя (`user_profiles`, ключ `user_id`) — четвёртый источник
системного промпта, но **не слой памяти**: он не хранит диалог, не отбирается по
релевантности (в отличие от долговременной памяти) и подставляется в промпт
целиком — см. §4.4 и §6.

## 1. Установка зависимостей

Нужен **Python 3.14+**. Все команды выполняются из папки `day12` в PowerShell.

```powershell
cd day12
python -m venv .venv
.venv/Scripts/python -m pip install --upgrade pip
.venv/Scripts/python -m pip install -r requirements.txt
```

Проверка, что все зависимости импортируются (одна команда, ничего не запускает):

```powershell
.venv/Scripts/python -c "import fastapi, uvicorn, streamlit, openai, requests, sqlalchemy, tiktoken, httpx, pytest, pandas; print('ok')"
```

Ожидаемый вывод — `ok`. Если какой-то пакет не найден, повторите
`pip install -r requirements.txt` (убедитесь, что активирован именно `.venv`).

## 2. Переменные окружения: ключ DeepSeek

Ключ DeepSeek нужен **только бэкенду**. Фронтенд ключ не читает — он общается с
бэкендом по HTTP, поэтому вводить ключ в интерфейсе нигде не нужно.

Порядок поиска ключа:

1. файл `day12/.env` (строка `DEEPSEEK_API_KEY=...`);
2. переменная окружения `DEEPSEEK_API_KEY`.

Создайте `.env` из шаблона и впишите свой ключ:

```powershell
copy .env.example .env
```

```dotenv
# day12/.env
DEEPSEEK_API_KEY=sk-ваш-ключ
```

Файл `day12/.env` не коммитится в git. Если ключа нет:

| Без ключа | Поведение |
|---|---|
| Создание/список/правка/удаление агентов, **все операции со слоями памяти** (`/memory/...`) и **весь CRUD профилей** (`/users`, `/users/{user_id}/profile`) | работают полностью |
| `POST /agents/{id}/generate` (реальный ответ модели) | `502` со `status: "error"` и понятным текстом вроде «Ключ API не задан…»; при этом в ответе всё равно есть `profile` и `system_prompt` — блок персонализации считается до вызова DeepSeek |
| `POST /agents/{id}/compare` без `call_api` | работает: считаются только токены |

Адрес бэкенда фронтенд берёт из переменной `DAY12_BACKEND_URL`, по умолчанию
`http://127.0.0.1:8000`. Менять её нужно, если бэкенд поднят на другом порту:

```powershell
$env:DAY12_BACKEND_URL = "http://127.0.0.1:8019"
.venv/Scripts/python -m streamlit run app.py
```

Скрипт отчёта читает ключ из того же `day12/.env` (или из окружения) — см. §9.

## 3. Запуск

Нужны **два процесса**, оба запускаются из папки `day12`.

**Терминал 1 — бэкенд (FastAPI + uvicorn, порт 8000):**

```powershell
cd day12
.venv/Scripts/python -m uvicorn backend.main:app --port 8000
```

При старте бэкенд создаёт файл базы `day12/agents.db` (если его ещё нет) и
таблицы: восемь унаследованных (`agents`, `short_term_messages`,
`working_memory`, `long_term_memory`, `summaries`, `token_usage`, `facts`,
`checkpoints`) плюс **`user_profiles`** — профили пользователей дня 12. Слои
памяти, диалог, факты, ветки, метрики и профили переживают перезапуск (активные
сессия и задача лежат в строке `agents`, профиль агента — в колонке
`agents.user_id`). Swagger — на `http://127.0.0.1:8000/docs`.

**Терминал 2 — интерфейс (Streamlit, порт 8501 по умолчанию):**

```powershell
cd day12
.venv/Scripts/python -m streamlit run app.py
```

Откройте адрес, который Streamlit напечатал в консоли (обычно
`http://localhost:8501`). В сайдбаре должно появиться
«🟢 Бэкенд: http://127.0.0.1:8000 · агентов: N».

Проверка бэкенда из третьего терминала:

```powershell
curl.exe http://127.0.0.1:8000/
```

> [!] В Windows PowerShell `curl` — это алиас командлета `Invoke-WebRequest`, и
> привычные флаги (`-X`, `-H`, `-d`) у него означают другое. Примеры в этой
> документации используют **`curl.exe`** — вызывайте именно его либо работайте в
> bash-подобной оболочке (Git Bash, WSL).

`GET /` вернёт список эндпоинтов — это подтверждает, что API живой; среди полей
ответа есть `personalization` со списком эндпоинтов профиля (§6.8).

### Порядок блоков в основной области

Вверху основной области — переключатель разделов (`st.radio` «Раздел»):
**«💬 Чат и память»** (открыт по умолчанию) и **«👤 Профиль пользователя»**.
Это именно radio, а не `st.tabs`: Streamlit не сохраняет выбранную вкладку между
перезапусками скрипта, а после «💾 Сохранить профиль» нужен `st.rerun` — с radio
пользователь остаётся в том же разделе (§6.1).

В разделе **«💬 Чат и память»** сверху вниз идёт: **карточка агента** (имя,
`agent_id`, модель, температура, `max_tokens`, стратегия и `window_size`, профиль
`user_id`; рядом — «🗑 Удалить агента») → **панель текущей стратегии** (только
одна: «🗜 Сжатие контекста» при `summary`, «📌 Факты» при `sticky_facts`,
«🌿 Ветвление истории» при `branching`) → **«📊 Токены диалога»** → **«🧠 Слои
памяти агента»** (три вкладки, §5.2–§5.4) → **«🧭 Что ушло в последний запрос»**
(§5.6) → **«💬 Диалог»** → expander «⚖️ Сравнить режимы» → форма отправки
(поле «Сообщение агенту» + кнопка «🚀 Отправить»), отдельной строкой под ней —
кнопка «🧹 Очистить историю». Сайдбар: создание агента (в том числе селектор
«Профиль пользователя (user_id)», §6.5), «⚙️ Стратегия контекста», «🗂 Задача и
сессия».

То есть панели слоёв и индикатор стоят **выше** диалога и поля ввода, а не под
ними. Порядок блоков раздела «👤 Профиль пользователя» — в §6.

## 4. Модель памяти и профиль: что и куда сохраняется

### 4.1 Три слоя: таблица, ключ, жизненный цикл

| Слой | Таблица | Ключ | Что хранит | Когда очищается |
|---|---|---|---|---|
| 👤 Краткосрочная | `short_term_messages` | `session_id` | реплики текущего диалога (роль + текст + время) | `new_session()`, `DELETE /agents/{id}/memory/short-term`, `DELETE /agents/{id}/history` |
| 🗂 Рабочая | `working_memory` | `task_id` + `key` | данные активной задачи: цель, ограничения, решения, критерии | вручную (перезапись ключа) или сменой задачи; новая сессия её не трогает |
| 🧠 Долговременная | `long_term_memory` | `category` + `key` | профиль, устойчивые предпочтения, важные решения, знания | только вручную: `DELETE /agents/{id}/memory/long-term/{entry_id}` |

Активные `session_id` и `task_id` агента хранит строка `agents`
(`current_session_id` / `current_task_id`) — поэтому после перезапуска бэкенда
диалог продолжается в той же сессии, а рабочая память — в той же задаче.

Профиль пользователя лежит отдельно, в таблице `user_profiles`, и привязан к
`user_id` (не к агенту и не к сессии). Колонка `agents.user_id` (по умолчанию
`"default"`) указывает, чей профиль подключать к запросам агента. Внешнего
ключа между `user_profiles` и `agents` **нет намеренно**: удаление профиля не
должно уносить агентов — они просто теряют персонализацию.

### 4.2 Правило маршрутизации: действие → слой

Это и есть ответ на «вы явно выбираете, что и куда сохраняется»: ни одна запись
не попадает в рабочую или долговременную память «сама».

| Действие | Слой | Что происходит |
|---|---|---|
| Ход диалога (`POST /agents/{id}/generate`) | краткосрочная | после успешного ответа сохраняется пара реплик `user` + `assistant` текущей сессии |
| Форма вкладки «🗂 Рабочая» (`POST /memory/working`) | рабочая | upsert по `task_id` + `key`: повторный ключ перезаписывает значение |
| `POST /memory/working` с `task_id` в теле | рабочая | запись уходит в **указанную** задачу, не обязательно в активную |
| Форма вкладки «🧠 Долговременная» (`POST /memory/long-term`) | долговременная | upsert по `category` + `key`, с уверенностью 0…1 |
| `POST /memory/session` («🆕 Новая сессия») | краткосрочная | реплики прошлой сессии (плюс конспекты `summaries` и факты `facts`) удаляются; рабочая и долговременная память остаются |
| `PUT /memory/task` («🔀 Переключить задачу») | рабочая | меняется активная задача: в контекст идут записи только новой задачи; диалог и краткосрочный слой не трогаются |
| Форма профиля (`POST`/`PUT /users/{user_id}/profile`) | — (профиль, не слой) | профиль обновляется и **сразу** применяется к живым агентам этого `user_id`; слои памяти не затрагиваются (§6) |

**Автоматического извлечения профиля и предпочтений LLM нет.** Рабочая и
долговременная память, а также профиль наполняются только решением
пользователя — через формы вкладок, раздел профиля или соответствующие запросы
к API (что видно в §7, шаги 1 и 3, и в §6.8).

### 4.3 Что именно уходит в контекст

| Слой | Как попадает в запрос |
|---|---|
| 👤 Профиль пользователя | блок персонализации — **первым** в системном сообщении, если профиль не пуст (§4.4) |
| 🗂 Рабочая | **все** записи активной задачи, блоком «Рабочая память (данные текущей задачи, используй как опорные; при противоречии важнее свежая реплика):» |
| 🧠 Долговременная | до `LONG_TERM_LIMIT = 5` записей: сначала совпавшие по ключевым словам запроса или по упоминанию категории, затем добор самыми уверенными; блок «Долговременная память (профиль, предпочтения, решения, знания — устойчивые данные о пользователе):» |
| 👤 Краткосрочная | по наследованной из дня 10 стратегии: последние `window_size` реплик, последние `keep_last_messages` непокрытых конспектом или вся история активной ветки |

Порядок блоков системного сообщения: **блок профиля** → `system_prompt` →
рабочая память → долговременная память → конспект (если есть) → факты (только
`sticky_facts`). Все блоки вкладываются в **одно** системное сообщение: если ни
один блок не заполнен, отдельного system-сообщения в запросе нет вовсе.

### 4.4 Профиль в системном промпте

`Agent.__init__` читает профиль из БД по `cfg.user_id`
(`self.profile = self.profile_store.load(self.user_id)`). Профиля нет — агент
работает как обычно, без ошибки, просто без персонализации.

Блок профиля собирает `Agent._system_message(...)`, и он стоит **первым**: это
постоянная инструкция пользователя, одинаковая во всех запросах, и она не должна
теряться за блоками памяти. Так как блок — часть системного сообщения, он
попадает в контекст при **любой** стратегии (`sliding_window`, `sticky_facts`,
`branching`, `summary`) и учитывается в оценке токенов (токены блока входят в
общие `prompt_tokens` / `sent_context_tokens`; оценки трёх слоёв в `memory`
считают только слои).

Состав блока — по строке на заполненное поле, в таком порядке:

```
Профиль пользователя (персонализация; соблюдай в каждом ответе):
Обращайся к пользователю по имени: <name>.
Стиль общения: <текст по tone>
Формат ответа: <текст по format>
Длина ответа: <текст по verbosity>
Язык ответа: <текст по language>
Жёсткое ограничение: весь ответ не длиннее <N> символов.
Не обсуждай темы: <a>, <b>. Если запрос про них — вежливо откажись и предложи другую формулировку.
Всегда добавляй в ответ: <дисклеймеры>.
Дополнительные инструкции пользователя (выполняй буквально):
- <инструкция 1>
- <инструкция 2>
```

Точные тексты по значениям перечислений:

| Поле | Значение | Что попадает в промпт |
|---|---|---|
| `tone` | формальный | «на «Вы», без сленга и эмодзи, официальные формулировки» |
| `tone` | дружелюбный | «тепло и просто, уместны эмодзи и обращение к собеседнику напрямую» |
| `tone` | технический | «точные термины и конкретика, без вводных фраз, эмодзи и «воды»» |
| `format` | markdown | «заголовки, списки, блоки кода» |
| `format` | структурированный | «нумерованные разделы с подписями (например: 1. Анализ, 2. Решение, 3. Проверка)» |
| `format` | plain text | «простой текст без markdown-разметки» |
| `verbosity` | кратко | «только суть, без прелюдий и повторов» |
| `verbosity` | подробно | «с пояснениями, примерами и обоснованием» |
| `verbosity` | сбалансировано | «суть плюс короткое пояснение ключевых мест» |
| `language` | русский | «Язык ответа: русский.» |
| `language` | английский | «Язык ответа: английский — отвечай на английском.» |

Незаполненное поле (`None`, в интерфейсе — «— не задано —») в промпт не попадает
вовсе.

Чем профиль отличается от слоёв памяти:

* **краткосрочная** — реплики диалога; профиль её не читает и не пишет.
  «🆕 Новая сессия» очищает диалог, но профиль не трогает: персонализация та же;
* **рабочая** — данные задачи; `PUT /memory/task` переключает задачу, профиль не
  меняется. Блок профиля и блок рабочей памяти сосуществуют в промпте (профиль —
  раньше);
* **долговременная** — записи `profile`/`preference`/`decision`/`knowledge`,
  отбираемые по ключевым словам запроса: это **данные** для ответа, а не
  инструкции о стиле. Профиль — таблица `user_profiles` по `user_id`: одни и те
  же настройки применяются ко всем агентам пользователя, ко всем его задачам и
  сессиям, меняются на лету и не зависят от того, что попало в долговременную
  память.

## 5. Работа со слоями в интерфейсе

### 5.1 Создать агента и задачу

Создание агента — в сайдбаре, блок **«➕ Новый агент»** (форма
`create_agent_form`, очищается после отправки): «Имя агента», «Профиль
пользователя (user_id)» (§6.5), «Модель», «Температура», «Системный промпт
(роль)», «max_tokens», «Сжимать историю в конспект», «Последних реплик «как
есть»», «Сжимать каждые N новых реплик» → кнопка «Создать агента». Новый агент
сразу становится активным; в сайдбаре появляется строка вида
`Конспектёр · deepseek-chat · 0 сообщений · 🗜 сжатие`.

Задача нужна рабочей памяти. В сайдбаре, в блоке «🗂 Задача и сессия», введите
идентификатор в поле **«Новая задача (task_id)»** (например, `tz-portal`) и
нажмите **«➕ Создать задачу»** — задача станет активной с нулём записей.
Идентификатор по умолчанию — `default`.

### 5.2 Вкладка «👤 Краткосрочная»

* Подзаголовок — **«👤 Краткосрочная память (текущая сессия)»**.
* Подпись: `Сессия **session_id** · реплик: **N** · слой очищается кнопкой
  «🆕 Новая сессия» и командой ниже.`
* Таблица — **«роль / текст / создано»** (текст обрезан до 200 символов).
* Кнопка **«🧹 Очистить краткосрочную память»** (`DELETE /memory/short-term`)
  удаляет реплики текущей сессии; рабочая и долговременная память не
  затрагиваются. Пустой слой показывает подсказку, что реплики появятся после
  первого сообщения.

### 5.3 Вкладка «🗂 Рабочая»

* Подзаголовок — **«🗂 Рабочая память (текущая задача)»**.
* Подпись: `Задача **task_id** · записей: **N** · слой переживает смену сессии и
  очищается только вручную (или сменой задачи).`
* Форма **«Добавить/обновить запись»** (ввод существующего ключа перезапишет
  значение — upsert): поля **«Ключ»** (placeholder «например: цель») и
  **«Значение»**, кнопка **«💾 Сохранить»** → `POST /memory/working`.
* Таблица — **«ключ / значение / обновлено»**.

Держите записи короткими и по делу: они уходят в **каждый** запрос задачи.

### 5.4 Вкладка «🧠 Долговременная»

* Подзаголовок — **«🧠 Долговременная память (между сессиями)»**, подпись про
  устойчивые данные о пользователе.
* Селектор **«Фильтр по категории»**: «все категории» плюс `👤 профиль`,
  `⭐ предпочтение`, `✅ решение`, `📚 знание` — фильтрует и таблицу, и селектор
  удаления.
* Форма **«Добавить/обновить запись»** (upsert по категории и ключу):
  **«Категория»**, **«Ключ»** (placeholder «например: язык_интерфейса»),
  **«Значение»** и слайдер **«Уверенность»** (0.0–1.0, шаг 0.05, по умолчанию
  1.0). Кнопка **«💾 Сохранить»** → `POST /memory/long-term`.
* Таблица — **«id / категория / ключ / значение / уверенность»**.
* Удаление: селектор **«Удалить запись по id»** + кнопка **«🗑 Удалить»**
  (`DELETE /memory/long-term/{entry_id}`); если записи нет, бэкенд отвечает
  `404`.

> [i] Записи категории `profile` в **долговременной** памяти — это обычные
> данные агента (например, «роль пользователя: аналитик»). Они не связаны с
> профилем пользователя дня 12 и не влияют на стиль ответов: персонализация
> живёт в отдельной таблице `user_profiles` (§4.4, §6).

### 5.5 Задача и сессия (сайдбар, блок «🗂 Задача и сессия»)

* Подпись: `Сессия: **session_id** · задача: **task_id**`.
* Селектор **«Активная задача»** + кнопка **«🔀 Переключить задачу»**
  (`PUT /memory/task`): в следующих запросах фильтруется рабочая память; диалог
  и краткосрочный слой не меняются. Список задач наполняется из
  `GET /memory/working` (`tasks`).
* Поле **«Новая задача (task_id)»** + кнопка **«➕ Создать задачу»** — то же
  переключение, но на новый идентификатор.
* Кнопка **«🆕 Новая сессия»** (`POST /memory/session`): реплики прошлой сессии,
  конспекты и факты удаляются, у агента появляется новый `session_id`. **Рабочая
  и долговременная память, а также профиль пользователя сохраняются** — это и
  показывает §8.

### 5.6 Индикатор «🧭 Что ушло в последний запрос»

Заголовок **«🧭 Что ушло в последний запрос»**, сразу под панелями слоёв, читает
`record["memory"]` последнего **успешного** ответа `POST /generate`:

* три метрики — **«👤 Краткосрочная»**, **«🗂 Рабочая»**, **«🧠 Долговременная»**
  — со значением «N записей · M токенов»; подсказка метрики содержит подробности
  слоя (`details`);
* подпись: `Сессия **session_id** · задача **task_id** · всего по слоям:
  **total_tokens** токенов (короткая X + рабочая Y + долговременная Z)`;
* строка **«Использованы в запросе: …»** — только те слои, у которых
  `used = true`;
* строка **«Ключевые слова запроса (отбор долговременных записей): …»**.

До первого сообщения (и сразу после «🆕 Новая сессия») блок пишет: «Слои памяти:
индикация появится после первого сообщения». Токены самого нового промпта не
принадлежат слоям — реплика становится памятью только после успешного хода,
поэтому в **первой** реплике новой сессии краткосрочный слой даёт `0` токенов
(рабочая и долговременная при этом уже на месте).

Источник полей — `record["memory"]` ответа `POST /agents/{id}/generate`:
`session_id`, `task_id`, `layers[{layer, used, entries, tokens, details}]`,
`short_term_tokens` / `working_tokens` / `long_term_tokens` / `total_tokens`,
`keywords`. Токены блока профиля сюда не входят: они часть системного промпта
запроса — их видно в `usage.prompt_tokens` и в `record["profile"]` (§6.7).

### 5.7 Первый диалог: что ввести и что ожидать

Диалог — в самом низу раздела «💬 Чат и память»: заголовок **«💬 Диалог»**, под
ним сообщения, затем поле **«Сообщение агенту»** и кнопка **«🚀 Отправить»**
(отдельной строкой ниже — **«🧹 Очистить историю»**); между сообщениями и
полем ввода стоит expander «⚖️ Сравнить режимы» (§11). Пока агент не создан,
полей нет вовсе.

1. Создайте агента (§5.1) — поле ввода появляется сразу, никаких
   дополнительных шагов не нужно.
2. Введите первую реплику, например:
   `Привет! Начинаем собирать требования к корпоративному порталу.`
3. Нажмите **«🚀 Отправить»** (в поле работает и Ctrl+Enter) — текст уходит как
   есть, терять фокус полю не нужно.
4. Что ожидать:
   * под полем появляется плашка `Ответ получен за N с · токены … · стоимость
     … · finish_reason … · слои: короткая 0 / рабочая 0 / долговременная 0
     токенов`, а рядом — строка применённого профиля `👤 профиль <user_id>: N
     элементов` (§6.7);
   * в «💬 Диалог» добавляется пара `🧑 Вы` / `🤖 Ассистент` с временем;
   * в «🧭 Что ушло в последний запрос» появляются три метрики по слоям.

На **первой** реплике сессии краткосрочный слой даёт `0 записей · 0 токенов`
(сам новый промпт в слой ещё не входит) — это ожидаемо, а не ошибка. Со второй
реплики там `2 записи`, дальше `4`, `6` и так до `keep_last_messages` (по
умолчанию `6`). Рабочая и долговременная метрики показывают записи, сохранённые
формами вкладок: если ничего не сохраняли — там `0 записей · 0 токенов`.

Если нажать «🚀 Отправить» с пустым полем, ничего не отправляется и появляется
подпись «Пустое сообщение не отправлено: введите текст.»

## 6. Профиль пользователя: создание, редактирование, переключение, кастомные инструкции

### 6.1 Где живёт профиль и почему раздел, а не вкладка

Профиль — отдельный **раздел** приложения, а не вкладка внутри «💬 Чат и память».
Переключатель разделов (`st.radio` «Раздел») стоит **вверху основной области**:
**«💬 Чат и память»** и **«👤 Профиль пользователя»**. Выбран radio, а не
`st.tabs`, потому что Streamlit не сохраняет выбор вкладки между перезапусками
скрипта, а после «💾 Сохранить профиль» выполняется `st.rerun`: с radio
пользователь остаётся в том же разделе и видит результат сохранения, с вкладками
его выбрасывало бы на первую вкладку.

Подзаголовок раздела — **«👤 Профиль пользователя»**, под ним подпись: профиль
применяется ко **всем** запросам выбранного пользователя, системный промпт
каждого запроса собирается из обращения, стиля (tone), формата (format), длины
(verbosity), языка, ограничений (constraints) и произвольных инструкций
(custom_instructions); изменения действуют сразу, перезапуск агентов не нужен.

Порядок блоков раздела сверху вниз:

1. выбор профиля («Профиль») и форма создания нового («Новый профиль: user_id»);
2. **«⚡ Готовые профили»** — три кнопки демонстрации;
3. **«✏️ Редактирование профиля `<user_id>`»** — форма, предпросмотр блока
   промпта и «🗑 Удалить профиль»;
4. **«🔀 Профиль активного агента»** (быстрое переключение) + таблица элементов
   применённого профиля + expander «Итоговый системный промпт (без блоков памяти
   задачи)»;
5. **«📊 Сравнение двух профилей на одном вопросе»** (§6.6).

### 6.2 Создать профиль

**Пустой профиль вручную.** Слева — селектор **«Профиль»** со списком из
`GET /users` (подпись варианта — `<user_id> · <summary>`), под ним строка
«Обновлён: <дата> · пользователь `user_id`». Справа — форма
**«Новый профиль: user_id»**: поле идентификатора (placeholder `ivan`,
латиница/цифры, до 64 символов) и кнопка **«➕ Создать профиль»** (`POST
/users/{user_id}/profile`). Пустое значение даёт предупреждение «Укажите user_id
нового профиля.»; занятый `user_id` — `409` (§6.8). Созданный профиль пуст («—
не задано —» во всех полях) и в промпт ничего не добавляет, пока его не
заполнят в форме редактирования (§6.3). Если профилей нет вовсе, раздел пишет:
«Профилей пока нет. Создайте первый — он начнёт влиять на запросы сразу, без
перезапуска агентов.»

**Готовые профили — одним нажатием.** Блок **«⚡ Готовые профили»** (подпись
«создаются или обновляются одним нажатием») показывает три кнопки; данные берутся
из `DEMO_PROFILES` (модуль `backend/demo_profiles.py` — его импортируют и
интерфейс, и скрипт отчёта, поэтому настройки в UI и в отчёте не расходятся):

| Кнопка | `user_id` | Настройки | Чего ожидать в ответе |
|---|---|---|---|
| **Строгий технический** | `strict_tech` | имя `Инженер`, tone=технический, verbosity=кратко, language=русский, format=plain text, предел длины 600 символов | сухой ответ без разметки и вступлений: термины и план действий, не длиннее 600 символов |
| **Дружелюбный наставник** | `friendly_mentor` | имя `Илья`, tone=дружелюбный, verbosity=подробно, format=markdown, запрещённая тема «политика», инструкции «Объясняй простыми словами, используй аналогии» и «Обращайся ко мне по имени» | тёплый подробный ответ со списками и markdown-разметкой |
| **Оркестратор процесса** | `process_orchestrator` | имя `Тимлид`, tone=технический, verbosity=сбалансировано, format=структурированный, дисклеймер «Порядок ролей согласован с тимлидом», инструкции «При запросе «напиши фичу» следуй порядку: аналитик → разработчик → тестировщик» и «Всегда предлагай два варианта решения» | работа раскладывается по ролям именно в этом порядке |

Нажатие создаёт профиль, если его ещё нет, и обновляет, если он уже есть;
подсказка кнопки (`help`) показывает ожидаемый эффект и `user_id`. Для
демонстрации достаточно нажать первые две кнопки — профили с противоположными
настройками нужны панели сравнения (§6.6).

### 6.3 Отредактировать профиль

Выберите профиль в селекторе **«Профиль»** — ниже появится блок
**«✏️ Редактирование профиля `<user_id>`»** с формой (кнопка сохранения —
**«💾 Сохранить профиль»**):

| Поле формы | Что задаёт | Границы и особенности |
|---|---|---|
| **«Имя для обращения»** | строку промпта «Обращайся к пользователю по имени: …» | до 100 символов; пусто — обращения по имени нет |
| **«Стиль общения (tone)»** | тон ответов | `формальный` / `дружелюбный` / `технический` (§4.4) |
| **«Длина ответа (verbosity)»** | подробность | `кратко` / `подробно` / `сбалансировано` |
| **«Язык ответа (language)»** | язык | `русский` / `английский` |
| **«Формат ответа (format)»** | разметку | `markdown` / `plain text` / `структурированный` |
| **«Максимальная длина ответа, символов (0 — без ограничения)»** | жёсткий предел длины | 20…8000; `0` — без ограничения (в промпт строка не попадает) |
| **«Запрещённые темы (через запятую)»** | темы, которые нельзя обсуждать | до 20 тем по 100 символов; можно перечислять через запятую или точку с запятой, дубли убираются |
| **«Обязательные дисклеймеры (по одному в строке)»** | вставки в каждый ответ | до 20 штук по 500 символов |
| **«Произвольные инструкции (по одной в строке)»** | поведение агента | до 30 инструкций по 500 символов, суммарно до 4000 символов (§6.4) |

В каждом селекторе есть значение **«— не задано —»** — это `None`: поле не
навязывается и в системный промпт не попадает.

* Сохранение формы — `PUT /users/{user_id}/profile`: настройки **заменяются
  целиком**, поэтому поля, оставленные «— не задано —», сбрасываются в «не
  настроено». `created_at` профиля сохраняется, `updated_at` обновляется.
* После сохранения всплывает сообщение `Профиль **user_id** обновлён · <summary>
  · применён к агентам: N` — живые агенты этого `user_id` получили новые
  настройки немедленно.
* Справа под формой — предпросмотр **«Что уходит в системный промпт (блок
  профиля)»**: готовый текст блока считается локально, без обращения к API. Если
  все поля пусты, вместо него подпись «Профиль пуст: в системный промпт ничего не
  добавляется, агент отвечает как обычно.»
* Кнопка **«🗑 Удалить профиль»** (`DELETE /users/{user_id}/profile`) удаляет
  профиль; агенты пользователя остаются и продолжают работать, но без
  персонализации (внешнего ключа между таблицами нет — §4.1).
* Ошибки валидации: неизвестное значение перечисления, неизвестное поле объекта
  или выход за границы → `422` (§13).

### 6.4 Как добавить кастомную инструкцию

Поле **«Произвольные инструкции (по одной в строке)»** — то, чем профиль
настраивается под конкретную работу. Примеры (все они попадут в промпт
дословно):

* `Обращайся ко мне по имени`
* `Всегда предлагай два варианта решения`
* `При запросе «напиши фичу» следуй порядку: аналитик → разработчик → тестировщик`
* `Объясняй простыми словами, используй аналогии`

Правила:

* **одна инструкция — одна строка**; маркеры списка «`-`», «`*`», «`•`» и
  нумерация вида «`1.`» / «`1)`» допустимы — они отбрасываются при сохранении;
  пустые строки игнорируются, дубли схлопываются;
* до **30 инструкций**, каждая до **500 символов**, вся строка целиком — до
  4000 символов; за границами — `422`;
* каждая инструкция становится отдельной строкой блока «Дополнительные
  инструкции пользователя (выполняй буквально):» с маркером «-» и уходит в
  **каждый** запрос;
* placeholder поля показывает пример: «При запросе «напиши фичу» следуй порядку:
  аналитик → разработчик → тестировщик».

Отличие от настроек стиля: `tone`/`verbosity`/`format` описывают, **как** отвечать,
а произвольные инструкции — **что делать** (порядок ролей, число вариантов,
обязательные шаги). Проверить итог можно предпросмотром блока промпта (§6.3) и
expander-ом «Итоговый системный промпт» (§6.5).

### 6.5 Применить профиль к агенту

**При создании агента.** В сайдбаре, в форме **«➕ Новый агент»**, есть селектор
**«Профиль пользователя (user_id)»** — чей профиль подключать к системным
промптам агента. В списке вариантов первым всегда идёт `default` плюс все
созданные профили (§6.2). Выбранный `user_id` уходит в тело `POST /agents`.

**Переключение живого агента.** В разделе «👤 Профиль пользователя» есть блок
**«🔀 Профиль активного агента»** (быстрое переключение): подпись сообщает, какой
профиль использует активный агент («Агент **имя** (`agent_id`) использует профиль
`user_id`. Переключите пользователя — и следующий запрос уйдёт с другим системным
промптом.»), ниже — селектор **«Профиль для агента»** и кнопка **«Применить»**
(`PATCH /agents/{agent_id}` с `user_id`).

**Перезапуск не нужен:** агент перечитывает профиль, и **следующий же** запрос
уходит с новым системным промптом. Диалог, активная задача и слои памяти при
переключении не меняются — персонализация к ним не привязана (§4.4).

Тут же показано, что именно применено:

* таблица **«элемент / значение»** — по строкам применённого профиля (обращение,
  стиль, формат, длина, ограничения, инструкции);
* expander **«Итоговый системный промпт (без блоков памяти задачи)»** — как
  выглядит системное сообщение агента вместе с профилем (без рабочей и
  долговременной памяти текущего запроса). Источник — `GET
  /agents/{agent_id}/profile`;
* если у профиля нет заполненных полей, вместо таблицы подпись «У профиля нет
  заполненных полей: персонализация не применяется.»

### 6.6 Быстрое сравнение двух профилей (для видео)

Панель **«📊 Сравнение двух профилей на одном вопросе»** внизу раздела профиля
делает то же, что делает отчёт (§9), но в интерфейсе: создаются **два временных
агента** (по одному на профиль), им задаётся **один и тот же** вопрос, после
прогона агенты **удаляются**. Так разница ответов объясняется только профилем, а
не историей диалога.

1. Нужно минимум два профиля — иначе панель пишет: «Нужно минимум два профиля:
   нажмите «Строгий технический» и «Дружелюбный наставник» выше.» (§6.2).
2. Выберите **«Профиль A»** и **«Профиль B»** (в подписи — `user_id · summary`).
   По умолчанию подставляются два готовых профиля с противоположными
   настройками.
3. Поле **«Вопрос обоим профилям»** уже заполнено демонстрационным вопросом
   (`DEMO_QUESTION` = «Как ускорить медленный SQL-запрос в PostgreSQL?»).
4. Нажмите **«🚀 Спросить оба профиля»** — идут два запроса к DeepSeek, это
   занимает несколько секунд. Пустой вопрос и одинаковые профили отклоняются
   предупреждениями.

Результат — два столбца рядом:

* `<user_id>` и краткое описание настроек;
* токены и время ответа;
* сам ответ;
* **«Что повлияло на ответ»** — таблица «элемент / значение» из `elements`
  применённого профиля (только те поля, которые реально дали строку промпта);
* expander **«Системный промпт запроса»** — системное сообщение того запроса.

Если один профиль не ответил (например, `502` без ключа), ошибка показывается в
его столбце, а второй ответ остаётся на экране.

Режим «**один агент — переключили профиль — тот же вопрос**»: задайте вопрос
агенту в разделе «💬 Чат и память», затем вернитесь в профиль, переключите
профиль живого агента (§6.5) и задайте **тот же** вопрос ещё раз. В диалоге
видны оба ответа (история не сбрасывается), а плашка под полем показывает уже
другой профиль — наглядное доказательство, что персонализация меняется на лету.

### 6.7 Что видно в чате

* **Плашка после ответа** в разделе «💬 Чат и память» содержит строку вида
  `👤 профиль strict_tech: 6 элементов` — `user_id` и число элементов профиля,
  реально попавших в промпт. Если профиль не выбран, пуст или `default` без
  настроек — `👤 профиль: без персонализации`.
* **Карточка агента** над панелями слоёв содержит строку «Профиль пользователя
  (день 12): `user_id`» — из неё всегда видно, чей профиль подключён к агенту.
  В списке агентов в сайдбаре профиль не выводится
  (там `имя · модель · сообщения · стратегия · задача`) — его смотрят в карточке
  агента или в блоке «🔀 Профиль активного агента» (§6.5).
* **Expander «Итоговый системный промпт (без блоков памяти задачи)»** в разделе
  профиля (§6.5) читает `GET /agents/{agent_id}/profile` и показывает
  `system_prompt` — то, что уйдёт в запрос вместе с блоками памяти, — а таблица
  «элемент / значение» и поле `prompt_block` объясняют, из чего он собран.

### 6.8 Персонализация через API (curl.exe и requests)

Все примеры — с бэкендом из §3 (`http://127.0.0.1:8000`); форматы тел и коды
ошибок совпадают с интерфейсом. Тело профиля описывает его **целиком**
(`extra="forbid"`: неизвестное поле → `422`).

Создать профиль (`POST`, ответ `201`, занятый `user_id` → `409`):

```powershell
curl.exe -X POST http://127.0.0.1:8000/users/ivan/profile ^
  -H "Content-Type: application/json" ^
  -d "{\"name\":\"Иван\",\"preferences\":{\"tone\":\"дружелюбный\",\"verbosity\":\"подробно\",\"language\":\"русский\",\"format\":\"markdown\"},\"constraints\":{\"max_response_length\":1200,\"forbidden_topics\":[\"политика\"],\"required_disclaimers\":[\"Это оценка, а не гарантия\"]},\"custom_instructions\":\"Обращайся ко мне по имени\nВсегда предлагай два варианта решения\"}"
```

Заменить настройки (`PUT`, профиля нет → `404`, в ответе — `applied_to_agents`):

```powershell
curl.exe -X PUT http://127.0.0.1:8000/users/ivan/profile ^
  -H "Content-Type: application/json" ^
  -d "{\"name\":\"Иван\",\"preferences\":{\"tone\":\"технический\",\"verbosity\":\"кратко\"},\"constraints\":{\"max_response_length\":600},\"custom_instructions\":\"Всегда предлагай два варианта решения\"}"
```

Прочитать профиль (`GET`, нет профиля → `404`), список всех профилей и профиль,
применённый к агенту:

```powershell
curl.exe http://127.0.0.1:8000/users
curl.exe http://127.0.0.1:8000/users/ivan/profile
curl.exe http://127.0.0.1:8000/agents/<agent_id>/profile
```

Удалить профиль (`DELETE`, ответ `{"status": "deleted", "user_id": ...}`; агенты
остаются без персонализации):

```powershell
curl.exe -X DELETE http://127.0.0.1:8000/users/ivan/profile
```

Переключить профиль **живого** агента (`PATCH`; `user_id` — часть общего
частичного обновления агента, рядом с `strategy`, `window_size` и т. п.):

```powershell
curl.exe -X PATCH http://127.0.0.1:8000/agents/<agent_id> ^
  -H "Content-Type: application/json" -d "{\"user_id\":\"friendly_mentor\"}"
```

То же на Python (`requests`), с проверкой, что профиль реально попал в запрос:

```python
import requests

BASE = "http://127.0.0.1:8000"

profile = {
    "name": "Иван",
    "preferences": {"tone": "технический", "verbosity": "кратко",
                    "language": "русский", "format": "plain text"},
    "constraints": {"max_response_length": 600},
    "custom_instructions": "Всегда предлагай два варианта решения",
}
created = requests.post(f"{BASE}/users/ivan/profile", json=profile, timeout=30)
print(created.status_code, created.json()["summary"])      # 201 · описание профиля

agent = requests.post(f"{BASE}/agents",
                      json={"name": "Иван-агент", "user_id": "ivan"},
                      timeout=30).json()
applied = requests.get(f"{BASE}/agents/{agent['agent_id']}/profile",
                       timeout=30).json()
print(applied["personalized"], len(applied["elements"]))
print(applied["prompt_block"])                             # блок персонализации
record = requests.post(f"{BASE}/agents/{agent['agent_id']}/generate",
                       json={"prompt": "Как ускорить медленный SQL-запрос?"},
                       timeout=90).json()
print(record.get("system_prompt"))                         # промпт запроса
```

Коды ответов: `201` — профиль создан, `200` — чтение/обновление/удаление,
`404` — нет профиля или агента, `409` — профиль с таким `user_id` уже есть,
`422` — невалидные поля (значение перечисления, границы, неизвестное поле),
`502` — сбой генерации у DeepSeek (поля `profile` и `system_prompt` в ответе при
этом заполнены — профиль считается до вызова модели).

## 8. Проверка 2: как слои влияют на ответы

Здесь нужен ключ DeepSeek (§2) — сравнение идёт по смыслу ответа. Числа из
`record["memory"]` детерминированы и проверяются всегда, формулировка модели
свободная: сверяйте смысл, а не строку.

### 8.1 Долговременная память

Начинайте на свежем агенте, чтобы числа слоёв были однозначны.

| Шаг | Действие | Что должно быть в индикаторе | Что в ответе |
|---|---|---|---|
| а | задать вопрос «На каком языке должен быть интерфейс портала?» | «🧠 Долговременная» — `0 записей · 0 токенов` | модель ничего не знает о предпочтении (уточняет или отвечает обобщённо) |
| б | сохранить `preference / язык_интерфейса: русский` и задать тот же вопрос | «🧠 Долговременная» — `1 запись` (и токены > 0) | ответ учитывает русский язык интерфейса |
| в | нажать «🆕 Новая сессия» и задать тот же вопрос | краткосрочная `0` токенов, долговременная — по-прежнему `1 запись` | предпочтение снова учтено, хотя диалог пуст |

Примеры фактических ответов (формулировка свободная, сверяйте смысл): (а) общий
ответ про аудиторию портала, без упоминания русского; (б) «Судя по вашему
профилю — язык интерфейса: **русский**»; (в) «Интерфейс портала должен быть на
русском языке.»

Шаг «в» — главное доказательство: сессии сменились, диалога нет, а ответ
по-прежнему опирается на долговременный слой.

### 8.2 Рабочая память

| Шаг | Действие | Что должно быть в индикаторе | Что в ответе |
|---|---|---|---|
| а | в задаче `tz-portal` сохранить `ограничение: только on-premise`, спросить «Можно ли разместить в облаке?» | «🗂 Рабочая» — `1 запись` | ответ учитывает ограничение (облако не подходит: «у вас зафиксировано ограничение — только on-premise») |
| б | нажать «🆕 Новая сессия», переключиться на задачу `tz-cloud` (§5.5) и задать тот же вопрос | «🗂 Рабочая» — `0 записей · 0 токенов`, краткосрочная — `0` токенов | ограничение не упоминается — оно принадлежит другой задаче, а диалог пуст |
| в | нажать «🆕 Новая сессия», вернуться на `tz-portal` и задать тот же вопрос | «🗂 Рабочая» — `1 запись` | ограничение снова в ответе |

Примеры фактических ответов: (а) «Нет, нельзя. Есть ограничение: только
on-premise.»; (б) общий ответ про размещение в облаке, ограничение не
упомянуто; (в) «Нет. У вас зафиксировано ограничение — только on-premise.»

Так видно, что рабочая память привязана к `task_id`, а не к диалогу: сам диалог
при переключении задачи не теряется.

> [i] Шаги «🆕 Новая сессия» в (б) и (в) обязательны. В той же сессии
> предыдущий ответ про on-premise остаётся в **краткосрочном** слое, и модель
> цитирует ограничение из диалога — тогда опыт доказывает работу диалога, а не
> рабочей памяти. С пустой сессией единственный источник ограничения — записи
> задачи, и разница между `tz-portal` и `tz-cloud` видна однозначно.

### 8.3 Профиль: ответ меняется без изменения памяти

Профиль работает поверх слоёв и не зависит от них (§4.4). На свежем агенте с
профилем `default` (без настроек):

| Шаг | Действие | Что должно быть в ответе |
|---|---|---|
| а | задать вопрос «Как ускорить медленный SQL-запрос в PostgreSQL?» | ответ в обычном стиле агента; плашка `👤 профиль: без персонализации` |
| б | применить к живому агенту профиль `strict_tech` (§6.5) и задать тот же вопрос | сухой ответ без разметки, укладывающийся в предел 600 символов; плашка `👤 профиль strict_tech: N элементов` |
| в | применить профиль `friendly_mentor` и задать тот же вопрос | тёплый подробный ответ с markdown-списками; диалог не сброшен — видны все три ответа |
| г | нажать «🆕 Новая сессия» и задать тот же вопрос | профиль тот же (`friendly_mentor`): персонализация сохраняется вместе с профилем, а не с диалогом |

Формулировки свободные, строгий предел длины модель соблюдает приблизительно —
сверяйте стиль, формат и наличие ограничения, а не точное число символов. Что
проверяется жёстко — что блок профиля **попал** в промпт: это видно в
`record["profile"]["elements"]` и в expander-е «Итоговый системный промпт»
(§6.5), а также в отчёте (§9).

(«Как ускорить медленный SQL-запрос в PostgreSQL?») → «🚀 Спросить оба профиля».
Показать два столбца с ответами, таблицы «Что повлияло на ответ» и expander-ы
«Системный промпт запроса». Проговорить: агенты временные и удаляются, поэтому
разница — только из-за профиля, а не из-за истории диалога.

**Кадр 3 — переключение профиля живого агента (1 мин).** Вернуться в «💬 Чат и
память», задать тот же вопрос агенту с профилем `default`, затем в блоке
«🔀 Профиль активного агента» выбрать `friendly_mentor` → «Применить» → задать
тот же вопрос ещё раз. Видно: ответ изменился по стилю и длине, диалог не
потерялся, агент не перезапускался, а плашка под полем показывает
`👤 профиль friendly_mentor: N элементов` (§6.7).

**Кадр 4 — кастомная инструкция (1 мин).** Применить профиль «Оркестратор
процесса» (готовый, §6.2) и задать «напиши фичу: экспорт отчётов в Excel»:
ответ раскладывается на аналитик → разработчик → тестировщик. Показать
предпросмотр блока промпта в форме профиля (§6.3) и expander «Итоговый системный
промпт» (§6.5) — видно строку «Дополнительные инструкции пользователя».

**Кадр 5 — слои памяти на месте (1 мин).** Переключиться на вкладку «🧠 Слои
памяти агента»: рабочая задача `tz-portal` и долговременные записи как были,
«🆕 Новая сессия» очищает только диалог, «🧭 Что ушло в последний запрос»
показывает те же слои — персонализация к ним не привязана (§4.4). Тут же задать
вопрос после новой сессии: профиль по-прежнему влияет на ответ.

**Кадр 6 — офлайн-прогон и отчёт (1 мин).** Запустить
`python personalization_comparison.py --no-api` (быстро, без сети) и затем
`python personalization_comparison.py`; открыть `personalization_comparison.md`:
таблица «Профиль | Настройки | Ответ агента | Какие элементы профиля повлияли»,
системные промпты и наблюдения. Отметить, что это отдельная БД
`personalization_demo.db`, а отчёт дня 11 по слоям памяти лежит в
[`../../day11/memory_layers_comparison.md`](../../day11/memory_layers_comparison.md).

**Финал (30 сек).** Вывод: профиль подставляется **первым** блоком системного
промпта каждого запроса, применяется ко всем агентам пользователя, меняется на
лету (без перезапуска) и живёт отдельно от трёх слоёв памяти.

## 12. Просмотр SQLite

База — обычный файл `day12/agents.db`, смотреть можно без установки чего-либо
лишнего. Примеры выполняются из папки `day12`; порядок — по слоям, затем
персонализация.

Краткосрочная память (реплики сессий; при сжатии не удаляются, при новой сессии
прошлая сессия удаляется):

```powershell
.venv/Scripts/python -c "import sqlite3; print(sqlite3.connect('agents.db').execute('select id, agent_id, session_id, role, substr(content,1,60), created_at from short_term_messages order by id').fetchall())"
```

Рабочая память (пары задача+ключ уникальны):

```powershell
.venv/Scripts/python -c "import sqlite3; print(sqlite3.connect('agents.db').execute('select agent_id, task_id, key, value, updated_at from working_memory order by task_id, key').fetchall())"
```

Долговременная память (категория + ключ уникальны):

```powershell
.venv/Scripts/python -c "import sqlite3; print(sqlite3.connect('agents.db').execute('select agent_id, category, key, value, confidence from long_term_memory order by category, key').fetchall())"
```

Агенты (конфиг, настройки сжатия, стратегия, окно, активные сессия/задача и
профиль пользователя):

```powershell
.venv/Scripts/python -c "import sqlite3; print(sqlite3.connect('agents.db').execute('select agent_id, name, user_id, strategy, window_size, current_session_id, current_task_id, summary_enabled from agents').fetchall())"
```

Профили пользователей (день 12; `user_id` уникален):

```powershell
.venv/Scripts/python -c "import sqlite3; print(sqlite3.connect('agents.db').execute('select id, user_id, name, preferences, constraints, custom_instructions, created_at, updated_at from user_profiles order by user_id').fetchall())"
```

Конспекты (append-only: текущий — последняя строка по `id`):

```powershell
.venv/Scripts/python -c "import sqlite3; print(sqlite3.connect('agents.db').execute('select id, agent_id, covered_from_message_id, covered_to_message_id, covered_messages, source_tokens, summary_tokens, cost from summaries order by id').fetchall())"
```

Метрики, включая поля сжатия и расход по слоям памяти:

```powershell
.venv/Scripts/python -c "import sqlite3; print(sqlite3.connect('agents.db').execute('select id, agent_id, total_tokens, mode, saved_tokens, short_term_tokens, working_tokens, long_term_tokens from token_usage order by id').fetchall())"
```

Факты (стратегия sticky_facts; пара agent_id+key уникальна):

```powershell

```

Чекпоинты/ветки (стратегия branching; parent_id — дерево, messages — JSON-снимок):

## 13. FAQ и возможные проблемы

Сначала — вопросы про профиль пользователя (день 12).

| Проблема | Решение |
|---|---|
| Профиль сохранён, а ответ агента не изменился | Проверьте три вещи: (1) у агента именно тот `user_id` — карточка агента и блок «🔀 Профиль активного агента» (§6.5); (2) у профиля есть заполненные поля — предпросмотр «Что уходит в системный промпт» (§6.3) не должен быть пустым; (3) профиль не пустой: пустой профиль в промпт ничего не добавляет. Персонализация — это инструкция стилю, а не данные: фактических знаний она агенту не добавляет. |
| Профиль не появился в селекторе при создании агента | Список профилей читается при отрисовке сайдбара: нажмите «🔄 Обновить список» и откройте форму «➕ Новый агент» заново (§6.5). |
| `409` при создании профиля | Профиль с таким `user_id` уже есть. Откройте его в селекторе «Профиль» и сохраните форму (§6.3) либо возьмите другой `user_id`. |
| `404` на `/users/{user_id}/profile` | Профиля нет: создайте его формой «➕ Создать профиль» или кнопкой готового профиля (§6.2). `PUT` профиль не создаёт — он только заменяет настройки. |
| `422` при сохранении профиля | Проверьте значения: `tone` / `verbosity` / `language` / `format` — только из списка §6.3, длина ответа 20…8000, тем не больше 20 по 100 символов, дисклеймеров не больше 20 по 500, инструкций не больше 30 по 500 и не больше 4000 символов суммарно. Неизвестное поле тоже даёт `422` (схемы запрещают лишние поля). |
| Сохранил профиль, а часть настроек «сбросилась» | Так и задумано: сохранение формы — это `PUT`, полная замена. Поля, оставленные «— не задано —», становятся «не настроено» и в промпт не попадают. Заполните все нужные поля и сохраните снова. |
| Удалил профиль — агенты пропали? | Нет. Внешнего ключа между `user_profiles` и `agents` нет намеренно: агенты остаются работоспособными и просто теряют персонализацию (§4.1). Их диалог, задачи и долговременная память не затрагиваются. |
| Два профиля дали похожие ответы | Сравнение идёт по смыслу, а не по строке: посмотрите таблицы «Что повлияло на ответ» и системные промпты (§6.6) — если настройки различаются, а модель их проигнорировала, переформулируйте вопрос или сделайте настройки контрастнее (например, `plain text` + предел 600 символов против `markdown` + подробный ответ). Предел длины и формат модель соблюдает приблизительно. |
| Персонализация после «🆕 Новая сессия» исчезла | Не должна: новая сессия очищает только краткосрочный слой, профиль к нему не привязан (§4.4). Проверьте `user_id` агента и заполненность профиля, как в первом пункте; в отчёте §9 шаг (г) проверяет это же. |
| Плашка пишет «без персонализации» | Профиль не выбран, пуст или у выбранного `user_id` нет ни одной заполненной настройки — заполните форму (§6.3) и сохраните: следующий же запрос уйдёт с блоком профиля. |

Теперь — вопросы про слои памяти.

| Проблема | Решение |
|---|---|
| После «🆕 Новая сессия» диалога нет, но рабочая и долговременная память на месте | Так и задумано: сессия — это границы краткосрочной памяти. `POST /memory/session` удаляет реплики прошлой сессии, конспекты и факты, а рабочая (по `task_id`), долговременная (профиль/предпочтения/решения/знания) память и профиль пользователя к диалогу не привязаны. Индикатор после новой сессии показывает `0` записей в краткосрочном слое и прежние числа в двух других. |
| После новой сессии пропал конспект старого диалога — почему? | Конспект (`summaries`) — сжатие **краткосрочного** слоя, то есть производное от конкретного диалога. Если оставить его при смене сессии, устаревшее содержание продолжало бы подставляться в системное сообщение. Факты (`facts`) удаляются по той же причине. Если данные нужно сохранить между сессиями, перенесите их в долговременную память (категория `knowledge` или `preference`) — автоматического переноса нет. |
| Запись рабочей памяти «не сохранилась», а значение изменилось | Это upsert: пара «задача + ключ» уникальна, поэтому повторное сохранение того же ключа перезаписывает значение. Хотите две записи — используйте разные ключи (`цель` и `критерий_приёмки`). |
| Переключил задачу — рабочая память «опустела» | Записи привязаны к `task_id`, поэтому у новой задачи свой набор. Вернитесь к прежней задаче селектором «🔀 Переключить задачу» — записи на месте. Диалог при переключении не теряется. |
| Записей в долговременной памяти больше, чем видно в контексте | В запрос уходит до 5 записей (`LONG_TERM_LIMIT`): сначала совпавшие по ключевым словам запроса (и по упоминанию категории), затем самые уверенные. Поднять лимит — правка `LONG_TERM_LIMIT` в `backend/config.py`. |
| `422` при сохранении долговременной записи | Проверьте: категория — только `profile` / `preference` / `decision` / `knowledge`, `confidence` — от 0 до 1, ключ и значение непустые. Категория `profile` здесь — обычные данные агента, к профилю пользователя дня 12 она отношения не имеет (§5.4). |
| Записал в рабочую память, а индикатор показывает `0 записей` | Проверьте активную задачу (§5.5): запись ушла в другую задачу, либо это первая реплика сессии — в ней краткосрочный слой всегда `0` токенов, а рабочая метрика появится только после успешного хода. |

Общие вопросы:

| Проблема | Решение |
|---|---|
| «🔌 Бэкенд недоступен» в интерфейсе | Запустите бэкенд из папки `day12`: `.venv/Scripts/python -m uvicorn backend.main:app --port 8000`. Проверьте адрес: он должен совпадать с `DAY12_BACKEND_URL` (по умолчанию `http://127.0.0.1:8000`). |
| Порт 8000 (или 8501) занят | Запустите на другом порту: `uvicorn backend.main:app --port 8019` и, для фронтенда, задайте `$env:DAY12_BACKEND_URL="http://127.0.0.1:8019"`; Streamlit — `--server.port 8502`. |
| Генерация вернула `502` «Ключ API не задан» | Ключа нет ни в `day12/.env`, ни в переменной `DEEPSEEK_API_KEY`. Сделайте `copy .env.example .env` и впишите `DEEPSEEK_API_KEY=sk-...`, затем перезапустите бэкенд. Карточки агентов, слои памяти, CRUD профилей и скрипт с `--no-api` работают и без ключа. |
| Ошибка `429` (rate limit) от DeepSeek | Слишком много запросов подряд. Подождите и повторите; для демонстрации делайте паузы между ходами. Панель сравнения профилей тратит **два** запроса сразу, «⚖️ Сравнить режимы» с галочкой — тоже два. |
| `404` на агента | Агент был удалён или `agent_id` указан неверно. Обновите список кнопкой «🔄 Обновить список» и выберите агента заново. |
| `404` при удалении долговременной записи | Записи с таким `id` уже нет (например, её удалили в другой вкладке). Обновите страницу — селектор «Удалить запись по id» перечитает список. |
| `422` при создании/правке агента | Проверьте значения: `temperature` 0.0–2.0, `max_tokens` 1–8192, `keep_last_messages` 2–20, `summarize_every` 2–40, `user_id` — непустая строка до 64 символов. Такой ответ означает ошибку валидации тела запроса. |
| `agents.db` попал в git | Не должен: файлы `*.db` игнорируются. Если он уже отслеживается, уберите из индекса (`git rm --cached day12/agents.db`) — файл останется на диске. |
| Как сбросить эксперимент | «🧹 Очистить историю» удаляет реплики, конспекты, факты, ветки и метрики, сохраняя конфигурацию агента, рабочую и долговременную память. Полный сброс — «🗑 Удалить агента» и создать заново; можно также остановить бэкенд и удалить `day12/agents.db` (таблицы создадутся заново). Профили пользователей живут в той же базе: чтобы начать «с чистого листа», удалите их в разделе «👤 Профиль пользователя». |

Вопросы по наследованным панелям дня 9–10:

| Проблема | Решение |
|---|---|
| Кнопка «Сжать сейчас» отвечает «Сжимать пока нечего» | Это нормально: непокрытых реплик меньше порога `summarize_every`, либо истории нет вовсе. Наберите диалог или уменьшите порог. Отчёт приходит с `created: false` и текстом причины. |
| «Чистая экономия» отрицательная | Конспект оказался дороже заменённых реплик — типично для коротких сообщений. Экономия контекста есть, но на сам конспект ушло больше токенов. Увеличьте `summarize_every` и/или `keep_last`, либо пишите более длинные реплики. |
| Где посмотреть состояние FSM сжатия | В панели «🗜 Сжатие контекста» — подпись «Состояние процесса: …» (`tracking`, `summary_pending`, `summarizing`, `error`). В БД оно не хранится: выводится из watermark, числа непокрытых реплик и порога. Подробнее — [`../../day10/docs/usage.md`](../../day10/docs/usage.md). |
| Оценки tiktoken не совпадают с `usage` API | Это ожидаемо: tiktoken (`cl100k_base`) — приблизительная оценка, у DeepSeek свой токенизатор. Для конкретного запроса/ответа верьте фактическим `usage` из API; на tiktoken построены расчёты контекста, экономии и разбивка по слоям. |
