# День 21 — индексация документов и оптимизация затрат на LLM

Задание дня — **проиндексировать документы, сравнить две стратегии чанкинга и
снизить расходы на LLM**. День 21 надстраивает над агентом дня 20 два слоя:

1. **RAG-слой поиска по документам проекта** — набор документов, две стратегии
   чанкинга, эмбеддинги `sentence-transformers` в FAISS, метаданные чанков в
   SQLite, поиск по индексу и автоматическое сравнение стратегий по метрикам;
2. **оптимизацию затрат** — кэш стабильного префикса промпта, сжатие
   динамической части, предел длины ответа по типу задачи и перенос тяжёлых
   задач в непиковые часы DeepSeek.

Унаследованное приложение дня 20 (агент DeepSeek: память, профиль, состояние
задачи, инварианты, MCP-флот, планировщик, пайплайн, оркестрация) остаётся на
месте. Остальное — копия `day20/`: агент DeepSeek с памятью, профилем, состоянием
задачи, инвариантами, MCP-флотом, планировщиком, пайплайном и оркестрацией; их
описание — в `day20/README.md` и `day20/docs/`.

## Индексация и поиск

### Документы: откуда они берутся

Набор документов — **данные**: таблица `DOCUMENT_SOURCES`
(`backend/domain/document_sources.py`) перечисляет 25 источников репозитория
(README дней 5–20, `docs/architecture.md` дней 9/13/20, четыре исходника с
`ast`-структурой и корневые `AGENTS.md` + `README.md`) с пределом символов на
каждый. Суммарно ≈ 125 000 символов ≈ 70 страниц.

Папку `documents/` **готовить не нужно**: `DocumentLoader` собирает её сам при
первом прогоне (`ensure_documents`), поэтому демо-кнопка работает на свежем клоне.
Каждый документ получает метаданные (заголовок, вид, язык, размер, признак
усечения) и попадает в `documents/manifest.json`. Предел `max_chars` нужен
потому, что README дня 20 весит 285 КБ: целиком он задавил бы остальные документы,
и сравнение стратегий превратилось бы в сравнение одного файла с собой. Усечённый
документ помечается маркером `<!-- документ усечён -->`, и признак усечения едет
в манифест и в отчёт.

Источники перечислены данными:

```python
DOCUMENT_SOURCES = (
    DocumentSource(path="day20/README.md", kind="readme", max_chars=8000),
    DocumentSource(path="day9/backend/context_fsm.py", kind="code", max_chars=12000),
    DocumentSource(path="AGENTS.md", kind="guide", max_chars=8000),
    ...
)
```

`DocumentLoader.collect()` читает источники, обрезает их, определяет метаданные
(заголовок — первый заголовок markdown или первая строка модульного докстринга;
язык — по доле кириллицы) и пишет файлы в `day21/documents/` плюс
`documents/manifest.json`. Пропавший источник не роняет сборку — он пропускается с
записью в лог. `documents/` и `index/` — **производные данные**, в Git они не
попадают (`.gitignore`: `documents/`, `day21/index/`, `*.db`).

### Блоки документа: одна структура для обеих стратегий

`backend/domain/chunking.py` режет текст на блоки и гарантирует, что они делят его
целиком:

* **markdown** — секция от заголовка ATX (`#`…`######`) до следующего заголовка
  **любого** уровня; текст до первого заголовка — преамбула с пустым заголовком;
* **код** — top-level `def`/`async def`/`class` через `ast` (секция начинается со
  строки первого декоратора и тянется до следующей); текст до первого определения —
  блок `module`. Битый Python (`SyntaxError`) не роняет чанкинг: секции ищутся по
  строкам-шаблонам `^(def |class |async def |@)`, а если и их нет — блоком
  становится весь файл;
* **plain text** — абзацы, разделённые пустой строкой.

Блоки делят текст **без пропусков и перекрытий**, поэтому `content` любого чанка —
**срез исходного текста**, а `start_char`/`end_char` точны. Иерархия markdown НЕ
разворачивается в перекрывающиеся секции (иначе один текст попал бы в индекс
дважды), а уровень заголовка сохраняется в `section_level`.

### Стратегии чанкинга

`backend/services/chunker.py` содержит обе реализации за одним интерфейсом
(`chunk(document) -> list[Chunk]`), поэтому сравнение идёт на одном и том же входе.

| стратегия | правило | что даёт |
|---|---|---|
| `fixed` | окна по **512 токенов** с перекрытием **50**: окно набирается из блоков документа (абзац или секция не рвётся посередине), блок длиннее окна режется внутри себя | ровные чанки, 100 % покрытие документа, перекрытие не теряет факт на стыке |
| `structural` | чанк — **секция**: заголовок markdown, top-level `def`/`async def`/`class` с декораторами (`ast`) или абзац plain text | заголовок раздела в метаданных, но чанки разного размера |

`FixedSizeChunker` набирает окно из блоков, пока **измеренное** число токенов
(`shared.token_counter.count_tokens`, tiktoken `cl100k_base`) не упрётся в
`size_tokens`; следующее окно начинается с «хвоста» предыдущего не длиннее
`overlap_tokens`. Хвост собирается **целыми блоками**, а не символами: перекрытие
из половины абзаца дало бы чанк, начинающийся на середине предложения. Если
последний блок окна сам длиннее перекрытия — перекрытием становится он один. У
чанков этой стратегии `section = ""` и `section_level = 0`.

`StructuralChunker` делает чанк из секции. Секция короче `min_section_tokens` (20
токенов) не становится чанком — заголовок без тела приклеивается к следующей
секции (последний — к предыдущей). Секция длиннее окна режется, но заголовок и
уровень остаются у **всех** её частей.

Оба чанкера нумеруют чанки (`chunk_id = f"{strategy}:{source}:{index:04d}"`) и
возвращают их по возрастанию `start_char`.

### Таблицы `document_chunks` и `index_runs`

`document_chunks` (метаданные и текст; `backend/models/indexing.py`):

| колонка | назначение |
|---|---|
| `id` | номер строки; он же `embedding_id` — id вектора в FAISS |
| `source`, `title`, `section`, `section_level` | из какого документа, с каким заголовком документа и секции |
| `chunk_id` | `structural:day20-readme.md:0007` — читаемый идентификатор; **не unique**: повторный прогон дописывает индекс |
| `strategy` | `fixed` или `structural` |
| `content`, `token_count` | текст чанка и его измеренный размер |
| `start_char`, `end_char` | границы чанка в исходном документе |

`index_runs` (журнал прогонов): стратегия (`fixed`/`structural`/`demo`), этап,
счётчики документов/чанков/эмбеддингов, метки времени, длительности
(`duration_ms`, `embed_duration_ms`, `index_duration_ms`), метрики сравнения (JSON)
и текст ошибки. Журнал в SQLite, а не в памяти: прогон идёт фоновым потоком, а
`GET /indexing/status` читает его из другого процесса — и после перезапуска тоже.

Модель загружается лениво (`max_seq_length = 512`: базовые 128 токенов молча
обрезали бы чанк в 512), а греется демон-потоком при старте, чтобы бэкенд не ждал
скачивания весов. Векторы нормализованы (`normalize_embeddings=True`), поэтому
скалярное произведение в `faiss.IndexIDMap2(IndexFlatIP)` равно косинусной
близости; `id` вектора равен `document_chunks.id`, и второго источника истины
«какой вектор какому чанку соответствует» не нужно.

### Демо-сценарий одной кнопкой

Раздел «📦 Индексация»: кнопка **«🚀 Запустить демо-индексацию»** запускает
`POST /indexing/demo` с `background=true` — тот же путь, что у CLI-прогона и
теста. Прогресс читается фрагментом раз в секунду (`GET /indexing/status`): полоса
этапа (загрузка → чанкинг → эмбеддинги → индекс → поиск → сравнение), подпись
этапа и счётчики «документы 25/25 · чанков fixed/structural · эмбеддингов 300/300».
По завершении видны таблица метрик сравнения, две гистограммы размеров чанков,
примеры чанков каждой стратегии, результаты пяти тестовых запросов, история
запусков и форма ручного поиска.

Прогон идёт по стейт-машине (`backend/domain/indexing_fsm.py`), и её значения —
это ровно статусы колонки `index_runs.status`: `loading → chunking → embedding →
indexing → searching → comparing → completed` (у одиночной стратегии после
`indexing` сразу `completed`: сравнивать нечего).

```bash
cd day21
uv sync
# терминал 1 — бэкенд (при старте читает индексы и греет модель эмбеддингов)
uv run uvicorn backend.api.main:app --port 8000
# терминал 2 — интерфейс; раздел «📦 Индексация» → «🚀 Запустить демо-индексацию»
uv run streamlit run app.py
# тот же сценарий без интерфейса: пять сценариев и отчёт
uv run python scripts/indexing_demo.py
uv run python scripts/indexing_demo.py --stub-embedder   # офлайн, без весов модели
uv run python scripts/prepare_documents.py --force       # только собрать документы
```

### Первый запуск и модель

Первый прогон скачивает веса модели (~470 МБ) в `index/models/` — это кэш
Hugging Face, в Git он не попадает. Модель задаётся переменной
`DAY21_EMBEDDING_MODEL` (по умолчанию
`sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2`), а `max_seq_length`
выставляется в 512: базовые 128 токенов молча обрезали бы чанк в 512, и сравнение
стратегий потеряло бы смысл. Сбой загрузки (нет сети, нет весов) не роняет бэкенд:
он приходит текстом в строке запуска со статусом `failed`, а для офлайн-прогонов
есть флаг `--stub-embedder` (детерминированный хеш-эмбеддер: прогон и отчёт
собираются без сети, но качество поиска тогда НЕ показательно — это печатается в
выводе и попадает в отчёт).

### Поиск по индексу

`GET /indexing/search` кодирует запрос той же моделью, ищет `top_k` ближайших
векторов в FAISS и подставляет метаданные чанков из SQLite — попадание приходит с
`score`, `source`, `section`, `token_count`, `content` и `preview`. Поиск по
непостроенному индексу — **409** (это «нечего искать», а не «ничего не нашлось»),
пустой запрос — **400**.

Шаг поиска есть и в ходе агента (`record["indexing"]` ответа генерации):
`Agent.apply_index_context` ищет фрагменты по реплике, когда индекс непуст, и
дописывает их в системный промпт блоком «## Контекст из индекса документов» —
модель отвечает по документам проекта, а не по памяти. Реплика, занятая пайплайном
или оркестрацией, поиск не делает: **один ход — один автоматизм**. Сбой поиска ход
не роняет — он виден текстом в `error`.

### Метрики сравнения

Сравнение стратегий идёт по метрикам (`backend/domain/index_metrics.py`):

| метрика | что показывает |
|---|---|
| чанков | сколько фрагментов даёт стратегия на одном наборе документов |
| средний размер, токенов | у `fixed` близко к размеру окна (512) |
| σ размера | разброс: у окна он мал, у секций — большой |
| максимальный чанк | не должен превышать окно ни у одной стратегии |
| покрытие, % | доля символов документов, попавшая в чанки (объединение интервалов: перекрытие окон не удваивает покрытие) |
| структура, % | доля чанков с непустой секцией (у `fixed` — 0) |
| precision@k, recall@k | качество поиска по пяти запросам и ожидаемым источникам (ground truth — `DEMO_QUERIES` домена) |
| индексация, мс; эмбеддинги, мс | сколько занял прогон стратегии и расчёт векторов |

`scripts/indexing_demo.py` запускает **пять сценариев** и собирает отчёт
`docs/reports/indexing_demo.md`: полный демо-прогон обеих стратегий, одиночную
стратегию, поиск по индексу, качество поиска на обеих стратегиях и перезапуск без
переиндексации. Живой отчёт дня —
[docs/reports/indexing_demo.md](docs/reports/indexing_demo.md) (пять сценариев и
таблица сравнения).

## Оптимизация затрат на LLM

Четыре рычага снижают счёт за запросы; формулы и модули перечислены в
`docs/reports/cost_optimization.md`, числа оттуда же.

1. **Кэш контекста (стабильный префикс промпта).** `backend/core/prompt_builder.py`
   собирает промпт строго по зонам: стабильный префикс (`profile → system →
   invariants → tools → examples → general`), затем динамика (память, состояние
   задачи, результаты инструментов), затем хвост с инструкцией о длине ответа.
   Префикс кэшируется по содержимому: повторный запрос с тем же префиксом попадает
   в кэш DeepSeek, и его токены приходят по сниженной цене
   (`LLM_CACHE_INPUT_RATIO = 0.1` — 10 % цены ввода). Стабильный префикс **не
   сжимается** (это сломало бы кэш), а метка времени или hex-id в префиксе ловится
   guard'ом `looks_dynamic` с предупреждением в лог.
2. **Сжатие динамической части.** `backend/services/prompt_compressor.py` убирает
   HTML-комментарии, лишние пробелы и пустые строки, повторы строк и абзацев,
   минифицирует JSON в ограждениях и целые JSON-блоки. Модуль ничего не
   перефразирует (блоки в тройных бэктиках неприкосновенны, кроме минификации
   JSON), поэтому результат идемпотентен.
3. **Предел длины ответа по типу задачи.** `LLMClient.max_tokens_for(task_type)`
   берёт предел из `LLM_TASK_MAX_TOKENS` (по умолчанию 1000 токенов, для длинных
   задач — 4000): длинный ответ — самая дорогая часть запроса.
4. **Непиковые часы DeepSeek.** `backend/domain/peak_hours.py` знает окна:
   непик — будни 00:00–01:00, 04:00–06:00, 10:00–24:00 UTC и все выходные; пик —
   будни 01:00–04:00 и 06:00–10:00 UTC. Флаг `prefer_off_peak` у задачи
   планировщика (`backend/services/off_peak.py`) переносит **первый** запуск в
   ближайшее дешёвое окно; флаг живёт внутри JSON-колонки `schedule_value`, а не
   отдельной колонкой БД.

Модель тоже выбирается по типу задачи (`LLMClient.select_model`, таблица
`LLM_TASK_MODELS`); простые задачи не тратят основную модель:

| тип задачи | модель | предел ответа, токенов |
|---|---|---|
| `chat` (ответ агента) | `deepseek-chat` | 1000 |
| `summarize` (конспект истории) | `deepseek-chat` | 512 |
| `classify` (инварианты, короткие решения) | `deepseek-chat` | 256 |
| `keywords` (ключевые слова и факты) | `deepseek-chat` | 256 |
| `orchestration` (план шагов) | `deepseek-reasoner` | 800 |
| `code` (длинная генерация) | `deepseek-reasoner` | 4000 |
| `indexing` (тяжёлая пакетная обработка) | `deepseek-reasoner` | 4000 |

`backend/services/llm_client.py` — единственная точка вызова DeepSeek: выбирает
модель и предел, извлекает из ответа `prompt_cache_hit_tokens` /
`prompt_cache_miss_tokens`, считает стоимость (`backend/domain/llm_cost.py`) и
пишет строку в журнал `llm_usage` (`backend/models/llm_usage.py`,
`backend/storage/llm_usage_store.py`). Клиент берётся из фабрики
`Agent._make_client`, поэтому подмена клиента в тестах по-прежнему видна. Сбой
записи в журнал запрос не ломает.

`GET /llm/usage` отдаёт агрегаты за период (запросы, токены, доля попаданий в
кэш, стоимость, разбивка по моделям/типам/дням), `GET /llm/status` — пик или непик
сейчас и статистику кэша префиксов и сжатия, `POST /llm/estimate` — прогноз
экономии по числам токенов, `GET /llm/models` — таблицу выше, `GET /llm/peak` —
окна. В интерфейсе это вкладка **«💰 Расходы»** (`frontend/cost_api.py`,
`frontend/cost_section.py`). В ответе генерации появилось поле `llm` (модель,
токены, `cache_hit`/`cache_miss`, стоимость хода).

### Что это дало (измерено)

Отчёт [docs/reports/cost_optimization.md](docs/reports/cost_optimization.md) считает
по реальным текстам дня и реальному счётчику токенов:

| нагрузка дня | было, $ | стало, $ | экономия |
|---|---|---|---|
| диалог: 6 запросов (ввод 10363 → 10475 токенов, из них по полной цене 10363 → 6815) | 0.003986 | 0.003128 | **21.5 %** (кэш контекста + сжатие) |
| тяжёлая задача: пакетная обработка 2 артефактов | 0.006584 | 0.003292 | **50.0 %** (сжатие + непик 50 %) |
| **итого за день** | **0.010570** | **0.006420** | **39.3 %** |

Сжатие на материале, для которого оно сделано (документ с маркером усечения +
JSON в ограждении), дало 4173 → 4104 токенов (**1.7 %**); на компактных блоках дня
оно снимает мало. Числа непика — тариф провайдера, а не измерение: планировщик
переносит задачу флагом `prefer_off_peak`, а размер скидки остаётся за
провайдером.

## Экономия контекста агента

Отдельный от «Расходов» слой: агент не тратит контекст на архив дней и на сырые
выгрузки команд. Механизмы, замеры и допущения — в
[docs/reports/context_optimization.md](docs/reports/context_optimization.md); кратко:

| Механизм | Где включён | Что даёт (измерено) |
|---|---|---|
| Зона видимости | корневой `.gitignore` (плюс `.clineignore`): `day1`–`day20` вне обхода `grep`/`glob`/`find` | из обхода ушли 2 261 файл (28,74 МБ); исходники архива в 4,1× больше рабочего дня по `.py` |
| Правила в контексте | `day21/.omp/RULES.md` (sticky) + `day21/AGENTS.md` | правила дня переживают длинную сессию; агент цитирует их, не читая архив |
| Перехват команд | `bashInterceptor` в `~/.omp/agent/config.yml`: `cat`/`head`/`tail` → `read`, `grep` → `grep`, `find` → `glob`, `sed -i` → `edit`, `echo >` → `write` | `cat app.py` — 135 байт отказа вместо 7 559 байт файла (−98,2 %) |
| Сжатие контекста | `compaction` (порог 850 000 токенов, `idleEnabled`) + расширение `billion-context` (порог сжимаемости 50 000 токенов) + плагин `context-mode` (11 MCP-инструментов) | контекст проверочной сессии 36 303 токена против 610 958 у сессии до правок |

`Blocked: Use the read tool instead of cat/head/tail`, а
`omp -p "через glob **/*.py перечисли верхнеуровневые папки"` показывает только
папки `day21`. Расход по дням и агентам — `omp stats --json`.

Менеджер зависимостей — **uv** (`pyproject.toml` + `uv.lock`, интерпретатор из

Индексация добавила четыре зависимости: **`sentence-transformers`** (эмбеддинги;
тянет `torch` и `transformers`), **`sentencepiece`** (без него токенизатор
мультиязычной модели не собирается), **`faiss-cpu`** (векторный индекс) и

локальная модель. Он нужен для чата, а без ключа `summarize` пайплайна переходит на
агрегацию. Переменные `.env`:

* `DEEPSEEK_API_KEY=sk-...` — ключ DeepSeek (чат, сводки, план оркестрации);
* `DAY21_BACKEND_URL=http://127.0.0.1:8000` — адрес бэкенда для интерфейса и
  собственного MCP-сервера (указывают, только если бэкенд слушает другой порт);
* `DAY21_EMBEDDING_MODEL=sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2`
  — необязательная модель эмбеддингов.

Терминал 1 (бэкенд) и терминал 2 (интерфейс, <http://localhost:8501>):


## Ограничения

- **Повторный прогон дописывает индекс.** `index_chunks` не чистит индекс неявно:
  числа чанков растут (это видно в статистике и истории запусков). Переиндексация с
  нуля — явная кнопка «🧹 Очистить обе стратегии» (`POST /indexing/clear`).
- **Блоки кода покрывают не весь файл.** `ast`-секции начинаются с top-level
  `def`/`class`; модульные переменные и `if __name__` попадают в блок `module`, а на
  битом Python работает запасная эвристика по строкам.
- **Модель эмбеддингов одна на процесс** (`get_embedding_service`), вызовы
  сериализуются блокировкой: фоновый прогон и ручной поиск не идут параллельно.
- **Сжатие экономит мало на компактных блоках.** `PromptCompressor` убирает только
  разметку и повторы; на тексте без «воды» выигрыш близок к нулю (1.7 % на
  специально подобранном материале).
- **Непик зависит от тарифа провайдера.** Домен знает окна, но размер скидки —
  допущение: в отчёте это явно помечено.
- **Журнал `llm_usage` растёт и не чистится автоматически.** Есть окна периодов
  (`day`/`week`/`month`/`all`) для чтения, но удаления старых строк нет.
