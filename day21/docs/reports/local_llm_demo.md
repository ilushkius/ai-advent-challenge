# Локальная LLM (Ollama) как второй провайдер дня 21

Задание дня 26 — **развернуть локальную LLM и подключить её к приложению как второй
провайдер**: DeepSeek остаётся провайдером по умолчанию, локальная модель выбирается
переключателем в интерфейсе, и тогда ответы приходят из Ollama по HTTP — **из
программы, а не из `curl`**. Отчёт фиксирует железо, обоснование выбора модели,
установку, проверки CLI и HTTP API, три контрольных запроса и то, какими эндпоинтами
и каким клиентом они ушли.

## 2. Рекомендация модели

**Выбрано: `qwen2.5-coder:14b`, квантование Q4_K_M (~9.0 GB).**

| Довод | Значение |
|---|---|
| Корзина задания 8–12 GB VRAM | карта 12227 MiB → модель на 9.0 GB влезает с запасом ~3.2 GB на KV-кэш и контекст |
| Что даёт запас | рабочая выбранная модель заняла 9.5 GB резидентной памяти при 100 % на GPU — вытеснения в RAM нет |
| Почему не 32B (Q4 ≈ 20 GB) | в 12 GB VRAM не влезает, а на CPU 31 GB RAM даёт единицы токенов в секунду |
| Почему не 7B | влезает уж слишком свободно: 14B заметно лучше на логике и коде при том же «железном» бюджете |
| Фолбэк на CPU | 31.17 GB RAM хватает с запасом: 9 GB весов + KV-кэш |
| Профиль модели | 14.8B параметров, `qwen2`, Q4_K_M, заявленный контекст 32768 токенов |

Лестница фолбэков, если 14B не влезет или окажется слишком медленной:
`qwen2.5-coder:7b` (~4.7 GB) → `phi4-mini` (~3 GB). Фактическая проверка ниже
показала, что фолбэк не нужен: RTX 5070 (Blackwell) подхватилась Ollama 0.35.1 без
правки конфигурации.

[logic] Логическая задача: У Алисы 3 яблока, у Боба в 2 раза больше. Сколько всего яблок?
ответ: У Алисы 3 яблока, а у Боба в 2 раза больше, то есть у Боба 3 * 2 = 6 яблок. Всего у них 3 + 6 = 9 яблок.
время: 3029 мс · токены: 57 вход / 56 выход · качество (эвристика): 5/5

[code] Генерация кода: Напиши функцию на Python для сортировки списка пузырьком.
ответ: Конечно! Вот пример реализации сортировки списка пузырьком на Python:

```python
def bubble_sort(arr):
    n = len(arr)
    # Проходим по всем элементам списка
    for i in range(n):
        # Последние i элементов уже отсортированы, поэтому мы не рассматриваем их
        for j in range(0, n-i-1):
            # Меняем местами, если элемент больше следующего
            if arr[j] > arr[j+1]:
                arr[j], arr[j+1] = arr[j+1], arr[j]
    return arr

# Пример использования
example_list = [64, 34, 25, 12, 22, 11, 90]
sorted_list = bubble_sort(example_list)
print("Отсортированный список:", sorted_list)
```

Эта функция принимает список `arr` в качестве аргумента и возвращает отсортированный список. Внутри функции используется вложенный цикл для сравнения и обмена соседних элементов, если они находятся в неправильном порядке. Этот процесс повторяется до тех пор, пока весь список не будет отсортирован.
время: 6761 мс · токены: 49 вход / 277 выход · качество (эвристика): 5/5

итого: 3 запроса за 12201 мс, в среднем 4067 мс; провайдер local, модель qwen2.5-coder:14b
```

## 7. Какими эндпоинтами и каким клиентом идут запросы

| Что делает пользователь | HTTP-запрос приложения | Кто на бэкенде | Что уходит в Ollama |
|---|---|---|---|
| раздел «🖥 Локальная LLM» → «▶ Прогнать 3 запроса» | `POST /llm/local-demo` (тело пустое) | `services/local_llm_demo.run_demo` → `llm_factory.get_llm_client("local")` → `LocalLLMClient.generate` | `POST http://localhost:11434/api/chat` (три раза, `stream: false`) |
| раздел «💬 Чат и память» + переключатель «Local LLM (Ollama)» → RAG-запрос по корпусу | `POST /rag/query` с полем `provider: "local"` | `RAGService.llm_client_for("local")` → `LocalLLMClient.generate_with_context` | `POST http://localhost:11434/api/chat` (системный промпт отдельным сообщением, контекст корпуса — блоком в пользовательском) |
| мини-чат (8502) + переключатель «Local LLM (Ollama)» → реплика | `POST /mini-chat/sessions/{session_id}/messages` с `provider: "local"` | `MiniChatService.llm_client_for("local")` и `memory_client_for("local")` | два вызова: ответ по контексту и извлечение памяти задачи |
| `uv run python scripts/demo_local_llm.py` | HTTP-бэкенда нет вовсе | `local_llm_demo.run_demo` → `LocalLLMClient` напрямую | `POST http://localhost:11434/api/chat` |

Точка выбора клиента — одна на весь день: `backend/services/llm_factory.get_llm_client`
(`"local"` → `LocalLLMClient`, `"deepseek"` → обёртка дня 21 `LLMClient`).
Провайдер по умолчанию — `config.LLM_PROVIDER` (`deepseek`; в `.env` не менялся),
значение на один запрос перекрывается полем `provider` в теле запроса, а имя того,
кто ответил, приходит обратно в поле `provider` ответа
(`GET /llm/provider` отдаёт текущую конфигурацию целиком).

## 8. Ограничения локальной модели

Честно, по фактическим замерам этого прогона:

* **слабее DeepSeek на сложных рассуждениях и на русском** — 14B-модель пишет
  связно, но проще: в RAG-ответе из § 7 уверенность 0.3 (цитаты не подтвердились
  подстрочно), тогда как у облачного ответа на тот же вопрос — тот же вердикт, но
  формулировки точнее и ближе к тексту чанков;
* **медленнее**: 2.4–6.8 с на короткий ответ и до 12 с на генерацию кода против
  десятых долей секунды у облака с кэшем префикса; первый запрос после простоя
  дополнительно грузит 9.5 ГБ в VRAM (46 с в CLI, ~30–60 с в интерфейсе);
* **уже контекст по умолчанию**: Ollama поднимает модель с `num_ctx = 4096`
  (`ollama ps`: `CONTEXT 4096`) при заявленном контексте модели 32768 — у RAG-запроса
  из § 7 контекст 2556 токенов помещается, но длинный корпусный контекст (предел дня
  `RAG_CONTEXT_MAX_TOKENS = 3000` плюс системный промпт) уже близок к границе;
  увеличение `num_ctx` — параметр модели, а не правка кода;
* **нет ни кэша контекста, ни журнала расходов, ни цены**: локальный клиент отдаёт
  `cache_hit_tokens = 0`, `cache_miss_tokens = prompt_tokens`, `cost_estimate = 0.0`,
  и в `llm_usage` строк не пишет — считать там нечего. Поэтому вкладка «💰 Расходы»
  локальные запросы не увидит, а токены видны только в ответе демо (колонка
  «токены») и в метриках RAG;
* **качество ответа проверяется эвристикой** (см. § 6), а не человеком и не
  эталоном: оценка 5/5 у трёх запросов говорит лишь о том, что ответ содержит
  ожидаемые слова, и не заменяет ручную проверку.
