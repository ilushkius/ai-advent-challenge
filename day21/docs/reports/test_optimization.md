# Оптимизация тестов: параллелизм, общая схема БД, маркер slow

Отчёт о том, почему набор дня 21 шёл 6 минут, что именно его ускорило и как это
воспроизвести. Замеры сняты 2026-09-29 на этом окружении: 12 ядер CPU, Windows,
`pytest 9.1.1`, Python 3.14.

## 1. Диагностика (до оптимизации)

| Метрика | Значение |
|---|---|
| Полный прогон (`uv run pytest -q`) | **370,15 с** (6:10) |
| Тестов / файлов | 2521 / 125 |
| Покрытие (`--cov=backend`) | 96 % (11 151 оператор, 406 пропущено) |
| Топ-25 медленных тестов | 1,5–3,1 с, все — подпроцессы MCP-серверов по stdio |
| Фаза `setup` > 1 с | **102 теста, 114,5 с суммарно** |
| Фаза `call` > 1 с | 57 тестов, 150,4 с суммарно |

Причина найдена замером, а не догадкой: фикстура `session_factory` строила схему
БД **на каждый тест**, и это стоит почти секунду:

| Операция | Время |
|---|---|
| `make_engine` (пустая база) | 0,5 мс |
| `init_db` (`create_all` по ~25 таблицам) | **934,3 мс** |
| копия готового файла схемы | **2,65 мс** |

Схему строят 481 тест (33 % набора) — отсюда и шесть минут.

## 2. Что сделано (шаги 2.2–2.5)

| Шаг | Решение | Файлы |
|---|---|---|
| Параллельный запуск | `pytest-xdist`, `addopts = -ra -n auto`, тесты изолированы (у каждого своя временная SQLite, общие файлы дня не пишутся) | `pyproject.toml` (+`pytest-xdist`, `pytest-cov`), `pytest.ini` |
| Общая схема БД | session-scoped `schema_template` строит схему один раз; `session_factory` копирует файл (2,65 мс вместо 934 мс), изоляция сохранена — файл на тест | `tests/conftest.py` |
| Дубли в e2e | 15 e2e-файлов перестали строить собственную схему (`make_engine` + `init_db` + `make_session_factory`) — берут общую фикстуру `session_factory`; хелперы `_build_client` получают её первым параметром | `tests/e2e/*.py` |
| Маркер `slow` | 75 тестов (22 файла): 6 stdio-файлов целиком (`pytestmark`), остальные — точечно `@pytest.mark.slow`; по умолчанию `-m "not slow"`, полный прогон — `-m ""` или `--run-slow` | `pytest.ini`, `tests/conftest.py`, 22 файла тестов |
| Офлайн-гарантия | autouse-фикстура `no_real_network` запрещает TCP на нелокальные адреса (внешние API подменены фейками, стенды слушают 127.0.0.1) | `tests/conftest.py` |
| Фикстуры тяжёлых ресурсов | схема БД — session-scoped; изменяемые данные — function-scoped на временной БД (как было); модели и планировщик — autouse-запрет (`isolated_indexing`, `offline_planner`) | `tests/conftest.py` |
| Раскладка фикстур | `tests/conftest.py` после правок вырос до 419 строк (лимит 400), поэтому фикстуры флота и оркестрации переехали в `tests/fixtures_fleet.py`, индексации — в `tests/fixtures_indexing.py`, а conftest импортирует их обратно (pytest видит импортированные фикстуры как свои). Стало 261 + 90 + 107 строк | `tests/conftest.py`, `tests/fixtures_fleet.py` (новый), `tests/fixtures_indexing.py` (новый) |

## 4. Дубли тестов: что нашлось

Проверено объективно, а не «на глаз» (три сканирования AST по всем 2521 тестам):

| Проверка | Результат |
|---|---|
| Одинаковое имя **и** одинаковое тело теста | 1 пара: `test_summarize_falls_back_to_aggregation` в `integration/test_data_server_stdio.py` и `integration/test_mcp_server_stdio.py` |
| Одинаковое тело при разных именах (копипаста) | **0** |
| Семьи `test_x_with_*`/`test_x_when_*`, тела совпадают после нормализации литералов | **0** |
| Параметризация уже применена | 2521 тест при 125 файлах, у 62 файлов несколько кейсов на одно имя теста |

Единственная пара с совпадающим телом **не является дублем**: она проверяет две
разные реализации инструмента `summarize` — сервер флота `data_server` (день 20) и
собственный сервер дня (`mcp_server`, дни 17–19). Объединение в один
параметризованный тест связало бы два независимых продукта и потеряло бы проверку
одного из них, поэтому пара оставлена. Покрытие до и после совпадает (96 %), то
есть в ходе оптимизации не удалено ни одной проверки.

## 5. Команды

```bash
cd day21
uv run pytest -q                                  # быстрый прогон: 2446 тестов, ~31 с (без slow)
uv run pytest -q -m ""                            # полный прогон: 2521 тест, ~68 с
uv run pytest -q --run-slow                       # то же флагом
uv run pytest -q -m "" --cov=backend --cov-report=term-missing   # полный прогон с покрытием
uv run pytest -q --durations=25                   # где время (setup/call/teardown)
```

## 6. Ограничения

* **57 тестов с фазой `call` > 1 с не ускоряются кодом.** Это подпроцессы
  MCP-серверов по stdio (`test_*_stdio.py`, `test_mcp_scheduler_tools.py`): каждый
  тест поднимает процесс сервера и говорит с ним по протоколу. Ускорять их можно
  только меняя предмет проверки (например, общий процесс на файл), а это уже
  другая проверка — они и помечены `slow`.
* **`-n auto` = 12 процессов** на этой машине. На 2–4 ядрах выигрыш будет меньше;
  число воркеров задаётся в `pytest.ini` (`-n auto` → `-n 4`).
* **Покрытие с `--cov` считается по всем воркерам** (pytest-cov объединяет
  `.coverage.*`); цифра 96 % совпала с последовательным прогоном.
* **Первый прогон после правок схемы медленнее на один `init_db`** (~0,9 с) — это
  цена session-scoped шаблона.
