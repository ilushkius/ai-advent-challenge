## 1. Что нужно и как запустить

## 2. Workflow разработки

Маршрут работы над днём — три ступени: **сырое задание → архитектурный план →
выполнение**.

1. **Задание** берётся из челленджа как есть.
2. **Сложная задача проходит планирование.** Откройте шаблон
   [`ARCHITECT_PROMPT.md`](../../ARCHITECT_PROMPT.md) в корне `ai-challenge/`,
   вставьте текст задания в поле `{{ЦЕЛЬ}}` и отправьте его в **отдельный чат с
   DeepSeek**. Шаблон требует ответ в пяти частях: декомпозиция и Definition of
   Done, пошаговый план с файлами и командами, риски и план Б, проверка после
   выполнения, команды `git commit`/`git tag`.
3. **План передаётся в omp.sh** как промпт дня: агент исполняет пункты плана, а не
   пересказ задания. Готовый структурированный план повторно планировать не надо.
4. **Фиксация:** коммит с описанием дня и тег `dayN`; документация дня обновляется
   под текущее состояние.

Что считать сложной задачей: новые модули и слои, интеграции, изменения
архитектуры, работа с MCP, планировщик, индексация, оптимизация затрат. Простой
задачей (кнопка, текст, правка документации) можно заниматься сразу — без
архитектурной ступени. Полное описание маршрута — в
[`../WORKFLOW.md`](../WORKFLOW.md), правила для агента — в
[`../AGENTS.md`](../AGENTS.md) дня и в корневых [`../../AGENTS.md`](../../AGENTS.md),
[`../../RULES.md`](../../RULES.md).

## 3. Тесты

```bash
cd day21
uv run pytest -m "not slow"                      # быстрый прогон при разработке: меньше минуты
uv run pytest                                    # то же самое: -m "not slow" уже стоит в pytest.ini
uv run pytest -m ""                              # полный прогон, все тесты (включая slow): меньше 3 минут
uv run pytest --run-slow                         # то же самое флагом
uv run pytest -m "" --cov=backend --cov-report=html    # покрытие по всем тестам: отчёт в htmlcov/index.html
```

Покрытие считается **на том наборе, который запущен**: без `-m ""` отчёт в
`htmlcov/` описывает только быстрый набор. Цифра из отчёта дня (96 %) снята на
полном наборе.

Медленные тесты (интеграционные и e2e: подпроцессы MCP-серверов по stdio и полный
клиент приложения) помечены маркером `slow` — **85 штук, по умолчанию они
пропускаются**, чтобы не тормозить разработку; полный набор включают `-m ""` или
`--run-slow`. Тесты идут параллельно (`-n auto`), а схема БД строится один раз за
прогон, поэтому быстрый прогон занимает ~30 с, полный — ~70 с при покрытии 96 %.
Детали оптимизации и замеры «до и после» —
[`reports/test_optimization.md`](reports/test_optimization.md).

Отдельный маркер `remote` — у сквозного прогона удалённой модели (день 30,

## 4. Оптимизация затрат: что смотреть и как проверить

### 4.1 Сколько стоят запросы (вкладка «💰 Расходы»)

Вкладка отвечает на четыре вопроса сразу:

* **пик или непик сейчас** — блок «Непиковые часы DeepSeek»: если идёт дешёвое окно,
  показывается скидка провайдера, иначе — когда начнётся следующее окно;
* **сколько потрачено** — «Итоги периода»: запросов, токенов, **доля ввода из кэша
  контекста**, оценка стоимости; период переключается (сутки / неделя / месяц / всё
  время);
* **что даёт экономию** — строка «Экономия измеряемых рычагов» и прогноз «если бы
  весь период шёл в непиковые часы»: кэш контекста, сжатие промптов, предел длины
  ответа и скидка непика считаются по отдельности;
* **где кэш не сработал** — «Последние запросы»: модель, тип задачи, ввод, вывод и
  **раздельно `cache_hit` и `cache_miss`**.

Там же видно статистику кэша приложения («Префикс из кэша приложения», «Попаданий /
промахов»), сколько токенов снято сжатием и в каком размере стабильный префикс
(сколько токенов сервер может отдать из кэша).

### 4.2 То же по API

```bash
# журнал расходов за неделю (period: day | week | month | all)
curl "http://127.0.0.1:8000/llm/usage?period=week&limit=20"

# состояние рычагов: пик/непик, скидка, кэш префиксов, сжатие, таблица моделей
curl "http://127.0.0.1:8000/llm/status"

# прогноз экономии по числам токенов (вклад каждого рычага отдельно)
curl -X POST http://127.0.0.1:8000/llm/estimate \
  -H "Content-Type: application/json" \
  -d "{\"model\":\"deepseek-chat\",\"prompt_tokens\":100000,\"cache_hit_tokens\":60000,\"compressed_tokens\":10000,\"max_response_tokens\":1000,\"off_peak_share\":1.0}"

# какая модель и какой предел ответа выбраны для какого типа задачи
curl "http://127.0.0.1:8000/llm/models"

# окна непиковых часов и текущий статус
curl "http://127.0.0.1:8000/llm/peak"
```

Поля, на которые стоит смотреть: `cache_hit_tokens` и `cache_miss_tokens` (деньги:
попадание в кэш стоит 10 % цены ввода), `cache_hit_percent` (доля ввода из кэша),
`cost_estimate` (оценка стоимости запроса), `by_model` и `by_type` (кто именно
тратит), `core_saving` против `total_saving` (второй включает предел длины ответа —
это оценка сверху, а не факт).

### 4.3 Как убедиться, что кэш работает

1. Сделайте два хода подряд по одному и тому же агенту с одинаковой инструкцией
   (системный промпт, профиль, инварианты не менялись).
2. Откройте «💰 Расходы» → «Кэш промптов и сжатие»: **«Префикс из кэша приложения»**
   должен стать больше 0, а в «Последних запросах» у второго хода появится
   `cache_hit` (у первого он равен нулю — это и есть наполнение кэша).
3. Смените системный промпт агента и сделайте ещё ход: доля попаданий упадёт — это
   ожидаемо, стабильный префикс изменился.

Через API то же самое видно как рост `cache_hit_tokens` между двумя запросами в
`GET /llm/usage`. Помните про правило дня: **стабильный префикс не сжимается и не
меняется** — если в префикс попадут метка времени или случайный идентификатор,
строитель промптов предупредит в логе и не будет его кэшировать.

### 4.4 Как поставить тяжёлую задачу в непиковое окно

Непик: будни 00:00–01:00, 04:00–06:00, 10:00–24:00 UTC и все выходные;
пик: будни 01:00–04:00 и 06:00–10:00 UTC. Флаг `prefer_off_peak` переносит **первый**
запуск задачи в ближайшее дешёвое окно:

```bash
curl -X POST http://127.0.0.1:8000/scheduler/tasks \
  -H "Content-Type: application/json" \
  -d "{\"tool\":\"generate_summary\",\"arguments\":{\"name\":\"posts\",\"interval_seconds\":3600},\"prefer_off_peak\":true}"
```

В интерфейсе то же делает раздел «🗓 Планировщик» (галочка в форме задачи), а текущий
статус окна всегда виден во вкладке «💰 Расходы». Флаг переживает перезапуск: он
хранится вместе с расписанием задачи.

## 7. RAG-запрос по корпусу документов

Режим отвечает на вопрос **по внутреннему корпусу** (36 документов дня 21):
вопрос ищет релевантные фрагменты, они уходят в модель вместе с вопросом, а ответ
показывает источники и оценку опоры на контекст. День 23 добавляет к поиску второй
этап отбора: пересортировку кросс-энкодером, порог релевантности и
переформулировку вопроса моделью. День 24 делает источники и цитаты обязательными
и добавляет режим «не знаю»: если максимум косинуса лучшего фрагмента ниже порога
`RAG_RELEVANCE_THRESHOLD`, ответ строится без вызова модели.

Панель **«🔍 RAG-запрос по корпусу»** — внизу раздела «💬 Чат и память»:

* тумблер **«RAG: включён»** — выключите, чтобы получить ответ без контекста (та
  же модель отвечает по общим знаниям);
* слайдер **top_k** (1–10) и selectbox **стратегии** (`rag_corpus_structural` —
  секции по разделам, `rag_corpus_fixed` — фиксированное окно);
* тумблер **«Переформулировать запрос моделью»** — перед поиском модель делает из
  вопроса поисковый запрос; в ответе видно, по чему искали (`query_used`);
* тумблер **«Реранкер: кросс-энкодер»** — кандидаты пересортировываются
  кросс-энкодером `RAG_RERANK_MODEL` (первый запуск скачивает веса ~470 МБ в
  `index/models/`);
* слайдер **«Порог отсечения (min_score)»** — 0.00 означает «без отсечения»,
  стартовое значение — измеренный `RAG_FILTER_MIN_SCORE`. Порог — рычаг под
  короткий контекст, а не улучшение по умолчанию: на прогоне дня 23 он срезал в
  среднем 0.6 фрагмента, но три ответа из десяти стали хуже (`rerank_filter`
  против `rerank` — лучше 1, хуже 3, равно 6). Если порог срезал **все** фрагменты,
  ответ дня 24 приходит в режиме «не знаю»: ответа без источников больше нет;
* форма вопроса — кнопка «🔎 Найти ответ»;
* строка метрик: **время** ответа, **токены**, **фрагментов до фильтра**
  (`candidates`), **фрагментов после фильтра** (`kept`), **порог**
  (`min_score`), **кэш контекста** (% ввода из кэша DeepSeek) — последняя
  наглядно показывает, что системный префикс не меняется между режимами;
* **строка оценки опоры**: «есть опора в контексте» или «низкая уверенность: в
  ответе нет фактов из контекста» — вторая означает, что вопрос, скорее всего, вне
  корпуса; рядом строка уверенности `confidence`: `1.0` — ответ подтверждён
  цитатами, `0.3` — цитаты ответ не подтверждают;
* предупреждения: «переформулировка не удалась / вернула пустой запрос»,
  «реранкер недоступен» — ответ приходит в любом из этих случаев; «Недостаточно
  контекста: максимальный балл … ниже порога …» означает режим «не знаю»
  (`mode: "dont_know"`): источников и цитат нет, модель не вызывалась;
* expander **«📝 Цитаты из корпуса»** — по одной выдержке (≤ 200 символов) из
  каждого использованного фрагмента с источником, разделом и `chunk_id`. Цитаты
  формирует бэкенд из текста фрагментов, поэтому они воспроизводимы; модель их не
  сочиняет;
* expander **«📚 Использованные источники»** — таблица источник / заголовок /
  раздел / `chunk_id` / score плюс четыре балла фрагмента: `vector` (косинусная
  близость), `lexical` (словесные веса), `rerank` (кросс-энкодер) и `score` (по
  нему шла сортировка).

Раздел **«🆚 RAG-сравнение»** прогоняет один вопрос дважды и показывает ответы
рядом: слева «🚫 Без RAG», справа «✅ С RAG», у каждого — время, токены и число
фрагментов. Ниже мультиселект **«Режимы для сравнения»** (по умолчанию `baseline`
и `rerank_filter`) и кнопка «🆚 Сравнить режимы»: каждый режим рисуется отдельным
столбцом со своим ответом, источниками и метриками «до/после фильтра».

Полный отчёт сравнения — `docs/reports/rag_modes.md`: таблица на 10 контрольных
вопросов (ожидание, источники со баллами, ответы без RAG и в четырёх режимах,
вердикты против «без RAG» и против `baseline`), раздел свипа порога с выбранным
значением, «Итог» и приложение с полными ответами. Отчёт собирается скриптом на
реальных ответах модели:

```bash
cd day21
```

Флаги: у `prepare_rag_corpus.py` — `--list` (манифест), `--force` (пересобрать),

### RAG-демо (день 24)

Раздел **«🧪 RAG-демо»** отвечает на вопрос «а он вообще не врёт?»: одна кнопка
прогоняет весь набор контрольных вопросов и показывает по каждому режим, ответ,
источники, цитаты и вердикт.

1. Откройте раздел «🧪 RAG-демо»: сверху — подпись с действующим порогом
   релевантности (из `GET /rag/config`), ниже таблица вопросов с ожиданием
   («ответ есть в корпусе» / «частичный ответ» / «ответа в корпусе нет») и
   ожидаемым режимом.
2. Нажмите **«🚀 Прогнать демо»**: вопросы идут по одному, под кнопкой растёт
   прогресс «i/10» с текстом текущего вопроса. Один сбойный вопрос не срывает
   прогон — он становится строкой с вердиктом «ошибка модели, ответ без корпуса».
3. Результат — таблица: **режим** (`rag`, `no_rag`, `dont_know`), **ответ**
   (обрезан до 160 символов), **источники** (`сколько · первый источник`),
   **цитаты** (`сколько · первая выдержка`) и **вердикт**: «совпадает», «верно:
   ответа в корпусе нет», «источник не найден», «цитаты не подтверждают ответ»,
   «режим не совпал с ожиданием». В подписи под таблицей — сводка: сколько
   ответов с источниками и цитатами, сколько «не знаю», сколько вердиктов
   «совпадает».
4. Вопросы лежат данными — `backend/data/demo_questions.json`: `question`,
   `expectation`, `expected_mode` (`rag` или `dont_know`), `expected_sources`
   (слаги файлов корпуса, сравниваются по буквам и цифрам) и `note`.

**Как поменять порог «не знаю».** Порог читается из переменной
`RAG_RELEVANCE_THRESHOLD` (порядок: переменная окружения → `day21/.env` →
значение по умолчанию `0.6`). Значение берётся на импорте модуля
`backend/domain/rag_quotes.py`, поэтому после правки `.env` нужен **рестарт
бэкенда** (Streamlit перезапускать не нужно — он ходит по HTTP). Порог сравнивается
с максимумом косинуса лучшего фрагмента **из пула кандидатов** (30 штук, шкала
`[0, 1]`), а не с гибридным баллом `score`: тот не ограничен единицей и на частых
русских словах доходит до 1.1, поэтому для решения «знаю / не знаю» не годится.

**То же из терминала** — `scripts/run_rag_quotes_eval.py`:

```bash
cd day21
uv run python scripts/prepare_rag_corpus.py    # корпус (36 документов)
uv run python scripts/run_rag_quotes_eval.py --sweep    # только замер баллов, без вызовов модели
uv run python scripts/run_rag_quotes_eval.py            # полный прогон + отчёт
```

Флаги: `--sweep` (считает `max v` по каждому вопросу и предсказанный режим, отчёт
не пишет, к модели не обращается), `--threshold` (проверить другой порог),
`--limit` (сколько вопросов брать), `--json` (строки как JSON), `--out` (путь
отчёта, по умолчанию `docs/reports/rag_quotes_eval.md`). Отчёт —
[`reports/rag_quotes_eval.md`](reports/rag_quotes_eval.md): таблица на десять
вопросов с режимом, ответом, источниками, цитатами, `max v`, автоматическим и
ручным смыслом, вердиктом; ниже распределение `max v` и итог. Скрипт возвращает
код 1, если нашлись расхождения с ожиданиями, — это удобно для проверки набора
вопросов.

### Сценарий дня 23: отбор по шагам

Сценарий — один вопрос по корпусу, прогнанный по ступеням отбора: каждая ступень
добавляется к предыдущей, поэтому видно, что именно её изменило в ответе.

| Шаг | Что включить | Что должно получиться |
|---|---|---|
| 1. Корпус | `scripts/prepare_rag_corpus.py`, затем `scripts/index_rag_corpus.py` | `GET /rag/config`: корпус готов, 680 чанков (291 `fixed` + 389 `structural`); без индексов `POST /rag/query` отвечает `409` |
| 2. `baseline` | «RAG: включён», `top_k` 5, структурная стратегия, оба тумблера дня 23 выключены, порог `0.00` | ответ по корпусу; «до фильтра 30 / после фильтра 5»; в источниках `score`, `vector`, `lexical`, а `rerank` — «—» |
| 3. `rewrite` | + «Переформулировать запрос моделью» | строка `query_used` — поисковый запрос вместо вопроса; сбой модели даёт предупреждение и поиск по исходному вопросу |
| 4. `rerank` | + «Реранкер: кросс-энкодер» | порядок источников по баллу `rerank` (0…1), `score` равен ему; веса ~470 МБ тянет прогрев при старте бэкенда, первый запрос с реранкером считает баллы впервые (десятки секунд); без весов — предупреждение и порядок дня 22 |

порога: `uv run python scripts/run_rag_eval.py --sweep` (~2 минуты, 10 вызовов

а не «улучшал всё сразу».

## 8. Мини-чат с RAG и памятью задачи (день 25)

Мини-чат — **отдельное приложение**: ответ по корпусу проекта с источниками и
цитатами плюс боковая панель «Память задачи», где видно, что стало с целью диалога.
Песочница (`app.py`, порт 8501) при этом не меняется: у мини-чата свой вход, свой
раздел API `/mini-chat/*` и только транспорт `frontend/api_client.py` общий.

### Как запустить

Бэкенд один на оба приложения, мини-чат — вторым процессом из папки `day21/`:

```bash
# терминал 1 — бэкенд (в нём же живёт раздел /mini-chat/*)
uv run uvicorn backend.api.main:app --port 8000

# терминал 2 — мини-чат
uv run streamlit run mini_chat/app.py --server.port 8502   # http://localhost:8502
```

Порт 8502 занят — возьмите 8503: бэкенд об этом не знает, адрес задаёт переменная
`DAY21_BACKEND_URL` (по умолчанию `http://127.0.0.1:8000`). Корпус и индексы — общие
с RAG-режимом дней 22–24 (`scripts/prepare_rag_corpus.py`, `scripts/index_rag_corpus.py`).

### Сессия

Сессия создаётся сама при первом открытии страницы. Кнопка **«✨ Новая сессия»** в
боковой панели закрывает текущую (`DELETE /mini-chat/sessions/{session_id}` — реплики
удаляются), очищает историю и открывает новую. У каждой сессии свои `session_id` и
`task_id` (`mc-<session_id>`), поэтому новая сессия начинается с пустой памяти задачи.

### Панель «Память задачи»

| Поле | Что в нём |
|---|---|
| **Цель** | `goal` — что пользователь хочет получить от диалога |
| **Термины** | `terms` — зафиксированные понятия и идентификаторы |
| **Ограничения** | `constraints` — что делать нельзя |
| **Уточнения** | `clarifications` — что пользователь добавил по ходу |
| подпись под полями | `message_count` — число реплик и время обновления памяти |

Память обновляется после каждой реплики: отдельным запросом (предел ожидания 5 с,
одна попытка) модель извлекает четыре поля из последних реплик и **полностью
заменяет** прежнее состояние — слияния нет, иначе дрейф цели было бы не видно. Если
модель не ответила или вернула не JSON, память остаётся прежней, а под ответом
появляется строка «Память задачи не обновлена…».

### Переключатели и режимы ответа

* **«Фрагментов в контексте (top_k)»** — 1…10, по умолчанию 5: сколько фрагментов
  корпуса уходит в модель вместе с памятью задачи и историей диалога.
* **«Показывать цитаты»** — показывать ли блок «❝ Цитаты» под ответом.

Под ответом — «📚 Источники (N)» с `source`, `section`, `chunk_id`, `score` и подпись
с режимом, проверкой цитат и уверенностью. Режимы те же, что у RAG-режима:

* `rag` — ответ по корпусу: источники и цитаты есть;
* `dont_know` — **жёлтое** предупреждение: контекст слабее порога, модель не
  вызывалась (вопрос вне корпуса проекта);
* `error` — **красная** ошибка: модель не ответила после трёх повторов; реплика всё
  равно сохраняется в истории, чтобы ход диалога не терялся.

### Отчёт по длинным сценариям

Отчёт [`reports/mini_chat_scenarios.md`](reports/mini_chat_scenarios.md) — прогон двух
длинных сценариев (14 и 12 реплик: RAG по документации и агент обработки заявок).
По каждой реплике видно ответ, число источников, режим, память задачи после неё и
потеряна ли цель диалога. Цель реплики считается потерянной, если в текущей памяти
осталось меньше половины (`GOAL_SHARE_MIN` 0.5) слов первой цели сценария, а сценарий —
если таких реплик больше 20 % (`GOAL_KEEP_MIN` 0.8): пересказ с дописанными уточнениями
ещё не потеря, а исчезновение слов исходной цели в большинстве реплик — уже она.

```bash
uv run python scripts/prepare_rag_corpus.py --force   # если корпус устарел
uv run python scripts/index_rag_corpus.py             # оба индекса
uv run python scripts/run_mini_chat_scenarios.py      # нужен DEEPSEEK_API_KEY в day21/.env
```

Флаги: `--limit 3` (первые реплики сценария), `--top-k 8`, `--scenarios <файл>`,
`--report <файл>` (по умолчанию `docs/reports/mini_chat_scenarios.md`), `--quiet`.
Прогон делает два запроса к модели на реплику, поэтому его место — непиковое окно
DeepSeek.

Пошаговый прогон мини-чата с ожидаемыми наблюдениями на каждом шаге — «Сценарий
дня 25» в [README.md](../README.md#сценарий-дня-25-мини-чат-с-rag-и-памятью-задачи-по-шагам).

## 9. Локальная LLM (Ollama, день 26)

Второй провайдер ответа: тот же RAG-запрос и мини-чат могут отвечать **локальной
моделью** по HTTP, без облака. DeepSeek остаётся провайдером по умолчанию.

### Установка и модель

```powershell
winget install --id Ollama.Ollama -e     # Windows: установщик поднимает службу сам
ollama --version                        # ollama version is 0.35.1
ollama pull qwen2.5-coder:14b            # 9.0 GB; корзина «8–12 GB VRAM» под RTX 5070
ollama list                             # модель на месте?
```

Если порт 11434 не отвечает (`curl.exe http://localhost:11434/api/tags` — ошибка
соединения), служба не поднялась: запустите `ollama serve` в отдельном окне. Порт
11434 свободен от приложения (8000 — бэкенд, 8501 — песочница, 8502 — мини-чат).

Проверки «модель жива» — CLI и HTTP:

```powershell
ollama run qwen2.5-coder:14b "Сколько будет 2+2? Ответь одним числом."
curl.exe http://localhost:11434/api/generate -d '{\"model\":\"qwen2.5-coder:14b\",\"prompt\":\"Сколько будет 2+2?\",\"stream\":false}'
ollama ps          # PROCESSOR: 100% GPU, CONTEXT: 8192 (окно профиля tuned, день 29)
```

Настройки провайдера читает бэкенд при старте (`backend/core/config.py`):

```dotenv
LLM_PROVIDER=deepseek          # провайдер по умолчанию: deepseek | local
LOCAL_LLM_MODEL=qwen2.5-coder:14b
LOCAL_LLM_URL=http://localhost:11434
```

Профиль настройки локальной модели (день 29) читает домен
`backend/domain/local_tuning.py` — тоже при старте, поэтому после правки нужен
рестарт бэкенда (подробности — раздел 11):

```dotenv
LOCAL_LLM_PROFILE=tuned        # tuned — поведение по умолчанию, baseline — как день 26
LOCAL_LLM_TEMPERATURE=0.2
LOCAL_LLM_NUM_CTX=8192
LOCAL_LLM_CHAT_MAX_TOKENS=512
```

### Переключатель в интерфейсе

Переключатель **«🤖 Провайдер LLM»** — в самом верху боковой панели песочницы
(`app.py`). Он действует на RAG-запрос по корпусу в разделе «💬 Чат и память»: ответ
приходит от выбранной модели, а в метриках стоит строка «Провайдер» со значением
`local` или `deepseek`. Агентский чат всегда идёт в DeepSeek — подпись под
переключателем это проговаривает. У мини-чата (8502) свой переключатель
(«🤖 Провайдер ответа»), и под каждым ответом видно автора:
«Провайдер: local · модель: qwen2.5-coder:14b».

### Раздел «🖥 Локальная LLM»

Кнопка **«▶ Прогнать 3 запроса»** отправляет `POST /llm/local-demo`: простой факт,
логическую задачу и генерацию кода. В таблице — ответ (короткой строкой), время,
токены (вход/выход), эвристическая оценка качества 1–5 и провайдер; полный текст
каждого ответа — в раскрывающемся блоке. Первый запрос **самый долгий**: модель
грузится в память (30–60 с), дальше 2–12 с.

Тот же прогон из терминала — без бэкенда, прямо в Ollama:

```bash
cd day21
uv run python scripts/demo_local_llm.py
```

Скрипт печатает вопрос, ответ, время, токены и оценку по каждому запросу, затем
итог. Ненулевой код возврата — только когда Ollama недоступна: в этом случае
печатается причина и подсказка `ollama serve` / `ollama pull <модель>`.

### Чего у локальной модели нет

* **журнала расходов и цены** — в `llm_usage` строк не пишется, вкладка «💰 Расходы»
  локальные запросы не показывает (токены видны в ответе демо и в метриках RAG);
* **кэша контекста** — `cache_hit_tokens` всегда 0;
* **скорости облака** — 14B на 12 GB VRAM отвечает секундами, а не десятыми долями.

Полный отчёт дня (железо, обоснование выбора модели, замеры, скриншоты) —
[`docs/reports/local_llm_demo.md`](reports/local_llm_demo.md).

  без обрезки (лимит блока остаётся `RAG_CONTEXT_MAX_TOKENS = 3000`);
* **предел ответа** — 1000 → 512 токенов: ответ дешевле по времени и не уходит в

### Ресурсы и скорость

Ресурсы берутся у самой Ollama: `GET /api/ps` после прогона варианта отдаёт `size`
(модель целиком), `size_vram` (её часть в видеопамяти) и `context_length`; в отчёте это
`VRAM, МБ`, `GPU, %` = 100·`size_vram`/`size` и `Окно контекста`. Меньше 100 % GPU —
модель не влезла в VRAM и часть слоёв считает CPU (это то, ради чего сравнивается
квант). Скорость: `Время, с` — весь запрос (включая прогрев весов), `Токенов/с` — по
`eval_duration` Ollama (только генерация), `Прогрев, с` — по `load_duration`.

```powershell
ollama ps                                 # то же в таблице
```

## 12. Удалённая LLM (Ollama в Colab, день 30)

Раздел «🛰 Удалённая LLM» соединяет программу с моделью, которая работает **не на этой
машине**: ячейка в Google Colab (бесплатный GPU T4) поднимает Ollama и туннель
Cloudflare, а программа ходит на выданный адрес по HTTP (`POST {Base URL}/chat/completions`
в формате OpenAI). Ничего не нужно ставить локально поверх дня 26 — это третий провайдер
ответа рядом с `deepseek` и `local`.

### Как поднять сервис в Colab

1. Открыть <https://colab.research.google.com> и переключить среду на GPU: меню
   «Среда выполнения» → «Сменить среду выполнения» → `T4 GPU`.
2. Выполнить в ячейке:

```bash
uvx collab-ollama --model qwen2.5-coder:7b
```

3. Ячейка печатает Base URL вида `https://xxxx.trycloudflare.com/v1` — скопировать его.
4. Проверить адрес можно в браузере (`{Base URL}/models`) или кнопкой в разделе.

Бесплатная сессия Colab живёт ограниченное время и засыпает после простоя: ячейка умирает
вместе с туннелем, и адрес перестаёт отвечать. Лечится перезапуском ячейки и **новым**
Base URL.

### Как вписать адрес

| Что | Значение |
|---|---|
| Base URL туннеля | адрес из ячейки, вместе с `/v1` (поле раздела; если он задан в `REMOTE_LLM_URL` в `day21/.env`, поле уже заполнено) |
| Модель | `qwen2.5-coder:7b` — тег из команды ячейки |
| API-ключ | любая непустая строка, по умолчанию `ollama`; уходит заголовком `Authorization: Bearer`, но Ollama его не проверяет |

Настройки `.env` (читаются на импорте — после правки перезапустить бэкенд):

| Переменная | По умолчанию | Что делает |
|---|---|---|
| `REMOTE_LLM_URL` | пусто | адрес туннеля; пусто — значит вписать руками в поле раздела |
| `REMOTE_LLM_MODEL` | `qwen2.5-coder:7b` | тег модели в Colab |
| `REMOTE_LLM_API_KEY` | `ollama` | содержимое заголовка `Authorization` |
| `REMOTE_LLM_RATE_LIMIT` | `10` | предел частоты клиентского счётчика (окно 60 с) |
| `REMOTE_LLM_MAX_CONTEXT` | `4096` | окно контекста, уходит в Ollama как `options.num_ctx` |

### Два слайдера на экране

* **«Rate limit (запросов в минуту)»** — 1…30, по умолчанию 10. Это счётчик **клиента**
  (`RemoteLLMClient`): пока в текущую минуту уложилось меньше N запросов, они уходят в
  сеть, а N+1-й отклоняется уже на нашей стороне с ошибкой 429 и текстом «Rate limit
  exceeded» — в Ollama он не попадает. Сервис в Colab, если его ничто не ограничивает,
  принял бы и больше.
* **«Max context (токенов)»** — 1024…8192 шагом 1024, по умолчанию 4096. Уходит в Ollama
  полем `options.num_ctx` (расширение Ollama поверх OpenAI-формата; поддержано не всеми
  версиями — если версия его игнорирует, ответы всё равно придут).

Полный сценарий из пяти шагов проходит при лимите **от 3**: три вопроса шагов 2–4 идут в
общее окно минуты, поэтому при лимите 1–2 демо упрётся в отказ раньше пятого шага. Когда
слайдер ниже 3, раздел сам пишет об этом предупреждение.

### Прогон одной кнопкой

1. Поднять сервис: `uv run uvicorn backend.api.main:app --port 8000` и
   `uv run streamlit run app.py` (в браузере — <http://localhost:8501>).
2. Открыть раздел **«🛰 Удалённая LLM»**, вставить Base URL, при необходимости поправить
   модель, ключ и слайдеры.
3. Нажать **«🔌 Проверить соединение»** — это `GET {Base URL}/models`. Зелёная плашка
   печатает, сколько моделей доступно и за сколько секунд ответил запрос, красная —
   причину (пустой адрес, туннель не отвечает, сервис вернул ошибку). Проверка связи не
   тратит бюджет частоты.
4. Нажать **«🚀 Прогнать демо одной кнопкой»**. Прогресс-бар идёт по шагам, потому что
   каждый шаг — отдельный HTTP-запрос (прогон переживает закрытие вкладки):

| Шаг | Что проверяет |
|---|---|
| 1. Проверка соединения | `GET /models`: «✅ Соединение установлено, доступно N моделей» |
| 2. Простой вопрос | «Столица Франции?» — ответ приходит по сети, а не от локальной модели |

Сквозной прогон того же пути проверяется тестом без фейков — он идёт по настоящему туннелю:

ответил, проверка строгая: пять строк по порядку, есть токены ответа, провайдер `remote`,

* туннель бесплатного тарифа живёт часами и умирает вместе с сессией Colab;
* через туннель используются только `{Base URL}/v1/models` и
  `{Base URL}/v1/chat/completions`;
* первый ответ включает загрузку модели в память GPU, поэтому предел ожидания одного
  запроса — 120 с (`REMOTE_LLM_TIMEOUT`).

## 13. Частые ошибки

| Симптом | Причина | Что делать |
|---|---|---|
| «Модель эмбеддингов не загрузилась … задайте DAY21_EMBEDDING_MODEL» | нет сети или веса не скачаны | подключиться к сети; либо `--stub-embedder`; либо указать другую модель |
| `409` на `GET /indexing/search` | индекс пуст | выполнить индексацию (кнопка или `POST /indexing/run`) |
| В статистике чанков вдвое больше | прогон дописывает индекс | очистить индекс и прогнать заново |
| Доля кэша всегда 0 % | меняется стабильный префикс (профиль, инварианты, промпт) или запросов слишком мало | выровнять инструкции агента; первый запрос всегда промах — кэш наполняется |
| `400` на `GET /llm/usage` | неизвестный период | допустимы `day`, `week`, `month`, `all` |
| Задача с `prefer_off_peak` не побежала сразу | первый запуск перенесён в непиковое окно — так и задумано | посмотреть `next_run_at` в разделе «🗓 Планировщик»; убрать флаг, если запуск нужен сейчас |
| Прогноз экономии не показывается | в журнале нет записей за период | сделать ход в чате или прогнать демонстрацию |
| Нужный тест не запускается при быстром прогоне | он помечен `slow` (интеграция, e2e) | запустить полный набор: `uv run pytest -m ""` или `uv run pytest --run-slow` |
| `uv run pytest -k имя` ничего не находит | имя из интеграционного файла, а он отложен маркером | добавить `-m ""`: `uv run pytest -m "" -k имя` |
| `409` на `POST /rag/query` | корпус RAG не проиндексирован | запустить `scripts/prepare_rag_corpus.py` и `scripts/index_rag_corpus.py` |
