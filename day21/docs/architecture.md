# Архитектура приложения — индексация документов и оптимизация затрат (день 21)

Приложение дня 21 — копия агента DeepSeek дня 20 (FastAPI-бэкенд + Streamlit,
SQLite) с двумя надстройками:

1. **индексация документов** — набор документов в `documents/`, две стратегии
   чанкинга (фиксированное окно по токенам и структурная — по секциям), эмбеддинги
   `sentence-transformers` в FAISS, метаданные чанков в `document_chunks`, журнал
   прогонов `index_runs`, автоматическое сравнение стратегий по метрикам;
2. **оптимизация затрат на LLM** — `PromptBuilder` с кэшируемым стабильным
   префиксом, `PromptCompressor` для динамической части, `LLMClient` с выбором
   модели и предела ответа по типу задачи, журнал `llm_usage` и перенос тяжёлых
   задач в непиковые часы DeepSeek.

Унаследованное: память, стратегии контекста, профиль, состояние задачи и переходы,
инварианты, MCP-клиент и собственный сервер, флот MCP-серверов, планировщик,
пайплайн и оркестрация — копия `day20/`, их архитектура в
`day20/docs/architecture.md`.

## Индексация документов (день 21)

Задание дня — **проиндексировать документы и сравнить две стратегии чанкинга**.
Приложение дня 20 остаётся как есть; день 21 добавляет RAG-слой.

### Документы и их источники

Набор документов — **данные** (`backend/domain/document_sources.py`):
`DOCUMENT_SOURCES` перечисляет 25 источников репозитория с пределом символов —
шестнадцать README (дни 5–12 по 2000 символов, дни 13–17 по 4000, дни 18–20 по
8000), три `docs/architecture.md` (дни 9, 13, 20) и четыре исходника с
`ast`-структурой (`context_fsm.py`, `context_policy.py`,
`task_state_machine.py`, `pipeline_mapping.py`) по 12 000 символов, плюс корневые
`AGENTS.md` (8000) и `README.md` (5000). Суммарно ≈ 125 000 символов ≈ 70 страниц.

Предел нужен потому, что README дня 20 весит 285 КБ: целиком он задавил бы
остальные документы, и «сравнение стратегий» превратилось бы в сравнение файла с
самим собой. Усечённый документ получает маркер `<!-- документ усечён -->`, и
признак усечения уезжает в манифест и в отчёт.

PDF-источников в дне нет: генерация PDF потребовала бы новой зависимости, а
внешние статьи — сети и лицензий. Задание дня допускает «сгенерировать **или**
использовать публичные», и роль «статей» играют документы репозитория.

### Блоки документа: почему это отдельный слой

Чанкер работает не с сырым текстом, а с **блоками** (`backend/domain/chunking.py`):

| вид документа | блок |
|---|---|
| `markdown` (`.md`) | секция от заголовка ATX (`#`…`######`) до следующего заголовка **любого** уровня; текст до первого заголовка — преамбула с пустым заголовком |
| `code` (`.py`) | секция от top-level `def`/`async def`/`class` (начало — строка первого декоратора) до начала следующей; последняя секция тянется до конца файла; текст до первого определения — блок `module` |
| `plain` (прочее) | абзац, разделённый пустой строкой (разделитель достаётся предыдущему абзацу) |

Главное свойство — блоки **делят текст без пропусков и перекрытий**. Отсюда
следуют три вещи, на которых держится весь день:

1. `content` любого чанка — это срез исходного текста, а `start_char`/`end_char`
   точны (проверяется тестом `text[start:end] == content`);
2. один и тот же текст не попадает в индекс дважды: иерархия markdown НЕ
   разворачивается в перекрывающиеся секции (секция первого уровня не забирает
   свои подсекции), а уровень заголовка сохраняется в `level` → `section_level`;
3. метрика покрытия честная: у фиксированной стратегии она 100 % (её окна
   покрывают все блоки), у структурной — 100 % на markdown и меньше на файлах, где
   между секциями есть модульный код.

Битый Python (`SyntaxError`) чанкинг не роняет: секции ищутся по строкам-шаблонам
(`^(def |class |async def |@)`), а если и их нет — блоком становится весь файл.
Смещения строк в символы переводятся один раз (`line_offsets`).

### Две стратегии чанкинга

`backend/services/chunker.py` содержит обе реализации за одним интерфейсом
(`chunk(document) -> list[Chunk]`), поэтому сравнение идёт на одном и том же входе.

**`FixedSizeChunker`**: окно набирается из блоков, пока **измеренное** число
токенов (tiktoken `cl100k_base` через `shared.token_counter.count_tokens`) не
упрётся в `CHUNK_SIZE_TOKENS = 512`. Следующее окно начинается с «хвоста»
предыдущего не длиннее `CHUNK_OVERLAP_TOKENS = 50`; хвост собирается **целыми
блоками**, потому что перекрытие из половины абзаца дало бы чанк, начинающийся на
середине предложения. Если последний блок окна сам длиннее перекрытия —
перекрытием становится он один. Блок длиннее окна режется внутри себя. У чанков
этой стратегии `section = ""` и `section_level = 0`.

**`StructuralChunker`**: чанк — секция документа. Секция короче
`CHUNK_MIN_SECTION_TOKENS = 20` не становится чанком (заголовок без тела): она
присоединяется к следующей, а последняя — к предыдущей; если секция в документе
одна, она остаётся как есть. Секция длиннее окна режется, но `section` и
`section_level` остаются у **всех** её частей.

Оба чанкера нумеруют чанки (`chunk_id = f"{strategy}:{source}:{index:04d}"`) и
возвращают их по возрастанию `start_char`.

### Эмбеддинги

`backend/services/embedding_service.py` — `EmbeddingService`:

* модель по умолчанию `sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2`
  (понимает русский; переопределяется `DAY21_EMBEDDING_MODEL`);
* `max_seq_length = 512` выставляется явно: базовое значение модели (128 токенов)
  молча обрезало бы чанк фиксированной стратегии, и сравнение стратегий потеряло
  бы смысл;
* `normalize_embeddings = True`: векторы единичной длины, поэтому скалярное
  произведение в FAISS равно косинусной близости;
* батчи по `EMBEDDING_BATCH_SIZE = 32`;
* `sentence_transformers` импортируется **внутри** `_load`: импорт на уровне модуля
  потянул бы torch и задержал старт бэкенда, а офлайн-тесты стали бы невозможны;
* модель процесса одна (`get_embedding_service`), вызовы сериализуются блокировкой:
  прогон идёт в фоновом потоке, а интерфейс может попросить поиск в тот же момент;
* сбой загрузки — `EmbeddingError` с текстом «не удалось загрузить модель …;
  задайте DAY21_EMBEDDING_MODEL или прогрейте кэш `index/models`»; сам `warmup()`
  исключений не бросает, потому что вызывается демон-потоком на старте.

### Векторный индекс и метаданные

`backend/services/index_service.py` — `IndexService`:

* индекс — `faiss.IndexIDMap2(faiss.IndexFlatIP(dim))`: плоский индекс на
  нормализованных векторах (косинус как скалярное произведение) с **явными id**;
* id вектора = `document_chunks.id`, поэтому второй источник истины «какой вектор
  какому чанку соответствует» не нужен: FAISS отдаёт id, а
  `ChunkStore.rows_by_ids` возвращает метаданные **в том же порядке**;
* файлы `index/fixed.index` и `index/structural.index`
  (`faiss.write_index`/`read_index`); при старте бэкенда — `load_all()`, при
  остановке — `save_all()`; отсутствующий файл — не ошибка (`loaded: false`);
* `index_chunks(chunks, strategy, progress)`: эмбеддинги батчами с отчётом о
  прогрессе → строки в SQLite (id известны) → `add_with_ids` → запись файла;
* `search(query, top_k, strategy)`: `IndexNotBuiltError` на пустом индексе
  (роутер отвечает 409 — «нечего искать», а не «ничего не нашлось»), попадания с
  `rank`, `score`, `chunk_id`, `source`, `title`, `section`, `token_count`,
  границами, `content` и `preview`;
* `get_stats(strategy)` — число чанков, суммарный/средний/минимальный/максимальный
  размер, σ, документы, разбивка по документам, чанки с секцией, гистограмма, файл
  индекса с объёмом и `index_vectors` (число векторов в FAISS — рядом с `chunks`,
  чтобы расхождение файла индекса и таблицы не было молчаливым);
  индекса нет — нули без исключения;
* `clear_index(strategy)` — память, файл и строки таблицы; **повторный прогон
  индекс дописывает**, неявной переиндексации нет.

### Поток данных демо-сценария

```
DOCUMENT_SOURCES ──collect()──► documents/*.md|txt|py + manifest.json
        │
        ▼  chunk_document(doc, strategy)
   блоки ──► чанки (fixed: окно 512/50; structural: секции)
        │
        ▼  EmbeddingService.encode (sentence-transformers, 512 токенов, батчи)
   векторы ──► faiss.IndexIDMap2(IndexFlatIP)  ──── id ───┐
        │                                                  ▼
        └── метаданные ──► SQLite: document_chunks ──► ChunkStore.rows_by_ids
        │
        ▼  search(query) — 5 тестовых запросов на каждой стратегии
   попадания ──► precision@k / recall@k, покрытие, размеры, структура
        │
        ▼
   index_runs.metrics (JSON) ──► отчёт docs/reports/indexing_demo.md, интерфейс
```

Прогон идёт по стейт-машине `backend/domain/indexing_fsm.py`: `loading →
chunking → embedding → indexing → searching → comparing → completed`, а у
одиночной стратегии после `indexing` сразу `completed` (`DONE` вместо `INDEXED`:
сравнивать нечего). Значения состояний — это ровно статусы колонки
`index_runs.status`, поэтому интерфейс показывает тот же этап, что записан в БД.
Этап пишется в БД **в начале** своей работы, а терминальный статус — вместе с
метриками (`finish_run`), иначе читатель увидел бы «завершено» без метрик.

Стенд прогона (`scripts/indexing_scenarios.py`) работает на **той же БД, что
приложение** (`day21/agents.db`), и на **рабочих** файлах `index/`: векторы лежат в
общих файлах, поэтому метаданные обязаны быть в общей таблице — иначе запущенный
бэкенд прочитал бы чужие векторы и не нашёл к ним строк (поиск вернул бы пустой
список при непустом индексе). Перед прогоном стенд чистит индексы, чтобы число
чанков не зависело от прошлых прогонов; рабочую БД он при этом не удаляет.

### Метрики сравнения

`backend/domain/index_metrics.py` — чистая арифметика, отдельно от прогона:

| метрика | как считается |
|---|---|
| `size_stats` | count, avg, median, σ (`pstdev` — совокупность, а не выборка), min, max; округление до 0.1 |
| `histogram` | бакеты `0-128`, `129-256`, `257-384`, `385-512`, `513+`; верхняя граница входит в бакет |
| `coverage_ratio` | длина **объединения** интервалов чанков, делённая на суммарную длину документов: перекрытие окон не удваивает покрытие, а документ без чанков в знаменатель входит (иначе покрытие росло бы от того, что часть документов не проиндексирована) |
| `structure_ratio` | доля чанков с непустой секцией |
| `precision_recall` | precision@k = релевантные среди первых k (по фактическому числу возвращённых, если их меньше k); recall@k = релевантные среди первых k, делённые на `relevant_total` — число чанков стратегии, чьи источники входят в ожидаемые (`ChunkStore.chunks_by_sources`); усреднение по запросам, запрос без релевантных чанков в индексе в среднее recall не входит |
| `comparison_rows` | строки таблицы отчёта: метрика, fixed, structural, комментарий; отсутствующий ключ печатается «—», а не падением |
| `ascii_histogram` | текстовая гистограмма — отчёт обязан собираться без браузера |

Ground truth — пять тестовых запросов (`backend/domain/index_scenarios.py`):
оркестрация флота, стейт-машина сжатия, контролируемые переходы, планировщик
фоновых задач и декларативный пайплайн. Запросы
проверяются `validate_queries` (непустой текст и ожидаемые источники, которые есть
среди `DOCUMENT_SOURCES`) до создания строки запуска: опечатка в slug'е давала бы
вечный recall 0 и выглядела бы как плохая стратегия.

### Место шага поиска в `generate()`

`Agent.apply_index_context` делает шаг поиска **до** контроля лимита (добавленный
блок обязан в лимит войти) и **после** шага пайплайна:

* поиск выполняется, только если индекс непуст (`indexing_service.index_size`);
  иначе ход агента не меняется вовсе — первый же вопрос пользователя не должен
  отвечать ошибкой «нечего искать»;
* реплику модель не классифицирует: поиск по документам — дешёвая операция чтения,
  а не действие с побочным эффектом;
* реплика, занятая пайплайном или оркестрацией, поиск не делает — «один ход — один
  автоматизм»;
* найденные фрагменты уходят системным блоком «## Контекст из индекса документов»
  (источник, секция, оценка и выдержка до 300 символов);
* сбой поиска (модель недоступна, индекс повреждён) ход не роняет: он виден текстом
  в `record["indexing"]["error"]`, а ответ строится без фрагментов.

### Почему логика прогона разделена на три модуля

`indexing_service.py` отвечает на вопрос «когда запускать и что отдавать API»,
`index_runner.py` — «как идут этапы по FSM с журналом прогресса»,
`index_comparison.py` — «как из чисел собрать метрики». В одном файле это было 487
строк — за лимитом 400; граница проведена по вопросам, а не по объёму.

## Оптимизация затрат на LLM (день 21)

День снижает счёт за запросы четырьмя рычагами, каждый — отдельным модулем, и
считает их вклад чистой арифметикой. Числа отчёта
`docs/reports/cost_optimization.md`: нагрузка дня дешевле на **39.3 %** (диалог —
21.5 %, тяжёлая задача — 50.0 %).

### PromptBuilder: зоны и кэш стабильного префикса

`backend/core/prompt_builder.py` собирает промпт строго по зонам:

1. **стабильный префикс** — `profile → system → invariants → tools → examples →
   general`. Профиль идёт первым: он одинаков во всех запросах одного пользователя
   и должен образовывать общий префикс;
2. **динамическая часть** — блоки `dynamic` (память, состояние задачи) и
   `tool_results` (результаты инструментов); они проходят через
   `PromptCompressor`;
3. **хвост** — инструкция о длине ответа; стоит последней и только при непустом
   остальном содержимом.

Кэш контекста DeepSeek сопоставляет самый длинный общий префикс запроса, поэтому
собранный стабильный префикс кладётся в кэш экземпляра по кортежу непустых частей:
повторный вызов получает ту же строку без повторной конкатенации. Стабильный
префикс **никогда не сжимается** — сжатие меняло бы текст префикса и убивало кэш.
Guard `looks_dynamic` ловит метку времени или hex-id в стабильных частях: такой
префикс заведомо меняется каждый запрос, поэтому он не кладётся в кэш, а в лог
идёт предупреждение. `PromptBuilder.max_tokens_for` зажимает предел ответа,
`cache_hits`/`cache_misses` видны в `GET /llm/status`. Синглтон —
`get_prompt_builder()`, сброс — `reset_prompt_builder()`.

### PromptCompressor: что снимается и где НЕ применяется

`backend/services/prompt_compressor.py` убирает **только украшения разметки**, не
перефразируя текст:

1. `remove_comments` — `<!-- ... -->` (в том числе многострочные);
2. `minify_json_blocks` — минифицирует JSON внутри блоков в тройных бэктиках, если
   содержимое разбирается `json.loads`; блок целиком из JSON без забора
   минифицируется целиком (общие правила пробелов к нему не применяются — они бы
   испортили значение строки);
3. `dedupe_lines` и `dedupe_paragraphs` — подряд идущие дубли;
4. `normalize_whitespace` — хвостовые пробелы, ≥3 переводов строки → два, несколько
   пробелов подряд → один;
5. обрезка ведущих и хвостовых пустых строк.

Шаги 1, 3, 4 идут только по тексту **вне** блоков кода: проглотить пробелы внутри
примера кода значило бы сломать сам пример. Модуль идемпотентен (повторное сжатие
ничего не меняет) — блоки могут проходить через него дважды: при сборке промпта и
при дописывании блоков агентом. К стабильному префиксу промпта сжатие **не
применяется** (см. `PromptBuilder`). `stats` и `reset` — для отчёта и тестов.

### LLMClient: модель, предел ответа, метрики кэша, журнал

`backend/services/llm_client.py` — единственная точка вызова DeepSeek:

* `select_model(task_type)` выбирает модель по таблице `LLM_TASK_MODELS`:
  `chat`, `summarize`, `classify`, `keywords` идут на `deepseek-chat`;
  `orchestration`, `code`, `indexing` — на `deepseek-reasoner`;
* `max_tokens_for(task_type, limit)` берёт предел из `LLM_TASK_MAX_TOKENS`
  (1000 по умолчанию, 4000 для `code`/`indexing`);
* `call(...)` выбирает модель и предел, извлекает из ответа
  `prompt_cache_hit_tokens` / `prompt_cache_miss_tokens`, считает стоимость
  (`backend/domain/llm_cost.py`) и пишет строку в журнал;
* клиентский объект берётся из фабрики `client_factory`; в приложении это
  `Agent._make_client`, поэтому подмена клиента в тестах по-прежнему видна;
* сбой записи в журнал запрос не ломает: расходы — учёт, ошибка идёт
  предупреждением в лог.

`LLMCallResult` возвращает исходный объект SDK вместе с `to_dict()` (модель, токены,
`cache_hit`/`cache_miss` и доля попаданий) — этим словарём заполняется поле `llm`
ответа генерации. `get_usage_stats(agent_id, period)` и `usage(...)` читают агрегаты
из журнала.

### Домен стоимости и журнал `llm_usage`

`backend/domain/llm_cost.py` — чистая арифметика (ни сети, ни БД):

* `prices_for(model)` — цены за 1M токенов (`{"in", "out"}`);
* `estimate_cost(model, prompt_tokens, completion_tokens, cache_hit_tokens)` —
  стоимость запроса; попадание в кэш считается по `LLM_CACHE_INPUT_RATIO = 0.1`
  (10 % цены ввода);
* `cache_savings`, `compression_savings`, `off_peak_savings` — вклад каждого рычага
  отдельно; `savings_summary` собирает их в одну таблицу;
* `aggregate_costs(rows)` — агрегаты по строкам журнала.

Журнал — таблица `llm_usage` (`backend/models/llm_usage.py`): `id`, `agent_id`,
`timestamp`, `model`, `prompt_tokens`, `completion_tokens`, `cache_hit_tokens`,
`cache_miss_tokens`, `cost_estimate`, `request_type`, `created_at`. Хранилище —
`backend/storage/llm_usage_store.py` (`LLMUsageStore`): пишет строку, отдаёт
последние запросы и агрегаты за период (`LLM_USAGE_PERIODS`: `day`/`week`/`month`/
`all`), включая разбивку по моделям, типам задач и дням. Проекции строк —
`backend/storage/llm_usage_rows.py`.

### Непиковые часы и планировщик

`backend/domain/peak_hours.py` — чистые правила окна скидки в UTC:

* непик — будни 00:00–01:00, 04:00–06:00, 10:00–24:00 и все выходные;
* пик — будни 01:00–04:00, 06:00–10:00.

`is_off_peak`, `next_off_peak` (ищет **строго позже** переданного момента),
`peak_status`, `savings_forecast`. `backend/services/off_peak.py` — `shift_to_off_peak`:
если у задачи в JSON-колонке `schedule_value` стоит флаг `prefer_off_peak`, пиковый
первый запуск сдвигается на начало ближайшего непикового окна (решение пишется в
лог). Флаг живёт **внутри JSON**, а не отдельной колонкой `scheduled_tasks`:
старые базы от новой колонки сломались бы, а расписание и так читается из JSON.
Сдвиг применяется **один раз** — при постановке: у cron расписание считает
APScheduler, и перенос каждого следующего запуска поломал бы его триггер. Модуль
`off_peak.py` вынесен из `scheduler.py`, который упёрся в лимит 400 строк.

### API `/llm` и вкладка «💰 Расходы»

`backend/api/llm.py` — пять эндпоинтов:

| метод и путь | что отдаёт |
|---|---|
| `GET /llm/usage` | агрегаты журнала за период (токены, доля кэша, стоимость, разбивка по моделям и типам) + последние запросы |
| `GET /llm/status` | пик или непик сейчас, когда начнётся дешёвое окно, статистика кэша префиксов и сжатия |
| `POST /llm/estimate` | прогноз экономии по числам токенов: вклад кэша, сжатия, предела ответа и непика по отдельности |
| `GET /llm/models` | модель и предел ответа по типу задачи |
| `GET /llm/peak` | пиковые и непиковые окна DeepSeek (UTC) |

Числа нигде не пересчитываются на стороне роутера: их дают хранилище журнала и
домен стоимости, поэтому вкладка «Расходы», отчёт об оптимизации и API показывают
одни суммы. В интерфейсе это `frontend/cost_section.py` (пик/непик, кэш контекста,
сжатие, расход по дням, последние запросы, маршрутизация моделей) поверх
`frontend/cost_api.py`.

### Место `record["llm"]` в `generate()`

В словаре-заготовке хода `record["llm"] = None`; после вызова модели он
заполняется `call.to_dict()` (`agent.py`). Поле видно в ответе генерации и в сводке
хода в чате. Сам шаг поиска по индексу описан выше и стоит отдельно: `record["indexing"]`.

## Схема БД (`day21/agents.db`)

День 21 добавляет к схеме дня 20 три таблицы: две индексации (`document_chunks`,
`index_runs`, ORM — `backend/models/indexing.py`) и одну журнала расходов на LLM
(`llm_usage`, ORM — `backend/models/llm_usage.py`). Остальные таблицы (агент и его
память, профиль, состояние задачи и переходы, инварианты, планировщик, пайплайн,
оркестрация) унаследованы из дня 20 — см. `day20/docs/architecture.md`. Файл
`day21/storage.db` (таблица `saved_records` сервера хранения) в схему дня не входит:
его пишет только процесс `storage_server`.

**`document_chunks`** — чанк документа (день 21).
`id` (Integer PK, autoincrement), `source` (String(`INDEX_SOURCE_MAX` = 128),
index — имя файла в `documents/`, например `day20-readme.md`), `title`
(String(`INDEX_TITLE_MAX` = 200) — заголовок документа), `section`
(String(`INDEX_SECTION_MAX` = 200), nullable — заголовок раздела у структурной
стратегии, `""` у фиксированной), `chunk_id` (String(`INDEX_CHUNK_ID_MAX` = 200),
index — `structural:day20-readme.md:0007`; **НЕ unique**: повторный прогон
дописывает индекс, и уникальность превратила бы кнопку демо-прогона в
одноразовую), `strategy` (String(`INDEX_STRATEGY_MAX` = 16), index — `fixed` или
`structural`), `content` (Text), `token_count` (Integer — измеренный размер в
токенах), `embedding_id` (Integer — id вектора в FAISS, равный `id`), `start_char`
и `end_char` (Integer — границы чанка в тексте документа), `section_level`
(Integer — уровень заголовка, 0 у преамбулы и фиксированных чанков), `created_at`
(DateTime, UTC). Проекция строки — `chunk_dict` (`backend/storage/index_rows.py`).

**`index_runs`** — запуск индексации (день 21).
`id` (Integer PK, autoincrement), `strategy` (String(`INDEX_STRATEGY_MAX`), index —
`fixed`/`structural`/`demo`), `status` (String(`INDEX_STATUS_MAX` = 16), index —
значения `IndexingState`: `loading`/`chunking`/`embedding`/`indexing`/`searching`/
`comparing`/`completed`/`failed`), счётчики `documents_total`, `documents_done`,
`chunks_fixed`, `chunks_structural`, `embeddings_total`, `embeddings_done` (все
Integer, default 0), `started_at` / `finished_at` (DateTime, UTC; `NULL`, пока
прогон идёт), `duration_ms`, `embed_duration_ms`, `index_duration_ms` (Integer),
`metrics` (JSON, nullable — документы, запросы, метрики обеих стратегий, таблица
сравнения, модель эмбеддингов) и `error` (Text, nullable). Строка создаётся **до**
старта фонового потока и получает терминальный статус вместе с метриками: прогресс
опрашивает другой процесс (Streamlit), поэтому память процесса такого не переживёт.
Проекция строки — `index_run_dict`; хранилище — `IndexRunStore`
(`backend/storage/index_run_store.py`).

**`llm_usage`** — журнал расходов на LLM (день 21).
`id` (Integer PK, autoincrement), `agent_id` (String(`LLM_USAGE_AGENT_MAX` = 64),
index, nullable), `timestamp` (DateTime, index), `model` (String(
`LLM_USAGE_MODEL_MAX` = 64)), `prompt_tokens` и `completion_tokens` (Integer),
`cache_hit_tokens` и `cache_miss_tokens` (Integer — раздельно: попадание в кэш
дешевле обычного ввода), `cost_estimate` (Float — стоимость запроса по формулам
`domain/llm_cost.py`), `request_type` (String(`LLM_USAGE_TYPE_MAX` = 32), index —
тип задачи) и `created_at` (DateTime, UTC). Строку пишет `LLMClient.call` через
`LLMUsageStore` — единственное место записи, иначе строки разошлись бы по формату.

## Архитектурный этап

Задание дня приходит «сырым» — текстом из челленджа. Из размытого ТЗ получается
размытый Definition of Done, и агент незаметно решает похожую задачу вместо
поставленной. Поэтому сложное задание сначала прогоняется через шаблон
[`ARCHITECT_PROMPT.md`](../../ARCHITECT_PROMPT.md) в отдельном чате с DeepSeek:
шаблон требует декомпозицию с DoD, пошаговый план (файлы, команды, ожидаемый
результат), риски с планом Б, проверки и команды фиксации. Структурированный план
передаётся в omp.sh как постановка дня — агент исполняет пункты плана, а не
пересказ задания; готовый план повторно не планируется.

Правило зафиксировано в [`AGENTS.md`](../AGENTS.md) (раздел «Архитектурный этап»,
шаг 0 в «Рабочем процессе») и в sticky-правилах [`.omp/RULES.md`](../.omp/RULES.md),
маршрут целиком — в [`WORKFLOW.md`](../WORKFLOW.md). Простые задачи (кнопка, текст,
документация) идут без планирования: архитектурная ступень стоит запроса к модели
и нужна там, где цена ошибки в постановке выше её стоимости — новые модули,
интеграции, изменения архитектуры, MCP, планировщик, индексация.

## Тестовая инфраструктура

Набор дня 21 — **2521 тест** в 125 файлах; по умолчанию запускается 2446 (75
помечены `slow`). Запуск держится на четырёх решениях:

| Решение | Зачем и как |
|---|---|
| **Параллельный запуск** | `pytest-xdist`: `addopts = -n auto` в `pytest.ini` разносит тесты по всем ядрам (здесь 12) — 370 → 127 с. Изоляция обеспечена построением: у каждого теста своя временная SQLite, общие файлы дня тесты не пишут |
| **Общая схема БД на прогон** | `init_db` (`create_all` по ~25 таблицам) стоит ≈0,93 с — почти секунда на каждый тест с базой, и это был главный тормоз. Session-scoped фикстура `schema_template` строит схему один раз, а `session_factory` отдаёт тесту копию файла (2,65 мс) — 127 → 68 с. Изоляция сохранена: файл свой у каждого теста |
| **Маркер `slow`** | `pytest.mark.slow` + `addopts = -m "not slow"`: тяжёлые тесты (подпроцессы MCP-серверов по stdio, часть e2e) по умолчанию пропускаются, полный набор включают `-m ""` или `--run-slow`. Флаг реализован в `tests/conftest.py` (`pytest_addoption`) и снимает **дефолт** из `addopts`, не перебивая явный `-m` пользователя |
| **Моки внешних API и запрет сети** | `FakeClient` подменяет клиент DeepSeek; autouse-фикстуры `offline_planner` (модель планировщика оркестрации) и `isolated_indexing` (загрузка модели эмбеддингов запрещена — сотни мегабайт и сеть) держат тесты офлайн; `no_real_fleet` не даёт `lifespan` поднимать процессы флота; `no_real_network` роняет тест при TCP на нелокальный адрес, а стенды `stub_api`/`backend_stub` слушают 127.0.0.1 и работают |

Фикстуры разложены по доменам: общие и БД — в `tests/conftest.py`, флот и
оркестрация — в `tests/fixtures_fleet.py`, индексация — в
`tests/fixtures_indexing.py` (conftest импортирует их: pytest видит импортированные

## Ограничения

- **Повторный прогон дописывает индекс.** `index_chunks` не чистит индекс неявно:
  числа чанков растут (видно в статистике и истории запусков). Переиндексация с
  нуля — явный `POST /indexing/clear` / кнопка «🧹 Очистить обе стратегии».
- **Блоки кода покрывают не весь файл.** `ast`-секции начинаются с top-level
  `def`/`class`; модульные переменные и `if __name__` попадают в блок `module`, а на
  битом Python работает запасная эвристика по строкам.
- **Модель эмбеддингов одна на процесс** (`get_embedding_service`), вызовы
  сериализуются блокировкой: фоновый прогон и ручной поиск не идут параллельно.
- **Сжатие экономит мало на компактных блоках.** `PromptCompressor` убирает только
  разметку и повторы; на тексте без «воды» выигрыш близок к нулю (1.7 % на
  специально подобранном материале).
- **Непик зависит от тарифа провайдера.** Домен знает окна, но размер скидки —
  допущение: в отчёте это помечено явно.
- **Журнал `llm_usage` растёт и не чистится автоматически.** Есть окна периодов
  (`day`/`week`/`month`/`all`) для чтения, но удаления старых строк нет.
