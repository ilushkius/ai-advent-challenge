Правила работы в этом каталоге. Устройство дня — [`STRUCTURE.md`](STRUCTURE.md),

**Правила проекта — в корневых [`../AGENTS.md`](../AGENTS.md),
[`../RULES.md`](../RULES.md) и [`../docs/project-rules.md`](../docs/project-rules.md);
здесь только специфика дня.**

## Границы

- **Основная папка — `day21`.** Папки `day1`–`day20` — архивные снимки: не читать
  и не упоминать при работе. Они исключены из обхода поиска корневым
  `.gitignore` (omp `grep`/`glob`/`find` уважают его) и перечислены в
  `.clineignore`.
- **Не создавать новые папки `dayN`.** Состояние дня фиксируется git-коммитом и
  тегом `dayN`.
- **Все изменения — только в `day21/`** (плюс корневые `CHANGELOG.md` и
  `AGENTS.md`, если запись относится к дню).

## Документация и тесты

- Документация описывает **только текущее состояние** проекта: устаревшие
  сценарии удалять, не копировать из прошлых дней.
- Тесты не дублировать. Изменение функциональности отражать в **существующих**
  тестах; новый файл — только для новой сущности; похожие сценарии — один
  параметризованный тест (`@pytest.mark.parametrize`), а не три копии.
- Медленные тесты (дольше 1 секунды) помечать `@pytest.mark.slow`; тяжёлые
  ресурсы (БД, модели, клиент приложения) держать в фикстурах, а изменяемые
  данные — в function-scoped фикстурах на временной БД.
- Быстрая проверка при разработке — `uv run pytest -m "not slow"`; полный прогон
  перед коммитом — `uv run pytest -m ""`; покрытие бэкенда —
  `uv run pytest --cov=backend`. Лимиты строк — скилл
  `fastapi-streamlit-day-structure` (любой `.py` ≤ 400, `app.py` ≤ 100,
  `backend/api/main.py` ≤ 80).

## Обязательное завершение дня

День считается завершённым только при выполнении всех пунктов ниже. Если хотя бы
один не выполнен — день не закрывается.

1. **Код реализован и работает** — smoke-запуск изменённого пути, а не только тесты.
2. **Тесты проходят:** `uv run pytest -m "not slow"`, перед коммитом — `uv run pytest`.
3. **Документация обновлена:** `docs/usage.md` содержит раздел с инструкцией по
   запуску новой функциональности — команды, шаги и кнопки в UI, скрипты с флагами;
   `docs/architecture.md` описывает новую архитектуру и поток данных; `README.md`
   ссылается на новый функциональный блок и отчёт.
4. **Отчёт создан** — `docs/reports/<тема>.md` с результатами, если задание требует
   сравнения или демонстрации.
5. **Зафиксировано:** `git commit` с описанием дня, затем `git tag dayN`.
6. **Проверено в UI:** интерфейс запускается и новая функция доступна пользователю
   (если применимо).

**Правило проверки.** Перед `git commit` задать вопрос: «Если человек впервые откроет
проект через месяц, поймёт ли он, как запустить то, что я только что сделал?» Если
ответ «нет» — дописать документацию (раздел в `docs/usage.md`, ссылку в `README.md`,
схему в `docs/architecture.md`) и только потом коммитить. Быстрая проверка перед
коммитом — скилл `.agents/skills/check_docs/`.

## Инструменты

- Всегда `read` вместо `cat`/`head`/`tail`; `grep`/`glob` вместо `bash grep`/
  `find`/`ls`; `edit` вместо `sed -i` (включён `bashInterceptor`).
- Тяжёлые задачи (индексация, генерация сводок, пакетная обработка) планировать
  на **непиковые часы DeepSeek** — флаг `prefer_off_peak`,
  [`backend/domain/peak_hours.py`](backend/domain/peak_hours.py).

## Архитектурный этап (сложные задания)

Перед выполнением задания дня, если пользователь дал **сырое** описание задачи без
структуры DoD, шагов и рисков — сначала применить шаблон
[`../ARCHITECT_PROMPT.md`](../ARCHITECT_PROMPT.md) и получить структурированный
план. Только после этого приступать к реализации. Если пользователь дал уже
структурированный план — выполнять его напрямую. Простые задачи (кнопка, текст,
правка документации) можно выполнять без архитектурного этапа. Маршрут целиком —
[`WORKFLOW.md`](WORKFLOW.md).

## Рабочий процесс нового дня

0. Сложное задание без структуры — сначала план по `../ARCHITECT_PROMPT.md`
   (см. «Архитектурный этап»); задание со структурой — сразу к шагу 1.
1. Убедиться, что `git status` чистый.
2. Реализовать функциональность дня в `day21/`.
3. Обновить документацию (только текущее состояние): `README.md`,
   `STRUCTURE.md`, `docs/` — обязательно **с разделом в `docs/usage.md` о запуске
   новой функциональности** (см. «Обязательное завершение дня»).
4. Обновить или добавить тесты (не дублировать существующие).
5. Запустить `uv run pytest`.
6. Пройти чек-лист «Обязательное завершение дня» — без него день не закрывается.
7. Закоммитить с сообщением `dayN: краткое описание`.
8. Поставить git-тег `dayN`.
9. Создать отчёт в `day21/docs/reports/`, если он нужен заданию.
