# System Patterns — архитектура и паттерны

## Общая архитектура

**Моно-репозиторий с общим пакетом `shared/`**: приложения лежат в папках `day1/`,
`day2/`, `day3/`. У каждого дня свои `requirements.txt`, `.env` и запуск, но day2/day3
импортируют общие утилиты из `shared/deepseek_utils.py` (корень репозитория
добавляется в sys.path через `Path(__file__).resolve().parents[1]`). day1 остаётся
полностью автономным (консольный скрипт).

Исполняемые артефакты:
- `day1/deepseek_chat.py` — **консольный скрипт** (процедурный код + `while`-цикл).
- `day2/app.py`, `day3/app.py` — **Streamlit-приложения** (модель script-and-rerun:
  весь код выполняется сверху вниз при каждом взаимодействии).

Слоёв/MVC нет — это осознанно учебные одностраничники.

## Паттерны внутри приложений

1. **Константы и конфигурация наверху.** Поведение UI и промптов задают словари в
   начале файла: `REASONING_METHODS`, `REASONING_SYSTEM_PROMPTS`,
   `REASONING_METHOD_HINTS` (Day 3, ключи синхронизированы), `FINISH_REASON_LABELS`,
   `SYSTEM_PROMPT_JSON`. Общая константа `DEEPSEEK_BASE_URL` живёт в
   `shared/deepseek_utils.py` и импортируется.

2. **Общие helper-функции в `shared/deepseek_utils.py` + императивный UI-код.**
   В общий модуль вынесена переиспользуемая логика: чтение ключа из `.env`
   (`read_key_from_env_file`), разбор stop-строк (`parse_stop_sequences`),
   конвертация `usage` в dict, константа endpoint. Локально в приложении остаются
   функции, завязанные на промпты/параметры конкретного дня (`build_request_params`,
   `build_system_messages`, `run_meta_stage`). Виджеты и вкладки — напрямую в теле
   модуля (канон Streamlit).

3. **Params-dict как единый источник правды.** `build_request_params(...)` собирает
   полный dict запроса; тот же dict сохраняется в результат и рендерится во вкладке
   «Технический лог» → лог гарантированно совпадает с реальным API-вызовом.

4. **Состояние через `st.session_state`.** Результат запроса кладётся в
   `st.session_state["result"]` и не теряется при rerun; при ошибке — очищается и
   показывается `st.error`.

5. **Словарь промптов как стратегия (Day 3).** `selectbox` выбирает ключ → словарь
   даёт system-промпт и хинт. Добавление нового «способа рассуждения» = правка словаря.

6. **Двухэтапная оркестрация (Day 3, мета-промпт).** `run_meta_stage()` выполняет
   скрытый вызов (Шаг А: модель пишет «идеальный» промпт), затем текст промпта
   подставляется user-сообщением в финальный вызов (Шаг Б). Лог обоих этапов — в
   `meta_log`.

7. **Единый клиент DeepSeek = OpenAI SDK.** `OpenAI(api_key=..., base_url=
   "https://api.deepseek.com")` + `client.chat.completions.create(...)`. Стриминг —
   только в Day 1.

## Поток данных (Day 2/3)

1. Настройки в sidebar → значения виджетов.
2. Кнопка «Запустить» → валидация: пустой промпт, отсутствие ключа.
3. Сборка messages + params (в Day 3 для мета-промпта — сначала Шаг А).
4. `chat.completions.create(**params)`, замер времени через `time.monotonic`.
5. Из ответа: content, finish_reason, usage → `st.session_state["result"]`.
6. Вкладки рендерят: теги/метрики/карточка или `st.json` + технический лог с JSON
   для копирования.

## Безопасность вывода

- Текст модели перед выводом в markdown-карточку экранируется `html.escape`
  (Day 2/3) — ответ модели не ломает разметку и не вставляет HTML.
- В JSON-режиме ответ парсится `json.loads` → `st.json`; при ошибке парсинга —
  предупреждение + «сырой» текст.

## Ключевые технические решения

- DeepSeek через **OpenAI SDK**, а не прямой HTTP: меньше кода, стриминг, объекты
  с типами.
- Поиск ключа: `.env` → env-переменная → ручной ввод (без хардкода секретов).
- **Streamlit вместо консоли** со Дня 2 — вкладки/метрики/JSON-логи ради наглядности.
- Настройки Дня 2 **перенесены в День 3 как есть** — наследование фич между днями.
- Общие утилиты вынесены в `shared/deepseek_utils.py` (day2/day3) при сохранении
  автономного запуска каждого дня из своей папки.
